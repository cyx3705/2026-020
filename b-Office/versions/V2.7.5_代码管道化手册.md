# OneHistoryStudio / AppShell V2.7.5 代码管道化手册

> 状态：施工设计，尚未交付  
> 适用范围：`b-Code-AppShell`、`b-Code-Studio`，以及 AppShell 消费者 WBall  
> 目标版本：OneHistoryStudio 2.7.5 / AppShell 2.7.5  
> 基线：当前源码、运行时注册表与 `b-Office/meta/`；本文不依赖其他 V 文档

## 1. 本版要解决什么

前几个版本由 AI 高频开发，已经出现一种可重复的结构性风险：同一项功能事实被分别硬编码在命令注册、菜单、
工具窗口、MCP、Help、命令手册、Service 宿主、发布脚本和消费者装配点中。一次改动只更新其中几处时，程序仍可
编译，却会留下版本漂移、入口漂移、发布物膨胀和只在特定消费者出现的暗病。

V2.7.5 建立以下开发铁律：

> 一项事实只能有一个权威源；其他位置必须经注册、投影、生成或校验管道自动形成。

“管道化”不是把复制动作改成脚本，也不是增加另一份配置。合格管道必须同时满足：

1. 只有一个可人工维护的权威输入；
2. 下游产物可确定性重建；
3. 下游不得反向成为新真值；
4. 漂移可由构建、Smoke 或发布预检自动阻断；
5. 消费者可显式关闭未使用能力，关闭后不携带该能力的运行时依赖和默认副作用。

本版同时审查 SQLite 在 OHS 与 WBall 中的必要性。结论是两者均无数据规模或并发压力要求关系数据库；去库可行，
但 OHS 的审计与提示词治理必须先完成可校验迁移，不能把“数据少”误解为“数据可以丢”。

## 2. 当前审查结论

### 2.1 SQLite 实际占比

2026-07-28 对当前用户运行数据的只读盘点：

| 消费者 | `main.db` 大小 | 表数 | 总行数 | 主要数据 |
|---|---:|---:|---:|---|
| OHS | 124 KiB | 9 | 417 | `mcp_history` 371、`push_history` 38、工具/提示词治理 8 |
| WBall | 116 KiB | 12 | 86 | 场景对象 54、球 16、场景 12、阵营 4 |

代码接触面不是零：WBall 的性质投影与数据门面约占应用生产代码 7.03%；OHS 自身数据库接触文件约占生产代码
6.4%，另有 AppShell 的提示词治理和 MCP 审计实现。SQLite 发布依赖约 2.144 MiB，在一次 OHS 顶层发布文件
统计中约占 46%。因此问题不在数据库承压，而在通用依赖被 AppShell `Services` 强制传递给所有消费者。

### 2.2 WBall 判断

WBall 的业务真值已经存在于 `SceneWorld` 与场景 JSON。SQLite 中的 `balls`、`scene_objects`、`scenes`、
`wireframes`、`solids`、`factions` 是为通用表窗口形成的重复投影，不是恢复运行状态所必需的数据源。

WBall 可优先去库，但必须同时处理以下行为：

- 表窗口与 `db.*` 不再作为领域编辑入口；
- 球、对象、阵营和场景编辑继续通过领域命令进入 `SceneWorld`；
- 自定义球属性名需要轻量 schema 文件，不能依赖 SQLite 列定义；
- `scene.refresh` 直接扫描 `scenes/*.json`；
- WBall 必须显式设置 `EnableMcp=false`、`EnableModules=false`，不能承受 AppShell 默认能力变化；
- 旧 `main.db` 只保留，不删除，也不再写入。

### 2.3 OHS 判断

OHS 数据量同样不需要数据库，但数据语义比 WBall 重要：

| 现有数据 | 目标存储 | 写入语义 |
|---|---|---|
| MCP 调用留痕 | `state/mcp-history.jsonl` | 单条追加，失败旁路告警 |
| 项目操作留痕 | `state/push-history.jsonl` | 单条追加，失败旁路告警 |
| 分支说明 | `state/branch-notes.json` | 单进程锁 + 临时文件原子替换 |
| 工具溯源 | `state/tool-registry.json` | 单进程锁 + 原子替换，可由模块槽辅助核验 |
| 提示词修订/提案/勘误/事故 | `state/prompt-governance.json` | 同一文档内完成状态迁移后原子替换 |

提示词批准、应用、拒绝和回滚必须保持当前状态机约束。文件化不是把每张表机械导出成独立 JSON；关联状态应放在
同一原子文档中，避免一次操作跨多个文件只写成功一半。

## 3. 管道模型

每项功能应按以下单向链路建设：

```text
权威定义
  → 规范化与校验
  → 运行时注册表/领域服务
  → UI、Help、MCP、Web 等只读投影
  → 手册、包、manifest 等生成产物
  → 构建/Smoke/发布预检阻断漂移
```

禁止出现反向依赖。例如：

- UI 按钮文字不能成为命令名真值；
- 命令手册不能反向驱动运行时代码；
- MCP 只读名单不能再维护一份命令名白名单；
- 发布目录中的 DLL 不能反向覆盖源码目录；
- WBall 的 SQLite 投影不能反向恢复或覆盖 `SceneWorld`；
- V 版本施工文档不能成为后续开发的现行设计输入。

## 4. 必须管道化的事实

### 4.1 命令合同

权威源是最终进入 `CommandRegistry` 的 `CommandDescriptor`，它必须一次性声明：

- 名称、摘要、示例；
- 参数、类型、默认值、允许值和必填性；
- `Readonly`、危险确认、撤销能力和 UI 线程要求；
- 执行站点和结构化结果。

Help、命令集、MCP schema、Web 目录、命令手册和菜单校验只能读取该注册表。桌面与 Service 共用的命令元数据
必须在 AppShell.Core 的共享定义中维护，两个宿主只绑定各自 handler。

禁止：

- 在桌面与 Service 分别复制参数表；
- 为 MCP 再写命令名白名单；
- 菜单或按钮绕过 `CommandBus` 直接调用业务服务；
- 手工编辑 `meta/命令手册.md` 的命令条目。

验收：同一命令在 `help`、`command.show`、`mcp.schema` 和自动生成手册中的参数与只读性完全一致。

### 4.2 窗口身份与布局

AppShell 标准窗口 ID 只来自 `StandardWindowIds`。OHS 和 WBall 的业务窗口 ID 在各自宿主定义，但必须稳定、
小写且进程内唯一。布局文件只记录实例状态，不定义新窗口身份。

消费者通过一张 `ToolWindowDescriptor` 表声明窗口；菜单的显示/隐藏/浮动/复位项由窗口描述符集合生成。禁止在
布局、菜单、字符串命令和窗口工厂中分别维护同一个 ID。

### 4.3 MCP 暴露

内置命令只读性来自 `CommandDescriptor.Readonly`；模块命令的附加档位来自模块清单 `mcpExposure`；硬排除来自
AppShell 唯一策略函数。最终工具列表每次从当前命令注册表计算。

禁止按命令名补登记第二份只读集合。模块清单也不能把危险命令降级为无确认命令。

### 4.4 模块与工具同步

模块业务事实属于模块自身；OHS 只保存宿主集成事实。唯一输入是模块的 `module.manifest.json` 与构建产物，
同步管道负责：

1. 校验名称、路径、保留指令域和枚举值；
2. 计算源产物 SHA-256；
3. 重建 `Modules/<name>/` 临时槽；
4. 复制 DLL、XML、面板、清单和依赖；
5. 复制后复核哈希；
6. 原子替换目标槽；
7. 写入工具溯源状态；
8. 由模块监听器触发注册表换血和面板同步。

禁止手工把模块 DLL 同时复制到多个位置，禁止从发布槽回灌源码，禁止把模块原始文档复制到 OHS `b-Office`。

### 4.5 版本身份

OHS 与 AppShell 使用同一版本列车。版本值各自只允许一个项目级权威源，发布脚本必须求值读取，不得在脚本、
README、包工程和命令示例中分别维护当前版本常量。

发布预检至少比较：OHS 产品版本、AppShell 包版本、程序集文件版本、发布参数和文档适用版本。任一不一致即阻断。
WBall 等伞外消费者必须显式锁定 AppShell 包版本，不能隐式跟随开发目录。

### 4.6 命令手册与 Help

`meta/命令手册.md` 只能从当前运行时注册表生成。生成步骤必须进入发布脚本，并在生成后核对命令数和内容哈希。
其他五份 `meta` 手册由人维护稳定合同，但发布脚本应校验文件存在、链接有效、版本身份一致。

### 4.7 包依赖与消费者能力

AppShell 的能力必须分为“核心必需”和“消费者显式选择”。消费者没有启用某项能力时，不应因为引用 Shell 就获得
其原生运行时依赖、后台监听器、数据库文件或默认端口。

冻结前目标分层：

| 层 | 冻结后保留职责 | 不应包含 |
|---|---|---|
| Core | 命令、数据结构、日志/设置/模块/MCP 契约、窗口描述符 | WPF、SQLite、消费者业务 |
| Services | 设置、日志、工作区、模块、MCP/Web 通用服务、文件状态原语 | SQLite 强制依赖、表窗口 UI |
| Shell | WPF 外壳、停靠、控制台、资源和管理视图 | 消费者业务、默认创建数据库 |
| ServiceHost | 无 UI 服务生命周期和执行站点中继 | 第二套命令元数据、消费者领域对象 |
| Consumer | 能力开关、业务命令、业务窗口和领域存储 | AppShell 源码副本、隐式默认能力 |

若未来仍需要通用数据库浏览器，应作为独立可选包和插件交付，而不是回到 Services 的强制依赖。

## 5. AppShell 冻结前最小化

### 5.1 高体积/高耦合项排序

| 项目 | 体积/复杂度判断 | 冻结动作 |
|---|---|---|
| SQLite + 多 RID 原生库 | 发布体积显著，所有消费者被动携带 | 从默认包图移除；如保留则拆可选包 |
| 通用表窗口 + `db.*` | 需要 `IDataService`、SQL 片段和行定位合同 | OHS/WBall 移除入口；是否保留为可选组件另案评审 |
| WBall 性质投影 | 约占 WBall 生产代码 7.03%，且重复领域真值 | 删除数据库镜像，只保留领域编辑与轻量 schema |
| MCP/模块默认启用 | WBall 未显式关闭时会产生空表、监听器和隐性行为 | 所有消费者必须显式声明开关；新消费者默认最小能力 |
| ServiceHost | OHS 需要，WBall 不需要 | 保持独立包，不传递给普通桌面消费者 |
| PackageSmoke 缓存 | staging 曾累计约 936 MiB | 发布结束后按版本保留必要证据，其余缓存可再生成且不得入库 |

### 5.2 冻结条件

AppShell 只有满足以下条件才能冻结：

1. OHS 与 WBall 都从同一正式 AppShell 2.7.5 包/源码基线构建；
2. 两个消费者显式声明 MCP、模块、ServiceHost 和数据能力开关；
3. 默认包图不再包含 SQLite 和原生 RID 资产；
4. WBall 启动不创建 `main.db`，不注册 `db.*`，不显示空表窗口；
5. OHS 文件状态通过迁移、崩溃恢复和治理状态机 Smoke；
6. AppShell 演示宿主、OHS、WBall 均完成 Debug/Release 构建与 GUI 冒烟；
7. 包内容、依赖图、发布体积和消费者命令目录形成可复验证据；
8. `meta` 已抽干长期合同，命令手册由最终运行时重新生成。

冻结后，AppShell 只接受安全修复、明确的兼容性修复和经三方消费者矩阵验证的必要变更。新业务能力优先进入
消费者或模块，不继续扩张框架公共面。

## 6. SQLite 退出迁移

### 6.1 迁移原则

迁移必须是“先导出并验证，再切换读取”，不得启动新版本后直接忽略旧库。

标准顺序：

1. 只读打开旧 `main.db`；
2. 为每张受支持表导出规范 JSON/JSONL；
3. 记录源库 SHA-256、表名、行数和导出文件 SHA-256；
4. 重新读取新文件并做字段级校验；
5. 写入 `state/migration-sqlite-v1.json` 完成标记；
6. 新运行时改读文件状态；
7. 将原库复制为带时间或固定迁移标识的保留备份；
8. 不删除、不截断、不改写原 `main.db`。

迁移过程任一步失败：不写完成标记、不切换真值、保留诊断日志，下次启动可安全重试。

### 6.2 OHS 校验最低要求

- `mcp_history` 与 `push_history`：源行数等于 JSONL 有效行数；逐行关键字段非空；
- `branch_notes`：分支名唯一，说明与更新时间一致；
- `tool_registry`：名称唯一，SHA-256 格式正确，槽存在状态重新计算；
- 提示词治理：每个命令最多一个 `Applied=true` 修订；提案状态属于允许枚举；
- 已应用提案必须指向存在的修订；回滚目标必须存在；
- 导出内容使用 UTF-8 无 BOM，中文不得出现替换字符或疑似乱码串；
- 新文件损坏时优先读取上一次 `.bak`，不得回落后静默覆盖好备份。

### 6.3 WBall 校验最低要求

WBall 的 SQLite 是镜像，不迁移表行到新业务真值。切换前只需证明：

- 当前场景可由 `scenes/*.json` 完整加载；
- 球自定义属性已包含在场景 JSON，空场景所需属性名进入轻量 schema；
- 场景扫描、改名、删除、保存和重新加载一致；
- 旧数据库被保留但不再更新；
- 关闭程序后重启，运行状态不依赖数据库恢复。

## 7. AI 开发强制流程

AI 开始任何功能前，必须先回答以下问题并写入本次计划：

1. 这项事实的唯一权威源在哪里？
2. 哪些下游位置应自动形成？
3. 当前是否已有相同字段、名单、版本或路径的第二份硬编码？
4. 变更影响 AppShell、OHS、WBall 中的哪几个消费者？
5. 哪个自动化门禁能阻止只改一半？

实施顺序固定为：

```text
查权威源 → 查所有消费者 → 改权威源 → 接通投影/生成器
→ 加漂移测试 → 构建消费者矩阵 → 更新 meta → 生成命令手册 → 发布预检
```

代码审查出现以下任一项即退回：

- 新增命令后又手工编辑命令手册；
- 同一参数在桌面与 Service 复制声明；
- 使用裸字符串代替已有标准 ID/版本/域名常量；
- 为修复一个消费者而把其业务判断写进 AppShell；
- 通过复制源码或 DLL 解决包版本问题；
- 能力关闭后仍产生文件、线程、端口、监听器或原生依赖；
- 迁移没有源行数、哈希、备份和失败重试证据；
- 只构建 OHS，不构建 AppShell 演示宿主和 WBall；
- 用 V 历史文档覆盖当前源码或 `meta` 事实。

## 8. 文件归属与并行开发

AppShell、OHS 和 WBall 联合开发期间按以下所有权拆批，避免多个 AI 同时改组合根：

| 批次 | 允许修改 | 禁止夹带 |
|---|---|---|
| A：框架解耦 | AppShell 项目引用、MCP/模块/数据可选装配 | OHS/WBall 业务 |
| B：OHS 文件状态 | History、Tool registry、Prompt governance、迁移器 | AppShell 停靠/UI 重构 |
| C：WBall 去投影 | WBall 装配、领域状态、窗口表 | OHS 服务组合根 |
| D：生成与门禁 | 构建、Smoke、发布脚本、包内容验证 | 新产品功能 |
| E：文档抽干 | `meta` 与本施工记录 | 运行时代码 |

同一时间只能有一个任务修改各消费者的组合根。若工作树已有未提交重叠修改，后来的任务只能新增独立文件或停止并
报告合并点；不得格式化整文件、还原他人改动或用覆盖写入解决冲突。

## 9. 实施批次与验收

### P0：冻结现状

- 记录 AppShell/OHS/WBall 当前版本、依赖图、命令数、发布体积和数据库统计；
- 为两个现有 `main.db` 计算 SHA-256，只读保留；
- 暂停对 AppShell 公共 API 的非必要扩张。

### P1：解除 AppShell 强制数据库依赖

- MCP 提示词治理与审计改为文件状态，不再要求 `DataService`；
- SQLite 实现与表窗口若保留，拆到独立可选组件；
- Core 不删除 `IDataService` 契约，避免无关第三方实现源码断裂，但默认 Shell 不装配它；
- 包依赖图验证无 `Microsoft.Data.Sqlite`、`SQLitePCLRaw` 和原生 SQLite 资产。

### P2：WBall 去库

- 移除数据库镜像和数据门面；
- 移除表窗口与 `db.*`；
- 显式关闭 MCP/模块；
- 以领域命令和场景 JSON 完成回归；
- 对比去库前后启动行为、命令目录、内存和发布体积。

### P3：OHS 去库与迁移

- 先交付独立、可重复、只读的 SQLite 导出器；
- 校验并切换五类文件状态；
- 移除 OHS `db.*` 与表窗口；
- 保持 MCP、项目留痕、分支说明、工具溯源和提示词治理用户行为；
- 完成损坏文件、写入中断、重复迁移和旧库保留回归。

### P4：冻结与发布

- Debug/Release 构建 AppShell、OHS、WBall；
- 运行各自 Smoke 和 GUI 冒烟；
- 从最终运行时重新生成命令手册；
- 更新 `meta/使用说明.md`、`项目库与备份.md`、`模块开发手册.md`、`MCP接入与安全.md`、
  `发布与升级.md`；
- 生成依赖清单、文件清单、SHA-256 和体积对比；
- 只有全部通过后把本文状态改为“已交付”。

## 10. 风险提示

### 高风险

1. **旧 OHS 数据丢失**：没有导出校验便删除 SQLite 依赖，会让已有审计和治理状态不可见。
2. **提示词状态机退化**：文件化若拆成多文件写入，批准与应用可能形成半事务。
3. **并行任务覆盖**：当前 AppShell/OHS 有其他任务修改组合根和公共文件，必须分批合并。
4. **伞外消费者仍携带旧包**：只改 020 源码不会改变 WBall 使用的已发布 AppShell 包。

### 中风险

1. 移除 `db.*` 会改变命令目录、Help、MCP schema 和既有脚本；必须作为明确破坏性变更处理。
2. 旧布局仍可能引用 `table` 窗口，需要幂等布局清理或忽略未知窗口。
3. JSONL 长期只追加，需要后续轮转与导出策略，但当前数据量无需提前引入复杂日志数据库。
4. 原子替换依赖同卷临时文件；临时文件必须与目标文件位于同一目录。
5. 文件状态默认只支持单服务进程写入；若未来多进程并写，必须重新评估锁与存储方案。

### 低风险但必须清理

1. `packages.lock.json`、`.deps.json` 和 staging 可能继续残留 SQLite 字样；应由锁定还原和全新发布消除。
2. 文档中的 `main.db`、`SQLite`、`db.*` 描述在交付前必须按最终运行时更新。
3. WBall 版本号、AppShell 包版本和 OHS/AppShell 同列车规则不能混为同一概念。

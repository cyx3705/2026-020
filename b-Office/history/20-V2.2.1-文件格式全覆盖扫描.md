## 0. 一句话定义

把 Git 文件规则从「用户已声明的少数格式」升级为「**全库格式台账 + 覆盖率**」：
一次扫描列清项目库里存在的每一种文件格式与未决目录，标出哪些已纳管、哪些待决策，
并支持按建议批量补全规则——目标是覆盖率可量化地推向 100%。

## 1. 现状与差距（实测体检 2026-07-22）

### 1.1 现状

V2.1.3/V2.1.4 的 `git.rule.*` 与「项目操作」页已具备：三状态规则（纳入 Git / LFS / LF）、
托管块（`# OneHistoryStudio managed begin/end`）写入 `.gitignore` 与 `.gitattributes`、
预览-应用两段式、索引增删与 renormalize。

**但规则表的数据源是「已写进两个规则文件的 pattern」**——即 `ListAsync` 只回显用户
声明过的格式。项目里真实存在、却从未被声明的格式，在界面上根本不出现，
于是「没被规则覆盖的文件」永远看不见（用户此次指出的正是这个缺口）。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 格式 | 文件扩展名归一化形式，规则形态 `*.ext`（含复合如 `*.tar.gz`） |
| 台账 / inventory | 一次扫描产出的「库内全部格式 + 目录候选 + 统计 + 覆盖状态」结构化结果 |
| 覆盖状态 | 某格式在某项目内的归宿：已跟踪管 / 已忽略管 / **未决** / 目录规则覆盖 |
| 未决（undecided） | 文件既未被 `.gitignore` 命中，其格式也无任何规则声明——本版要消灭的对象 |
| 基线 | **模板项目 `0000-000-Template` 根 `.gitignore` / `.gitattributes` 本体**（不另设存储，见 §3.4） |
| 目录规则 | 限定形态的路径规则（`目录/`、`目录/**`），用于闭合无扩展名与杂项文件 |

## 3. 覆盖模型（核心设计）

### 3.1 每个文件恰好落入一个归宿

```text
文件
 ├─ 被 .gitignore 命中 ────────────→ 【忽略管】(ignored)
 ├─ 在 Git 索引内
 │    ├─ 有 LFS 属性 ──────────────→ 【跟踪管·LFS】
 │    ├─ 有 LF 属性 ───────────────→ 【跟踪管·LF】
 │    └─ 无格式属性 ───────────────→ 【跟踪·默认】(可接受，但需显式确认)
 └─ 既未跟踪也未忽略 ──────────────→ 【未决】★ 本版消灭对象
```

### 3.2 覆盖率定义（可量化、可验收）

对每个项目与全库各算一份：

```text
覆盖率 = (已明确归宿的文件数) / (总文件数)
未决文件数 = 未跟踪未忽略文件 + 已跟踪但其格式无任何规则声明的文件
```

**验收即以覆盖率为准**：扫描 → 应用建议 → 复扫，覆盖率应显著上升且未决数下降到人可清点。
不追求首版即 100%（有些格式确实需要人逐个想清楚），追求**未决项永远可见、可清零**。

### 3.3 规则形态扩展（最小必要）

| 形态 | 例 | 用途 | 本版 |
|---|---|---|---|
| 格式规则（现有） | `*.par` | 按扩展名 | 沿用 |
| **目录规则（新增）** | `Library/`、`Temp/**` | 闭合无扩展名/杂项 | P0 |

目录规则的守卫（延续 M1.5 路径纪律，只放宽到必要形态）：
- 只允许相对形态：`名/`、`名/**`、`父/子/`；**禁**绝对路径、盘符、`..`、空白；
- 长度 ≤ 128；仍写入托管块，注释块外的用户手写内容不动；
- 目录规则**只写 `.gitignore`**（不生成 `.gitattributes` 行）——目录级 LFS/LF 无意义。
- **不新增指令**：`git.rule.set` 依模式形态自动判别（以 `/` 结尾 = 目录规则），
  避免为同一件事开两套入口。

### 3.4 基线与项目特例的两层归属（关闭 Q221-2）

**判定：基线不另设存储位置——模板项目自己的根规则文件就是基线本体。**

理由是实测事实：33 个项目的 `.gitattributes` 完全一致，这不是巧合，正是
`proj.create` 从模板拉分支时 **git 继承**干的活。分发机制一直在正常工作，
本项目此前只是从未刻意管理它。因此：

```text
0000-000-Template 根 .gitignore / .gitattributes   = 基线本体（用 git.rule.set 正常编辑）
派生项目根规则文件
   ├─ baseline 托管块   ← 由 git.rule.sync 自模板整块重刷（机器所有）
   ├─ managed 托管块    ← 本项目特例（如 2025-013 的 office 规则）
   └─ 托管块外内容      ← 用户手写，零改动（既有语义不变）
```

- **新项目**：走 git 继承自动获得基线，工具零介入。
- **老项目**（已分叉，无法靠 merge）：`git.rule.sync` 推送基线块，不触碰项目块。
- **解析器**：复用 `ReadDeclaredRulesAsync`，**不引入新文件格式**。
- **版本历史**：基线本就在模板分支内，随仓库推送到 GitHub，白得一份变更史。

**为什么不在模板放 z 级文件夹存基线**（用户 2026-07-22 提出的关键约束）：
模板工作树的一切内容都会被后续新项目继承，放 `z-GitRules/` 会让每个新项目
白得一个规则文件夹——正是要避免的 z 级污染。

**为什么不取消 z 级继承关系**（备选路线，否决）：需要 `proj.create` 在建分支后补一次
删除提交（脏历史）或全局 ignore；且会堵死「模板给新项目预置有用 z 级脚手架」的可能，
伤及 V2.0.1 Meta 约定。选定路线后此问题根本不存在，无需付这笔代价。

> **附带收益**：既然模板根规则文件即基线，修模板 = 一次性堵住未来所有新项目。
> 实测模板现状：无根 `.gitignore`（故 35 个项目全无）、`.gitattributes` 含 5 行
> 由中文注释被 `git lfs track` 拆碎而成的垃圾模式（`Premiere`、`工程文件`、
> `常见视频格式`、`Pro`、`\#`），且已随继承复制到 33 个项目。M2/M3 一并清理。

## 4. 扫描设计（效率是一等约束）

### 4.1 实测成本（决定一切设计取舍）

| 操作 | 实测 |
|---|---|
| `git ls-files -z`（全库 35 项目跟踪清单） | **1s** |
| 追加 `--others` / `--others --ignored`（全库三态） | 累计 **~4s** |
| `git check-attr -z --stdin`（单项目 15,897 文件） | **143ms** |
| `git ls-files -s` + `cat-file --batch-check`（200 blob） | **130ms** |
| 文件系统全量 stat（单项目 15,892 文件） | **<1s** |
| **`git lfs ls-files --json`（单项目）** | **725ms ← 唯一昂贵项** |

**推论**：git 自身的枚举与属性查询都很便宜；唯一需要设防的是 LFS 指针枚举
（×35 项目 ≈ 25s 串行）。因此把它降级为**按需项**，而不是每次扫描都付的固定成本。

### 4.2 扫描深度：两档（原三档为过度设计，2026-07-22 精简）

| 档位 | 内容 | 实测（全库 35 项目） |
|---|---|---|
| 默认 | 三态枚举 + 规则解析 + **逐文件体积统计** | **1.67s** |
| `deep=true` | 默认 + `git lfs ls-files` 指针核验 | **2.94s** |

原设计的 `quick`（不含体积）实测仅比默认快 580ms，却让 LFS 建议失去依据——
一个省不下多少、又削弱决策质量的档位没有存在价值，**已删除**。
参数由 `depth=quick|normal|deep` 简化为布尔 `deep`。

### 4.3 三条效率铁律

1. **按格式聚合，不按文件展开**：39,311 文件 → 278 格式，聚合比 **141:1**。
   `check-attr` 只对「每格式的代表路径（取 1–3 个样本）」调用，把 O(文件) 降为 O(格式)。
   逐文件明细仅在用户点开某一格式时**按需**加载。
2. **项目级并行 + 有界**：35 个项目的 git 调用互相独立，并行度
   `min(ProcessorCount, 8)`；单项目内的多条 git 命令沿用现有 `Task.WhenAll` 并发。
3. **缓存 + 增量失效**：台账落 `data/format-inventory.json`（沿 V2-M2 `branch-tree.json` 先例）。
   每项目失效键 = `HEAD sha` + `索引 mtime` + `.gitignore/.gitattributes 内容哈希`；
   **只重扫失效项目**，其余读缓存。`refresh=true` 强制全量重扫。

### 4.4 输出结构（台账行）

```text
格式台账行：格式 / 总文件数 / 涉及项目数 / 跟踪·忽略·未决计数 /
            最大文件 / 合计体积（normal 档）/ 当前规则(track,lfs,lf) / 覆盖状态 / 建议
目录候选行：目录（相对路径）/ 文件数 / 是否已被忽略 / 建议
```

两者都随 `CommandResult.Data` 结构化输出（MCP 可读，Codex 能直接分析全库格式分布）。

## 5. 建议引擎（人在环上，绝不静默改写）

对 278 个格式逐个人工决策不现实，故给**建议**而非**自动应用**：

| 类别 | 判据 | 建议 |
|---|---|---|
| 派生/临时 | 内置清单（`.lck .cache .tmp .obj .pdb .eox .eod` 等）或位于派生目录 | **忽略** |
| 大二进制 | 已知二进制格式 且 最大文件 ≥ `proj.rejectmb`（现 100MB）或均值超阈 | 跟踪 + **LFS** |
| 中小二进制 | 已知二进制格式且体积不大 | 跟踪（不加属性） |
| 文本源码 | 已知文本格式（`.cs .md .json .xml .txt .yml` 等） | 跟踪 + **LF** |
| 未知格式 | 不在任何清单 | **不建议**，保持未决待人工判定（宁可留空，不猜） |

- 建议只进台账的「建议」列；**应用必须显式**（`apply=true` 或页面点按钮），沿用现有
  预览-应用两段式与托管块写入。
- 分类清单为代码内常量。（原设计的 `rule.textexts` / `rule.binexts` / `rule.junkexts`
  三个可配置键属**投机性过度设计**——尚无任何证据表明用户需要改这些清单，
  2026-07-22 删除；真出现需求再加，那时也已知道该加什么。）

## 6. 指令与页面

### 6.1 指令（`git.rule.*` 域扩展）

| 指令 | 说明 | 暴露档 |
|---|---|---|
| `git.rule.scan [name=] [deep=] [refresh=]` | 扫描并输出格式台账 + 覆盖率；省略 name = 全库 | readonly |
| `git.rule.gaps [name=]` | 只列未决项（格式 + 目录候选），按影响文件数降序 | readonly |
| `git.rule.suggest [name=] [apply=]` | 输出建议规则集；`apply=true` 走预览-应用写入托管块 | standard（apply 需确认） |
| `git.rule.sync [name=] [apply=]` | 把模板基线推送进项目的 baseline 块（§3.4）；省略 name = 全库 | standard（apply 需确认） |

既有 `git.rule.list/set/remove` 语义不变（向后兼容，快照对账口径）；
`git.rule.set` 的 pattern 扩容为「格式 或 目录」两种形态，**不新增 `git.rule.dir` 指令**。

### 6.2 页面（「项目操作」页）

- 规则表新增列：**覆盖状态**、**文件数**、**建议**；顶部显示该项目「覆盖率 x%，未决 n 个」。
- 新增筛选：`全部 / 已纳管 / 未决`——默认落在「未决」，让缺口一眼可见。
- 行内「采纳建议」按钮 = 组装 `git.rule.set` 指令经总线（架构不变量 1）。
- **顺带补做 A220-8**（V2.2.0 顺延项）：「模块管理」页的 `tool.scan/sync/remove` 行内按钮。

## 8. 非目标（本版明确不做）

- **不自动改写任何项目的规则文件**——一切写入需显式 apply + 确认。
- 不做历史重写（已提交的 4,314 个 Unity 缓存文件，本版只负责「今后忽略」与
  `git rm --cached` 出索引；`filter-repo` 式历史清理列 V2.3 候选，风险与备份要求另议）。
- 不做按文件（而非按格式/目录）的逐个规则——粒度过细无收益。
- 不改 GitRunner 结构化参数、路径守卫、托管块写入语义（M1.5 与 V2.1.3 纪律延续）。
- 不动框架三目录（延续 0.4.3 未分叉）。

### 3.5 无扩展名文件的两段处置（Q221-3 判定落地）

```text
无扩展名文件（实测 4,384 个）
 ├─ 大集中目录（≥ 阈值，如 Unity Library 4,314 个）→ 单独目录规则，一条吃掉
 └─ 散尾（~70 个 / 22 个目录前缀）           → 归入 other 类别整体决策
```

- 阈值默认 50 个文件：超过即在缺口清单里单列为「目录候选」，供立目录规则；
- 未达阈值的一律归 `other`，台账中作为**一行**呈现（而非 22 行噪音），
  一次决策覆盖全部散尾；
- 这样既不放过 98% 的大头，也不让长尾把缺口清单淹掉。

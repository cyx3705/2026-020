## 3. 核心架构决策（用户对 GPT 方案的四点修正）

### 3.1 z-APPShell 降格为 b-Code-AppShell

AppShell 不再是「模板」，而是 020 伞下的**一个平级组件**（`b-` 前缀），与 OHS 本体、V1 前身同级。
它有自己的 `AppShell.sln`、自带演示宿主 `src/App`（用于独立验证框架），可脱离 OHS 单独构建。

> 迁移前的 `z-APPShell/WpfApp1` 是更早的脚手架；已确认无引用并按 D2 清理。

### 3.2 OHS 与 AppShell 同源（**本方案的核心，一次范式转变**）

**旧模式（至 0.4.4 为止）**：模板正本 + OHS 副本，靠「整体替换 + 逐文件哈希 0 差异 + 反哺回灌」同步。

**新模式（V2.4.0 起）**：`b-Code-AppShell/src/AppShell.*` 是**唯一正本**，OHS 直接 `ProjectReference`：

```xml
<!-- b-Code-OneHistoryStudio/src/App/App.csproj -->
<ProjectReference Include="..\..\..\b-Code-AppShell\src\AppShell.Core\AppShell.Core.csproj" />
<ProjectReference Include="..\..\..\b-Code-AppShell\src\AppShell.Services\AppShell.Services.csproj" />
<ProjectReference Include="..\..\..\b-Code-AppShell\src\AppShell.Shell\AppShell.Shell.csproj" />
```

**这一步消除了整套旧纪律**：13 处副本、逐文件哈希对账、`TEMPLATE_VERSION` 的「跟随基线/未分叉/0 差异」语义、
「反哺 = 整体替换 + 回灌」的流程——全部作废，因为**不再有两份**。

**但要用新纪律补位**（关键，否则会失去旧模式的质量保护）：

| 旧模式靠什么保证 | 新模式如何替代 |
|---|---|
| 哈希 0 差异证明「没偷改框架」 | 改 `b-Code-AppShell` = 改框架本身，须过 **AppShell 自带演示宿主 + 框架层测试**才算数 |
| 「先上报再改框架」的演进手册纪律 | 保留：框架层改动仍走评审；但落点是唯一正本，不再有回灌动作 |
| 派生副本与模板对账 | 改为 **OHS 冒烟 + GUI 实跑**兜底：框架改坏了，OHS 一构建/一跑就暴露 |

> **本次会话的三个教训直接支撑此纪律**：0.4.4 反哺中，`command.list` 双注册、
> `CommandSelection` 空引用、窗口工厂在构造期调用——**三个都只有 GUI 实跑抓到，冒烟全绿**。
> 同源模式下框架改动影响面更直接，**GUI 实跑必须是框架层改动的强制验收环节**，写进新纪律。

### 3.3 z 级身份改为发布包 z-Package-AppShell

020 内部 OHS 用**源码引用**（§3.2），不经 nupkg。`z-Package-AppShell` 承担的是**对外/未来的二进制发布**：
`.nupkg` feed、清单、校验和、changelog。它是「发布产物存放地」，不是 020 构建的必需路径。

> 已按 D3 建立发布治理空壳；RID 裁剪后单份框架输出约 3.3M，首次正式打包流程后续补充。

### 3.4 文档上抛到 b-Office/OHS

OHS 的 `meta/versions/snapshots` 归入 020 根级治理区 `b-Office/OHS`：这些需求、版本、部署、
验收和基线属于整个产品，不属于某一个代码目录。组件目录只留与自身直接相关的 README：

- `b-Code-OneHistoryStudio/README.md`：仅自身构建与源码结构；
- `b-Code-AppShell/README.md`：框架 API 与二次开发说明；
- 跨组件的规则、版本演进、验收证据 → `b-Office/OHS/{meta,versions,snapshots}`。

## 4. 技术要害（实现者补充的坑，GPT 施工时逐条核对）

1. **跨 `b-` 目录的 ProjectReference 路径**：从 `b-Code-OneHistoryStudio/src/App/` 到
   `b-Code-AppShell/src/AppShell.Core/` 是 `..\..\..\b-Code-AppShell\src\AppShell.Core\...`（三级上行）。
   `tests/Smoke` 仍只引 `App.csproj`，不直接引框架，无需改。

2. **根级 `OHS.sln` 必须同时含两组项目**：`b-Code-AppShell` 的三个框架项目 + 演示 App，
   与 `b-Code-OneHistoryStudio` 的 App + Smoke。`AppShell.sln` 保留在 `b-Code-AppShell` 供框架独立构建。

3. **命令手册的发布路径会二次失效**：`App.csproj` 用 `Content Include="..\..\meta\命令手册.md" Link="docs\命令手册.md"`
   打包 6 份手册进 `Publish\docs\`。meta 上抛到根级后，`Include` 路径变
   `..\..\..\meta\命令手册.md`；**`Link="docs\..."` 保持不变**（那是面向使用者的产品界面布局，
   不随源码目录动）。本次会话刚处理过一次 `docs→meta` 的同类迁移，务必核对 Publish 布局不变。

4. **`Directory.Build.props` 的层级**：现在 `b-Code-OneHistoryStudio/` 和 `z-APPShell/` 各有一份
   （均含 0.4.4 的 RID 裁剪 `win-x64` + `AppendRuntimeIdentifierToOutputPath=false`）。伞形后建议
   **根级一份**管公共项（RID、Nullable、ImplicitUsings、TreatWarningsAsErrors），组件级只留特有项。
   注意 `AppShell.Core/Services` 是 `net8.0`（非 windows），RID 对它们的输出路径影响已由
   `AppendRuntimeIdentifierToOutputPath=false` 抵消，根级 props 要延续这一点。

5. **框架三目录的哈希对账脚本作废**：本次会话大量使用「z-APPShell 与 OHS 副本逐文件 md5 比对」
   验证 0 差异。同源后**没有副本可比**，这类脚本全部删除，验收改用 §3.2 新纪律。

6. **`TEMPLATE_VERSION.md` 转型**：不再表达「OHS 跟随 AppShell 某基线/未分叉」。
   改为 `b-Code-AppShell` 自己的版本记录（0.1→0.4.4 的里程碑史 + 今后版本），
   放 `b-Code-AppShell/` 或根级 `meta/`。「派生/跟随/回灌」措辞全部退场。

7. **AppShell 自带演示宿主是新纪律的支点**：`b-Code-AppShell/src/App` 必须能**独立构建运行**
   （本次会话验证过：模板独立构建 0 警告、输出 3.27M）。它是「框架改动是否自洽」的第一道闸，
   OHS 冒烟 + GUI 实跑是第二道。两道都要保留。

8. **编号字典序约束只作用于 worktree**：OHS 继承树算法要求子项目名字典序 > 父（020 > 018 满足）。
   但 `b-Code-AppShell` 是 020 内部的**组件目录**，不是独立 worktree，**不受此约束**。

## 5. 施工顺序（供 GPT 执行，每步可独立验证）

> 原则：先立结构、再迁源码、后接引用、最后删冗余；每步构建 + 冒烟通过才进下一步。

1. **根级骨架**：建 `meta/ versions/ snapshots/`，把 `b-Code-OneHistoryStudio/{meta,versions,snapshots}`
   上抛到根级；组件内只留 README。修所有跨文档链接（本次会话有先例：README 与《发布与升级》的编号文档链接）。
2. **AppShell 降格**：`z-APPShell` → `b-Code-AppShell`；`src/App`(演示) + 三目录 + `AppShell.sln` +
   `Directory.Build.props` + `docs`(转 `b-Code-AppShell/README` 或根级 meta) 一并迁入。
3. **切同源**：删 `b-Code-OneHistoryStudio/src/AppShell.{Core,Services,Shell}` 三个副本目录；
   改 `App.csproj` 的 3 条 ProjectReference 指向 `b-Code-AppShell`（§4.1）。
4. **根级构建入口**：建 `OHS.sln`（§4.2），能一次构建 AppShell 演示 + OHS + Smoke。
5. **验收**：主解决方案 Debug/Release 0 警告；六套冒烟 12/12；**GUI 实跑三窗口可见、无崩溃**
   （§3.2 强制项）；命令手册 Publish 布局不变（§4.3）。
6. **发布包壳**：按需建 `z-Package-AppShell/{feed,manifest,checksums,changelog}`（§3.3、§6）。
7. **删冗余**：删 `b-Code-MyAPI-Core`、`b-Code-MyAPI-Lite`（与 OHS 无关）；`b-Code-OneHistory-V1`
   与 `WpfApp1` 去留见 §6。删框架哈希对账脚本（§4.5）。
8. **收口文档**：本文件归档进 `versions/`，写 V2.4.0 交付记录；`TEMPLATE_VERSION` 转型（§4.6）。

## 7. 版本与项目编号分离

- **020 长期承载整个 V2.x**（2.4、2.5、2.6…），**不为小版本新建项目**；
- 小版本通过 Git 提交、标签、`versions/` 文档管理；
- **只有架构代际变化才拉新项目**：例如 V3.0 从稳定的 020 拉出 `2026-027-OHS-V3`：

```
2026-018-MyAPI
└─ 2026-020-OneHistoryStudio   （V2 产品线，长期维护）
   └─ 2026-027-OHS-V3          （V3 产品线，未来；本方案不涉及，仅记血缘）
```

继承树因此表达的是**产品代际与架构血缘**，不是「每次发布」。027 未来继承的将是**整理后的伞形结构**
（元文档、AppShell 组件、测试规范、历史基线），而非本次的混合态。**V3 具体做法本方案不展开**。

## 8. 风险与边界

1. **Git 祖先不干净，接受不重写**：020 祖先含 MyAPI/OHS 混合历史。重写历史对「裸仓库 + 多 worktree」
   树状项目库是破坏性操作（大量 SHA 变动、worktree 重挂、强推、旧克隆回灌），代价大于约 159M 历史负担。
   **从 020 起边界干净即可**，存量不动。（与 V2.3.3 DQ233-3 判断一致。）
2. **同源去掉了副本保护**：框架改动直接影响 OHS，无「先在副本试」的缓冲。用 §3.2 新纪律
   （演示宿主 + 冒烟 + **强制 GUI 实跑**）补位。
3. **跨目录引用的路径脆弱性**：`..\..\..\` 相对引用一旦目录改名即断。改名 `b-Code-AppShell` 后须全仓搜索
   旧路径引用（本次会话有先例：`docs→meta` 迁移后全仓搜残留引用）。
4. **不在 018 施工**：所有重构在 020 进行。018 保持现状（其 `z-APPShell` 若还要作为其他派生的模板，
   与 020 的 `b-Code-AppShell` 就此分道——这是可接受的分叉，因为 020 已是独立产品线）。

### M0 · 基线固定与目标骨架｜准备

- **干什么**：固定现状证据，建目标目录骨架（空壳），不迁任何内容。
- **产出**：采一份 020 现状清单（目录树 + 各 `b-`/`z-` 体积 + 当前 `git log` 继承点）；
  在 020 根级建空目录 `b-Office/`、`b-Code-AppShell/`、`z-Package-AppShell/`（占位，内容后续里程碑填入）。
- **出口**：骨架就位；现状清单存档；未动任何现有文件，`dotnet build` 仍与迁移前一致。

### M1 · 文档归位到 b 级（**覆盖 §2/§3.4 的根级三分**）

- **干什么**：按 **D5** —— 不做根级 `meta/versions/snapshots` 三分（过散）。文档不多，先集中：
  - OHS 的全部文档（现 `b-Code-OneHistoryStudio/{versions,meta,snapshots}` 的内容）**统一塞入 `b-Office/`**，
    先不细拆，保持可查即可；

- **产出**：`b-Office/` 含 OHS 全部版本工程文档、手册、快照基线；AppShell 文档独立可查。
- **出口**：`b-Code-OneHistoryStudio` 内只剩自身构建 README；全仓搜不到指向旧 `docs/`、
  `versions/`、`meta/`、`snapshots/` 的**断链**（本次会话有 `docs→meta` 迁移改链先例）；
  **命令手册 `App.csproj` 的 `Content Include` 路径随之更新，`Link="docs\..."` 保持不变**（§4.3）。

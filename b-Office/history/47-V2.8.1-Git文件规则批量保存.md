# V2.8.1 Git 文件规则批量保存

> 日期：2026-07-31
> 状态：实施完成，定向验证通过；待人工界面手势验收

## 目标

V2.8.1 修复“文件规则”表格一次只能保存当前所选行的问题。用户可以连续修改多行 Git、LFS 指针和 LF
状态，再通过一次保存、一次确认完成全部有效修改；保存过程中不得静默覆盖其他尚未保存的编辑。

本版本只收口 Git 文件规则编辑与批量写入，不修改 AppShell、Git 规则格式、仓库历史或发布部署流程。

## 当前问题

当前界面的按钮名称为“保存所选”，`OnSaveRuleClick` 只读取 `RuleGrid.SelectedItem`，并只对该行依次调用
`git.rule.set apply=false` 和 `git.rule.set apply=true`。应用成功后，界面立即执行 `LoadRulesAsync(...,
refresh: true)` 重载整张表。

因此，用户修改多行后点击保存时只有当前所选行会写入，其余行尚未保存的内存编辑会被重新扫描结果覆盖。
`RuleEditRow` 当前也没有加载快照、`IsDirty` 或脏行集合，界面无法识别和保护多行修改。这是产品 Bug，
不是用户操作错误。

## 决策

- OHS 提升到 2.8.1；四个 `OneHistory.AppShell.*` 包继续固定为 3.0.3；
- AppShell 023 保持冻结，本次修改全部位于 OHS 的 Git 规则服务、命令、界面和测试；
- 文件规则页由“保存所选”改为“保存修改（N）”，`N` 是当前有效脏行数；没有修改时按钮禁用；
- 每行保存加载完成时的 `Track`、`Lfs`、`Lf` 原始快照，属性变化后实时计算 `IsDirty`；恢复原值时
  自动退出脏状态；
- 保存动作必须先提交 DataGrid 当前单元和当前行编辑，确保用户最后一次点击已经进入绑定源；
- 一次保存收集项目内全部有效脏行，不依赖当前选择，不使用 DataGrid 多选表达保存范围；
- 所有修改先作为一个批次统一校验和预览；任一项预览失败时，整批不得开始写入；
- 用户对整批只确认一次，确认内容显示规则数、加入索引数、移出索引数和属性重写数；
- 应用完成后只重新扫描并加载一次，不允许逐行刷新覆盖尚未处理的行；
- 单行修改是批量保存的一行特例，不保留另一套 UI 保存路径；
- 现有 `git.rule.set` 公开语义保持兼容，新增 `git.rule.batch-set` 作为 UI、MCP 和控制台共用的批量入口；
- 批量命令不会提交、推送、删除本地文件或重写 Git 历史。

## 批量命令合同

新增命令：

```text
git.rule.batch-set name=<项目名> changes=<JSON数组> apply=false
```

`changes` 是 UTF-8 JSON 数组的命令参数，由调用方按现有命令参数引用规则整体转义。每项固定包含：

```json
{"pattern":"*.xlsx","track":true,"lfs":true,"lf":false}
```

批量合同规定：

- `name` 必须对应一个已登记项目，单批只允许修改一个项目；
- `changes` 必须包含 1 至 500 项，`pattern` 在忽略大小写后不得重复；
- 每项必须同时提供 `pattern`、`track`、`lfs` 和 `lf`，不接受部分更新；
- `track=false` 时 `lfs` 与 `lf` 必须为 false；`lfs=true` 与 `lf=true` 互斥；
- 服务按 `pattern` 的稳定顺序规划结果，跳过与当前声明及索引状态均无变化的项目；
- `apply=false` 只返回整批预览，不写 `.gitignore`、`.gitattributes` 或索引；
- `apply=true` 使用同一套校验和规划逻辑，经命令总线一次确认后执行；
- 预览结果返回每项状态以及整批的新增规则、重写规则、加入索引、移出索引和无变化计数；
- 输入、项目状态或 Git 前置检查有任一错误时，应用开始前整批失败；
- 写入开始后的运行时失败必须返回成功项、失败项和未执行项，保留失败与未执行行的脏状态，不得报告整批成功。

`git.rule.set` 继续服务既有脚本和单条调用，不改参数、确认语义或返回类型。批量入口增加对应的数据反序列化类型，
命令手册由 Help 元数据自动生成，不维护第二份手工命令文本。

## 服务与一致性

`GitFileRuleService` 增加类型化的批量预览与应用方法，由单条和批量命令共享规则校验、托管块规划和 Git 索引
同步能力。批量实现不得由 UI 循环调用单条命令，也不得每行独立确认。

批次执行分为三个阶段：

1. 读取一次项目事实，校验全部输入并生成完整计划；
2. 写入托管的 `.gitignore` 和 `.gitattributes` 目标内容，再按计划同步 Git 索引；
3. 汇总每项结果并返回，界面仅在整批处理结束后刷新一次。

规则文件写入继续使用现有机器所有块和原子替换机制。若规则文件写入失败，不得开始索引同步。若索引同步在运行
中失败，服务必须保留可诊断的部分结果，界面不得清除失败和未执行行；本版本不承诺跨 Git 命令的事务回滚，
但再次保存必须能够从当前仓库事实安全重算并收敛。

## 界面行为

- `RuleEditRow` 保存原始值，并公开 `IsDirty`；草稿行从创建时即为脏行；
- Git、LFS、LF 的现有联动和互斥约束保持不变，联动造成的值变化也参与脏状态计算；
- 保存前先执行 `CommitEdit` 提交当前单元和当前行，再重新计算待保存集合；
- “保存修改（N）”对全部有效脏行工作，当前选择只用于删除和表格定位；
- 存在无法确定三项布尔值的脏行时，保存不执行，并在表格中标出需要处理的行；
- 预览没有实际变化的行标记为已与仓库一致，更新其快照，不重复写入；
- 全部成功后只调用一次 `LoadRulesAsync(project, refresh: true)`；
- 部分失败时显示成功、失败和未执行数量，成功行更新快照，失败及未执行行继续保持可编辑和脏状态；
- 保存进行中禁用保存、删除、重新读取、扫描和项目切换入口，防止并发操作；
- 状态栏使用“已保存 N 条规则”“保存失败：成功 N、失败 N、未执行 N”等明确结果，不以当前选中行代替批次结果。

## 未保存修改保护

以下操作在存在脏行时必须统一进入“保存修改 / 放弃修改 / 取消操作”流程：

- 切换项目；
- 重新读取规则；
- 执行全覆盖扫描；
- 删除规则；
- 离开或关闭当前页面。

选择保存时，先完成批量保存，成功后继续原操作；保存失败或取消确认时停留当前页面。选择放弃时只丢弃当前
内存编辑，再执行原操作。选择取消时不改变表格或项目。程序不得因扫描、重载或选择变化静默丢失脏行。

## 实施

1. 为 `RuleEditRow` 增加原始快照、脏状态通知、快照提交和恢复能力；
2. 在 `GitFileRuleService` 增加批量请求、逐项结果、批量预览模型和统一规划/应用方法；
3. 注册 `git.rule.batch-set`，加入参数校验、一次确认提示、Help 元数据和服务端数据反序列化；
4. 将规则页保存逻辑改为提交当前编辑、收集全部脏行、统一预览、一次应用和一次刷新；
5. 为切换、重载、扫描、删除和离页接入统一未保存修改保护；
6. 更新现行文档与自动生成命令手册，不修改历史版本文档；
7. 修改 `StudioVersion.props` 为 2.8.1，AppShell 包版本保持 3.0.3；
8. 完成定向开发验证；正式包、完整 Smoke、部署与回滚留到发布候选阶段。

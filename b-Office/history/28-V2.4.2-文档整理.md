## 3. `README` 上抛与角色拆分（本版关键判断）

### 3.1 现状：一份文件扮演两个角色

`meta/README.md` 同时是：

1. **仓库文档中心导航**——目录结构表、旧路径映射表、指向 `../versions/` 的 20+ 条链接；
2. **随程序发布的用户手册**——被 `Studio.csproj` 打包进 `Publish\docs\README.md`。

### 3.2 冲突的实际后果（已核实）

`Studio.csproj:33`：

```xml
<Content Include="..\b-Office\meta\README.md" Link="docs\README.md" CopyToPublishDirectory="PreserveNewest" />
```

**最终用户拿到的 `Publish\docs\README.md` 里**：

| 内容 | 对最终用户的价值 |
|---|---|
| `versions\` / `snapshots\` 目录结构表 | **无意义**——用户没有源码仓库 |
| 旧路径映射（`docs\…` → 现位置） | **无意义**——用户从未见过旧路径 |
| 20+ 条 `../versions/xxx.md` 链接 | **全部是死链**——发布包里没有 versions 目录 |

即：**当前随程序发布的 README 有八成内容对使用者无效，且含大量死链**。

### 3.3 处置：拆成两份，各归其位

| 文件 | 位置 | 面向 | 内容 |
|---|---|---|---|
| `README.md` | **`b-Office/` 根级** | 仓库内的人（开发者/AI） | 文档体系导航、目录结构、旧路径映射、指向 versions/meta/snapshots 的全部链接 |
| `使用说明.md` | `meta/` | 最终用户（拿到 Publish 的人） | 程序是什么、五份随附手册各讲什么、`help` 怎么用、控制台入口——**不含任何仓库内路径与跨目录链接** |

`Studio.csproj` 的 `Content Include` 改指 `meta\使用说明.md`，`Link` 仍为 `docs\README.md`
（**发布布局不变**，最终用户看到的仍是 `Publish\docs\README.md`，符合 V2.3.3 起
「Link 固定发布布局」的一贯原则）。

### 3.4 上抛牵动的引用（全部必改）

| 位置 | 现值 | 改为 |
|---|---|---|
| `b-Code-Studio/Studio.csproj:33` | `..\b-Office\meta\README.md` | `..\b-Office\meta\使用说明.md`（Link 不变） |
| 020 根级 `README.md:19` | `./b-Office/meta/README.md` | `./b-Office/README.md` |
| `b-Office/README.md:5` 自述位置 | `b-Office\meta\README.md` | `b-Office\README.md` |
| 上抛后 README 内的相对链接 | `./命令手册.md`、`../versions/…` | `./meta/命令手册.md`、`./versions/…` |

> `b-Publish/docs/README.md` 是发布产物，重新发布即更新，不手工改。

## 4. `snapshots` 是什么、如何处置

### 4.1 它是什么（实测）

每组快照含 2~3 个文件：

| 文件 | 内容 |
|---|---|
| `command-manual.md` | 该版本运行时生成的**全部指令完整形态**（名称/参数/默认值/允许值/来源/MCP 投影） |
| `console-baseline.log` | `help` 全文 + `win.list` + `proj.config` + `mcp.schema` + `command.list` 的**全量回显** |
| `README.md`（v232/v233 有） | 采集方式、采集环境、对账结果 |

**用途**：V2.1.6 起确立的「**对外行为全不变**」铁律的**对账基准**。质量整备或结构重构前采一份、
改完再采一份，逐行 diff 必须为空（或只剩版本号差异）才算通过。
V2.3.3 的核心指令「102 条逐字符一致」结论、V2.4.0/V2.4.1 的行为不变声明，
证据都在这里。

### 4.2 处置：**保留，不移动**

| 选项 | 判断 |
|---|---|
| 删除 | **不可**——删了之后，任何「本次重构未改变行为」的声明都失去客观依据，只能靠口头保证 |
| 移出 `b-Office` | **不建议**——它全是 `.md`/`.log` 文本，性质接近文档证据；且移动会让 `README` 旧路径映射表与历史文档中的 `docs\snapshots\` 引用全部失准 |
| **保留原位，明确定性** | **采纳**——在 `b-Office/README.md` 中写明它是「验收证据，非手册；只增不改」 |

### 4.3 但发现一处真实缺口：快照断档

现有 7 组：`v215 v216 v217 v220 v221 v232 v233`。

**缺失**：`v222`、`v230`、`v231`、**`v240`**、**`v241`**。

其中 **v240 / v241 的缺失最值得关注**——V2.4.0（伞形迁移 + AppShell 同源）与
V2.4.1（骨干削薄 + 源码上抛）是**迄今改动面最大的两次结构重构**，恰恰最需要
「行为完全没变」的客观证据，却都没有留下基线快照。

**建议（不强制进本版）**：在 V2.4.2 施工完成后补采一份 `v242`，作为
「文档整理未触碰任何产品行为」的证据，同时把 v233→v242 的核心指令数对账留档。
采集方法见 `snapshots/v232/README.md`（含 PowerShell 引号陷阱的踩坑记录）。

## 5. 需要着重关注的三件事

### A. 两份手册标「适用版本 V2.1.7」，落后 6 个版本（**最高优先级**）

`MCP接入与安全.md` 与 `模块开发手册.md` 写于 V2.1.7，而此后发生了 **V2.4.0 的 AppShell 0.4.4 反哺**：

- MCP 服务（网关 / 提示词治理 / 命令目录）**整体上抛到 AppShell 框架**，由 `ShellWindow` 自动装配，`ShellConfig.EnableMcp` 可关；
- 模块托管（`ModuleHost` / 热重载 / 面板同步）同样上抛框架，`ShellConfig.EnableModules` 可关；
- 三个管理窗口（命令集 / 指令详情 / 模块管理）也已进入框架；
- `McpExposurePolicy` 的只读白名单改为 `RegisterReadonly()` 由派生应用登记。

**这不是改个版本号的事**——两份手册描述的架构归属已经变了。
**处置**：逐节核对当前实现后重写，重写完标注「适用版本 V2.4.2」。

### B. `命令手册.md` 是自动生成产物，须明确标记

1872 行，占 `meta/` 的 75%，由 `command.manual` 从运行时注册表生成，
文首已有「请勿手工维护指令条目」但位置不显著。

**处置**：文首加醒目标记块，写明生成命令与再生成方式；`b-Office/README.md` 的手册表
中也标注「自动生成」。**内容本身不动**（它是运行时真值的投影）。

### C. 两份一次性清单不是手册

`部署物清理清单-V2.3.3.md`（V2.3.3 删除 210MB 部署物的审计清单，含 EXE 版本与 SHA-256）
与 `V2.4.0-M0-迁移前现状清单.md`（迁移前目录与体积基线）都是**一次性证据**，
用完即成历史，放在「现行手册」区会持续误导。

**处置**：移入新建的 `b-Office/evidence/`。**内容一字不改**——它们和 versions 一样是证据。

## 7. 风险与边界

1. **versions 绝对不动**——这是本版最硬的约束。M4 明确把「versions 无改动」列为验收项。
2. **发布布局不能变**——`Link="docs\…"` 是面向使用者的产品界面，V2.3.3 / V2.4.0 / V2.4.1
   三次迁移都守住了这条，本版同样必须守住：源文件改名，发布出来的文件名不变。
3. **重写过期手册有引入错误的风险**——§5-A 的两份手册重写是「按当前实现重新描述」，
   不是润色。建议对照 `b-Code-AppShell/src` 的实际代码逐节核对，不要凭记忆写。
4. **快照断档不在本版强制范围**——§4.3 的 v242 补采是建议项；若采纳，须在
   `Studio.csproj` 改动**之后**采集，才能证明「文档整理未影响产品行为」。
5. **`evidence/` 是新目录**——需确认它是否要纳入 `b-Office/README.md` 的目录结构表
   （建议纳入，与 meta/snapshots/versions 并列，四类性质各有其位）。

## 0. 一句话定义

V2.4.3 给 `CommandDescriptor` 加了 `Readonly` 自描述字段并**完成了全部 32 条迁移**，
但按计划保留了两份白名单作为兼容层。实测证明这两份白名单**已 100% 冗余**——
32 条无一例外都有了 `Readonly = true`。V2.4.4 删掉它们，让「命令是否只读」
真正做到**一件事实一个出处**。

### 1.3 保留冗余白名单的实际代价

`State()` 的判定链：

```csharp
if (descriptor.Readonly) return "readonly";                  // ← 32 条全在这里命中
return IsReadonlyAllowed(descriptor.Name) ? "readonly" : ... // ← 白名单已永远不会被这 32 条触发
```

代价有三层，且**都是给后续开发者的**：

1. **同一事实两处声明**——V2.4.3 要消灭的正是这个模式，现在以新形态留存；
2. **`AppMcpPolicy` 的类注释已经说谎**——它写着「本类是这 14 条的**单一真值**」，
   而真值早已迁到各 `CommandDescriptor` 上；
3. **误导性维护负担**——后续开发者（尤其 AI）看到这份清单，很可能以为
   「加只读命令还要来这里登记」，于是继续维护一份死代码，甚至在两处写出不一致。

> 第 3 点正是 V2.4.3 立项时要根除的「开发覆盖缺口」。**保留冗余兼容层的成本，
> 现在已经高于它提供的保险。**

## 2. 必须保留的部分（**不要连坐删除**）

删除动作有明确边界。以下三项**继续保留**：

| 保留项 | 理由 |
|---|---|
| `McpExposurePolicy.RegisterReadonly(params string[])` **方法本身** | 公共 API，供派生应用登记**框架不认识的**命令；删方法是破坏性变更 |
| `ExposureOf()` / `ModuleOfCommand` / `ModuleExposure` | 服务于**模块清单**声明的 `mcpExposure=readonly`——那是**模块的事实**，不是命令描述符的事实，两者不可混为一谈 |
| `IsReadonlyAllowed()` | 仍被 `ExposureOf()` 与 `IsVisible()` 使用；只是它的名单来源变空 |

**本版删的是「名单内容」与「登记调用」，不是「登记机制」。**

## 3. 变更明细

### 3.1 框架侧：清空基线名单

```csharp
// AppShell.Core/Mcp/McpExposurePolicy.cs
private static readonly HashSet<string> ReadonlyCommands = new(StringComparer.OrdinalIgnoreCase);

// 本集合继续存在，供 RegisterReadonly() 接纳「无法修改注册点」的外部命令。
```

同时更新类注释：说明**只读性的单一真值是 `CommandDescriptor.Readonly`**，
本名单仅为无法改注册点时的补登记通道。

### 3.2 派生侧：删除 `AppMcpPolicy.cs` 及其 3 处调用

## 5. 风险与边界

1. **唯一真实风险：漏迁的命令会静默降级**。若某条命令只在白名单里、没有
   `Readonly = true`，清空名单后它会掉到 `standard` 档。
   §1.2 已逐条核验 32/32 全部自描述，但 **M0 基线对账是最终保险**——
   McpState 列有任何一条变化即回退。
2. **不要删 `RegisterReadonly` 方法**（§2）。它是公共 API，且模块清单通道仍需要
   `IsReadonlyAllowed` 链路。
3. **`WiringSuite` 断言必须改而不是删**——删断言等于降低覆盖，与本项目一贯做法相悖。
4. **改动量极小，但不可跳过 GUI 实跑**。V2.4.0 有三个「冒烟全绿却启动即崩」的前例，
   全部只有 GUI 实跑抓到；本版触及 MCP 判定链，属同类风险区。

### 实施中的方案疏漏（如实留档）

§3.2 只识别出 `WiringSuite` 一处需要改断言，**实际有三套受影响**：

| 文件 | 断言 | 处置 |
|---|---|---|
| `WiringSuite.cs:121` | `IsReadonlyAllowed("proj.list"/"git.rule.list")` | 升级 + 新增「白名单必须为空」防回归断言 |
| **`V213Suite.cs:165-166`** | `IsReadonlyAllowed("git.rule.list"/"git.rule.set")` | **方案未提及**，施工中由冒烟失败暴露 |
| **`V230Suite.cs:164-166`** | `IsReadonlyAllowed("proj.history"×3)` | **方案未提及**，同上 |

**根因**：方案阶段只搜了 `AppMcpPolicy` 的调用点，没搜 `IsReadonlyAllowed` 的**全部使用点**。
删除数据源时，应同时排查「所有读取该数据源的地方」，而非只排查「写入方」。

**处置**：三处全部按同一原则升级为「查 `CommandDescriptor.Readonly` 真值 +
`McpExposurePolicy.State()` 解释结果」，判据比原来更强（从查外部名单变为查真值）。
无一条断言被删除或放宽。

## 7. 施工建议（关于执行者）

本版特征：**改动点极少（4 个文件）、但判据极硬（McpState 逐条一致）、且有一处断言需要
理解语义后改写（`WiringSuite`）**。

| 环节 | 难点 |
|---|---|
| 删文件与调用 | 机械，无难度 |
| 清空集合 + 改注释 | 机械，无难度 |
| **改 `WiringSuite` 断言** | **需理解「为什么原断言会失败、新断言该验什么」**——不是替换字符串，是把判据从「查外部名单」升级为「查描述符真值」 |
| **M0/M3 基线对账** | 需要正确采集 `command.list` 并**逐条比对 McpState 列**，不能只看总数 |

后两项对执行者的要求高于前两项：前者要理解设计意图，后者要严格按判据核验而非「跑通就算过」。

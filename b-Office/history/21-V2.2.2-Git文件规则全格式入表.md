> 主题：项目操作区必须呈现所选项目扫描到的全部文件格式，并明确显示其 Git、LFS 指针与 LF 文本状态。

## 0. 一句话定义

把 V2.2.1 已经扫描出来、却只留在控制台和缓存里的格式台账，真正接入「项目操作 → Git 文件规则」表格：
**所选项目扫描到什么扩展名，表格就出现什么扩展名；模板项目与普通项目完全同路，不设特例。**

## 1. 问题确认与根因

### 1.1 用户可见现象

1. 模板项目因根 `.gitignore/.gitattributes` 已声明较多规则，规则表能看到若干行；
2. 其他项目即使实际包含大量文件格式，规则表仍为空或只有少量既有规则；
3. 点击「扫描覆盖」只更新覆盖率文本并向控制台输出台账，扫描到的格式没有进入下方规则表；
4. 当前只有 `Git / LFS / LF` 三个复选框，不能一眼确认“这是 LF 文本，并且明确不使用 LFS 指针”。

### 1.2 代码根因

现行页面有两条彼此断开的读取链路：

```text
选择项目
  → git.rule.list
  → GitFileRuleService.ListAsync
  → 只返回 .gitignore/.gitattributes 中已经声明的 pattern
  → 绑定 RuleGrid

点击「扫描覆盖」
  → git.rule.scan
  → FormatInventoryService.ScanAsync
  → 返回 InventoryReport.Formats（项目真实存在的全部格式）
  → 只更新 CoverageText，未绑定 RuleGrid
```

因此问题不在扫描器。V2.2.1 已能扫描普通项目，缺口是 **UI 仍以“已声明规则”作为唯一表格数据源**。
模板项目看似正常只是因为模板声明较多，并非模板获得了特殊扫描能力。

### 1.3 V2.2.1 验收勘误

V2.2.1 A221-11 实际完成的是覆盖率条和四个入口按钮，并未完成设计文档 §6.2 所述的
“全部格式台账进入规则表、覆盖状态/建议列可见”。V2.2.2 专门关闭这一设计与实现的落差，
不把按钮存在等同于完整页面交付。

## 2. 本版目标

### 2.1 必须实现

1. 选择任意项目后，自动读取该项目格式台账，所有扫描到的扩展名都进入 Git 文件规则表；
2. 普通项目即使没有根 `.gitignore`、没有托管规则，也必须显示扫描到的格式；
3. 已声明但当前没有匹配文件的预置规则、目录规则不得因改用扫描台账而消失；
4. 每行明确显示 Git 归宿、是否 LFS 指针、是否 LF 文本以及最终存储结果；
5. 扫描发现但尚未声明的格式可直接在该行选择状态并保存，保存后刷新为已声明规则；
6. 切换项目、重新扫描、保存规则、删除规则后，表格和覆盖率必须来自同一项目、同一轮结果；
7. 所有读取和写入仍组装现有 `git.rule.*` 指令并经过 `CommandBus`，不增加 UI 直调服务旁路。

### 2.2 明确显示语义

表格必须有只读「存储结果」列，使用完整文字，不允许仅靠复选框猜测：

| Git | LFS 指针 | LF 文本 | 存储结果显示 |
|---|---|---|---|
| 否 | - | - | `忽略（不进入 Git）` |
| 是 | 是 | 否 | `Git + LFS（仓库存指针）` |
| 是 | 否 | 是 | `Git + LF（文本，非 LFS 指针）` |
| 是 | 否 | 否 | `普通 Git（非 LFS，未强制 LF）` |
| 未声明 | 未声明 | 未声明 | `未决（扫描发现，尚未声明规则）` |
| 混合 | 混合 | 混合 | `混合状态（受路径规则或多条属性影响）` |

硬约束继续沿用：

- LFS 与 LF 互斥；启用一个时自动关闭另一个；
- 不纳入 Git 时，LFS/LF 不可编辑并显示 `-`；
- `LF=是` 必须同时明确显示 `LFS 指针=否`；
- 未声明不等于忽略，也不等于普通 Git，必须保持独立状态。

## 3. 页面读取模型

### 3.1 单一表格、两份既有数据合并

不新增第三套扫描指令。项目操作页通过 `CommandBus` 读取：

1. `git.rule.scan name=<项目> deep=false refresh=false`：提供真实存在的全部格式、文件数、
   tracked/ignored/undecided 计数、规则状态和覆盖率；
2. `git.rule.list name=<项目>`：提供已声明规则的精确编辑状态、实际索引状态，并保留
   “当前零文件的预置规则”和目录规则。

页面按不区分大小写的 pattern 合并：

```text
扫描格式 .cs      → UI pattern *.cs
扫描格式 .xlsx    → UI pattern *.xlsx

最终表格 = 全部扫描格式
         + 已声明规则覆盖同 pattern 的编辑状态
         + 已声明但扫描结果不存在的格式规则
         + 已声明目录规则
```

同一个 pattern 只能出现一行。UI 不重新遍历文件系统、不自行解析 `.gitignore/.gitattributes`，
扫描、规则解析和 Git 真值仍分别由现有两个服务负责。

### 3.2 无扩展名文件

`(无扩展名)` 也必须在台账区可见，显示为 `other（无扩展名）`，但不能伪造成 `*.` 规则。
该行只读展示文件数与归宿；需要处理大集中目录时仍使用既有目录候选和
`git.rule.set pattern=Library/ track=false`。这样既不漏数据，也不制造无效 Git pattern。

### 3.3 扫描发现但未声明的行

这类行初始显示：

- 来源：`扫描发现`；
- 规则状态：`未声明`；
- 存储结果：`未决（扫描发现，尚未声明规则）`；
- 文件统计继续显示 tracked / ignored / undecided 的实际数量；
- 「删除规则」禁用，因为当前没有规则可删；
- 用户选择 Git/LFS/LF 并保存后，仍执行既有
  `git.rule.set name=... pattern=... apply=false → apply=true` 链路。

不得把 nullable 的“未声明”静默转换成 `Git=true,LFS=false,LF=false`，否则页面会虚构一条
并不存在的普通 Git 规则。编辑时由用户明确作出选择，或使用现有建议入口辅助判断。

### 3.4 已声明但零匹配的行

预置规则可能暂时没有文件，例如项目预先声明 `*.xlsx` 的 LFS 策略。这类规则仍显示，来源标为
`已声明（当前 0 文件）`，允许修改或删除。扫描台账不能取代规则清单，只能与其合并。

## 4. 页面交互

### 4.1 自动加载

选择项目后自动执行缓存读取，不再先显示一张“只有已声明规则”的残缺表：

```text
选择项目
  → 禁用规则区并显示“正在读取格式台账”
  → 并行取得 git.rule.scan(refresh=false) 与 git.rule.list
  → 校验返回时所选项目仍未变化
  → 合并、排序、一次性替换 RuleGrid
  → 同时更新覆盖率与未决数
```

模板项目不走任何特殊分支。普通项目、工具项目、空规则项目均使用同一流程。

### 4.2 手动重新扫描

「扫描覆盖」改为真正刷新表格：

```text
git.rule.scan name=<项目> refresh=true
  → 合并 git.rule.list
  → 重绘表格
  → 更新覆盖率
```

按钮不再只是刷新顶部文字。扫描过程保持只读，不写规则、不改索引、不提交。

### 4.3 保存与删除后的回读

- 保存成功：对当前项目执行 `refresh=true` 的完整回读，确认规则、索引状态和覆盖率一致；
- 删除成功：同样完整回读；若该扩展名仍有真实文件，它应继续留在表格中，但状态变回“扫描发现、未声明”；
- 删除规则不等于删除扫描行，这是本版必须验证的行为。

### 4.4 项目切换与竞态

沿用当前项目名回查并增加加载代次或取消令牌：A 项目尚在扫描时切到 B，A 的迟到结果不得覆盖 B。
加载期间只禁用规则区，不阻塞项目列表和其他窗口；异常时保留项目名并给出明确失败摘要。

## 5. 表格列与排序

### 5.1 最小列集

| 列 | 说明 |
|---|---|
| 格式 / Pattern | `*.cs`、`*.xlsx`、`Library/`、`other（无扩展名）` |
| 来源 | 扫描发现 / baseline / managed / 手写识别 / 目录规则 / 零匹配规则 |
| 文件 | 所选项目内匹配文件总数 |
| Git | 是 / 否 / 未声明 / 混合 |
| LFS 指针 | 是 / 否 / - / 未声明 / 混合 |
| LF 文本 | 是 / 否 / - / 未声明 / 混合 |
| 存储结果 | §2.2 的完整文字，是“LF 不用指针”的主要明确表达 |
| 当前状态 | tracked / ignored / undecided 计数和索引核验摘要 |

不新增独立详情窗口，不做卡片，不加入第二套规则编辑器。

### 5.2 默认排序

1. 未决格式；
2. 混合状态；
3. 已声明且有文件；
4. 已声明但零文件；
5. 目录规则；
6. 同组内按文件数降序、pattern 升序。

这样普通项目首次打开时，最需要决策的格式会直接出现在顶部。

## 8. 生产复验样本

实施后至少选择三类非模板项目：

1. 代码型项目：应出现 `.cs/.xaml/.json/.md`，LF 文本状态明确；
2. Office/CAD 项目：应出现对应二进制扩展名，普通 Git/LFS/未决状态明确，绝不能误标 LF；
3. Unity 或大目录项目：应出现 `.meta/.cs` 与 `other（无扩展名）`，目录候选继续可查。

每个样本记录：`git.rule.scan` 格式数、表格格式数、额外声明规则数、覆盖率、未决数。
满足 `表格格式 = 扫描格式 + 零匹配/目录声明规则（去重后）` 才算通过。

### 1.5 ⭐ 立论更正：规范 SHOULD 要求保留 JSON 文本块

**这是 R1 最严重的错误，必须放在最显眼处。**

[MCP 2025-06-18 · Server/Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) 原文：

> **Structured** content is returned as a JSON object in the `structuredContent` field of a result.
>
> **For backwards compatibility, a tool that returns structured content SHOULD also
> return the serialized JSON in a TextContent block.**

规范给出的示例响应也正是**两者并存**：

```json
{
  "content": [{ "type": "text", "text": "{"temperature": 22.5, ...}" }],
  "structuredContent": { "temperature": 22.5, ... }
}
```

由此三条结论：

| # | 结论 |
|---|---|
| 1 | **删除 JSON 文本块是偏离规范（违反 SHOULD），不是符合规范。** R1 的「协议符合性修正」定性完全反了 |
| 2 | **完全符合规范的做法是「加 `structuredContent`、保留 JSON 文本块」——字节数比现在更多，上下文占用不降反升** |
| 3 | 因此「省上下文」与「守规范」在此处**直接对立**，必须作为一次有意识的取舍来决策，不能包装成 bug 修复 |

## 3. 变更明细（本版范围）

本版只做**三件互不冲突、且全部向后兼容**的事。

### 3.1 【先做】019 ToolRelay 改为「优先 `structuredContent`、回退 `content`」

**必须排在网关改动之前**，这样它在网关改动前后都能工作。

`2026-019-Studio工具箱/b-Code-ToolRelay/OhsmcpClient.cs`，
`ListVisibleModuleToolNamesAsync()` 开头插入优先路径：

```csharp
// V2.4.5：优先读规范字段 structuredContent.data；
// 回退扫 content 文本块（兼容 V2.4.4 及更早网关，以及未来可能移除文本块的网关）
if (result.TryGetProperty("structuredContent", out var structured)
    && structured.ValueKind == JsonValueKind.Object
    && structured.TryGetProperty("data", out var dataElement)
    && dataElement.ValueKind == JsonValueKind.Array
    && TryReadModuleNames(dataElement, out var fromStructured))
{
    return fromStructured;
}

// ↓ 原有 content 扫描逻辑保持不变，作为回退路径
```

把现有的「读 `Source` / `McpToolName`」循环抽成 `TryReadModuleNames(JsonElement rows, out ...)`，
**两条路径共用同一段解析**，避免两处逻辑漂移。

> **回退路径必须保留**，不是过渡代码：ToolRelay 可能连到旧版本 OHS。

部署实例跑的仍是旧 DLL，「优先路径生效」的验收就是在验旧代码。

### 3.2 【后做】网关纯加法新增 `structuredContent`

```csharp
// AppShell.Services/Mcp/McpGateway.cs —— MG-04
// V2.4.5：新增 structuredContent（规范字段）。
// content 的两个文本块【全部保留】——规范 SHOULD 要求向后兼容，且 019 ToolRelay 回退路径依赖。
var content = new JsonArray
{
    new JsonObject { ["type"] = "text", ["text"] = result.Message },
};

JsonNode? structuredData = null;
if (result.Success && result.Data != null)
{
    try
    {
        // 第一步：与 V2.4.4 完全相同的调用生成旧文本块 → 旧字节【天然不变】
        var legacyJson = JsonSerializer.Serialize(result.Data, DataJson);
        content.Add(new JsonObject { ["type"] = "text", ["text"] = legacyJson });

        // 第二步：structuredContent.data 从同一个字符串【解析派生】→ 与旧文本必然同源
        structuredData = JsonNode.Parse(legacyJson);
    }
    catch (Exception)
    {
        structuredData = null;   // 序列化失败：文本块与结构化字段同时不发，行为与 V2.4.4 一致
    }
}

var payload = new JsonObject
{
    ["content"] = content,
    ["isError"] = !result.Success,
};

if (structuredData != null)
{
    // 规范要求 structuredContent 为 JSON 对象；Data 实测有数组/对象/字符串三态，故统一信封
    payload["structuredContent"] = new JsonObject { ["data"] = structuredData };
}

return RpcResult(id, payload);
```

**要点**：

1. **旧文本块的生成调用与 V2.4.4 一字不差**（`JsonSerializer.Serialize(result.Data, DataJson)`），
   字节级不变性由**同一调用**保证，不依赖对账兜底。
   > R2 版曾用 `SerializeToNode(...)` + 无参 `ToJsonString()` 生成文本块 —— 后者不沿用
   > `DataJson` 的 `UnsafeRelaxedJsonEscaping`，中文会被转成 `\uXXXX` 转义，含中文的
   > `command_list` 等结果字节必变，零差异判据必然失败。R3 弃用该写法。
2. **`structuredContent.data` 由 `JsonNode.Parse(legacyJson)` 从旧文本派生** —— 新旧两份
   天然同源，无漂移可能；`legacyJson` 是序列化器自己的输出，`Parse` 不会失败。
   节点只挂载一次，**无需 `DeepClone()`**（R2 版声称必需，随写法作废）；
3. **信封 `{"data": ...}` 的合法性**：规范明确 `structuredContent` 是 JSON **对象**，
   而 `Data` 实测三态：

   | 形态 | 实例 |
   |---|---|
   | 数组 | `proj_list` `command_list` `tool_list` `module_list` `proj_metalist` `command_domains` `ToolRelay_List` |
   | 对象 | `ToolKit_Now` |
   | 字符串 | `HelloWorld_Say` `ToolKit_NewGuid` |

   裸数组、裸字符串均不合规，故统一包一层，使 83 条暴露工具的结构化出口形状一致。

4. **本版不声明 `outputSchema`**：规范规定「若提供 `outputSchema`，服务端 **MUST** 保证
   结构化结果与之相符，客户端 **SHOULD** 校验」。为 83 条工具的任意 .NET 返回类型生成准确
   schema 是独立工程，**写错会让本可用的客户端硬失败**。留待后续立项。
   不声明即客户端不校验，故信封形状自由。

> **本版对传输的真实影响：线包体显著增加、模型上下文影响未知。**
> `structuredContent.data` 是 `content[1]` 的完整副本 —— `command_list` 的 HTTP 响应体
> 会额外增加约 **45KB**。它是否进入模型上下文取决于客户端行为，正是 §3.3 要实测的问题。
> **这是有意的取舍**：先用带宽换规范字段落位，省上下文是实验结论出来之后的事，
> 本版不做，也不假称做到了。

### 3.3 【实验】实测客户端如何处理 `structuredContent`

R1 把「迁走就不占上下文」当事实，但**规范只定义结果字段，不规定客户端怎样把字段交给模型**。
客户端可能忽略、可能展示、也可能整份塞进上下文。**必须实测，不能推定。**

**探针法（canary）**：让 `structuredContent` 携带一个 `content` 中**完全不存在**的随机串，
问模型能否复述。

**载体：独立临时探针 MCP 服务，不用 OHS 网关。**
R2 版设想用普通模块命令做探针 —— 不可执行：§3.2 的网关代码**始终从同一个
`CommandResult.Data` 生成 `content[1]` 与 `structuredContent.data`**，任何走网关的命令
都做不出「两边内容不同」的响应。探针必须是能手工控制每个字段的独立服务：

1. **探针服务**：约 60 行的最小 HTTP 脚本（临时文件，不入库），只应答
   `initialize` / `tools/list` / `tools/call`，注册进客户端 `.mcp.json` 作第二个 server。
   暴露两个工具，响应字段逐个手写：

   | 工具 | `content` | `structuredContent` | 用途 |
   |---|---|---|---|
   | `probe_structured` | `[{"text":"探针已执行"},{"text":"{\"note\":\"probe\"}"}]`（**无** canary） | `{"data":{"canary":"<串A>"}}` | 主实验 |
   | `probe_text` | `[{"text":"对照已执行"},{"text":"{\"canary\":\"<串B>\"}"}]` | **不发** | **正向对照** |

   串A、串B 为两个不同的 16 位随机串，互不出现在对方响应里。

2. **全新会话**中先后调用两个工具，然后问：「刚才两次调用各自的 canary 值是什么？」

3. **判读（对照组先行）**：

   | 串B（对照） | 串A（主实验) | 结论 |
   |---|---|---|
   | 复述失败 | — | **实验作废**——`content` 都没进上下文，说明探针接线有误，排查后重来 |
   | 复述成功 | 复述成功 | `structuredContent` **进入**上下文 → 移除文本块**不会**省 |
   | 复述成功 | 复述失败 | `structuredContent` **未进入** → 移除文本块**才可能**省 |

   没有对照组时，「复述失败」无法区分「字段不可见」与「探针本身没接通」——
   这正是对照组存在的意义。

4. 对 **Claude Code** 与 **Codex** 各做一轮（两者是 OHS 的现役客户端），
   每轮换新的随机串。

**出口**：结论写入 `evidence/v245-structuredcontent-probe/`，含探针脚本、canary 值、
原始 HTTP 响应、模型应答、客户端版本号。

> **结论有保质期**：客户端行为随版本变化，因此**必须记录客户端版本号**。
> 后续若要据此推进移除文本块，须先复测。

## 6. 风险与边界

1. **跨项目消费者搜索范围**：本版新增硬规矩 —— 改动 MCP 网关输出契约前，
   必须在 `C:\OneHistory\OneHistory-Projects\` **全域**搜消费者，不是只搜 020。
   §1.6 的漏检就是范围不足造成的。
2. **旧文本块的生成调用不可改动**：字节级不变性来自「与 V2.4.4 用同一个
   `JsonSerializer.Serialize(result.Data, DataJson)`」这一事实本身。
   任何「顺手统一成别的序列化写法」都会引入转义差异 —— R2 版正是死在
   无参 `ToJsonString()` 不沿用 `UnsafeRelaxedJsonEscaping`、中文变 `\uXXXX` 上。
   M2 零差异对账是**核验**这一点，不是兜底。
3. **M3 是测量不是验证**：不要因为「希望省上下文」而把实验做成自我印证。
   canary 必须真的不在 `content` 里，必须用全新会话，且**对照组（串B）先行判读**——
   对照失败即实验作废，不得把「探针没接通」记作「字段不可见」。
4. **ToolRelay 验收必须先过注册闭环**：`tool.list` 版本不是 1.0.1 之前，
   任何「优先路径生效」的结论都无效 —— 可能在验旧 DLL（§3.1 闭环表第 5 步）。
5. **`outputSchema` 不要顺手加**（§4）。
6. **不可跳过 GUI 实跑**：V2.4.0 有三个「冒烟全绿却启动即崩」的前例。
7. **多实例日志取证限制**（V2.4.4 已记录）：并发实例会导致第二实例静默丢文件日志。
   取证前确认无并发实例，**不要为取证关掉用户正在使用的实例**。

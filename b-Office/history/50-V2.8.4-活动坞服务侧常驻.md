# V2.8.4 活动坞服务侧常驻

> 日期：2026-08-02  
> 状态：已实机部署并完成运行验收；SE2SW 模块更新受阻，见遗留文档

## 目标

让桌面右下角的活动项目坞脱离 OneHistoryStudio 主窗口生命周期，改由已有的无窗服务宿主承载。关闭 Shell
主窗口后活动坞继续显示、继续刷新、继续响应固定与拖动。

不修改 AppShell，不解冻 `v3.0.3`，不引入托盘图标，不改变活动坞自身的交互与外观。

## 改动前的事实

活动坞由 `2026-019-Studio工具箱` 的 `StudioTools 1.1.0` 聚合模块提供，是该程序集中唯一的 `IUiModule`。

- `App.xaml` 声明 `ShutdownMode="OnMainWindowClose"`；
- `App.xaml.cs` 的 `ShellConfig` 中 `EnableModules = false`、`EnableUiModules = isServer`，桌面进程只加载
  模块界面、不注册模块命令；
- `StudioServiceCompositionFactory` 中 `ModuleHost` 的 `EnableUiModules = false`，服务宿主注册模块命令但
  不承载任何界面；
- `ActiveDockUiModule` 自持 `DockWindow`，`ShowInTaskbar = false`、不是 `MainWindow`，拦不住关闭；主窗口
  关闭导致进程退出，模块宿主执行 `DestroyUi()`，活动坞随之消失。

即常驻服务被装配为无 UI，活动坞挂在带窗口的 Shell 进程上。服务宿主本身具备承载条件：`ServiceHost.Run`
创建 WPF `Application`、设置 `ShutdownMode.OnExplicitShutdown`、把 `Modules.UiContext` 指向 Dispatcher，
进程入口 `Program.Main` 标注 `[STAThread]`。

## 承载面判据

`EnableUiModules` 是模块宿主的全局开关，而两类界面模块归属相反：活动坞自持顶层窗口，应归服务宿主；
GitHubConnection 经 `ShellUi.RegisterToolWindow` 停靠进主窗口，应归桌面 Shell。

区分判据不需要 AppShell 新增任何 API，`IShellUiAware` 的注入行为本身就是宿主标识，且它是 AppShell 3.0.3
已发布的公开接口：

- `ModuleHost.ScanAssembly` 只在 `ShellUi != null` 时对 `IShellUiAware` 实例赋值；
- 桌面进程 `ShellWindow` 在 `EnableModules || EnableUiModules` 分支内无条件设置 `ShellUi`，恒非空；
- `AppShell.ServiceHost` 源码不存在任何 `ShellUi` 赋值，OHS 服务组合根也不设置，服务进程恒为空；
- 注入发生在实例化阶段，早于 `Start()` 触发的 `CreateUi()`，模块建界面时归属已确定，不存在竞态。

因此由模块自行判断宿主并弃权，宿主侧只需打开开关。

AppShell 3.0.3 已发布的公开属性。桌面侧 `ShellConfig.EnableUiModules = isServer` 保持不变。

AppShell 四包引用继续固定 `3.0.3`，`StudioVersion.props` 提升为 `2.8.4`。

### 019 模块侧

活动坞整体迁出聚合程序集，成为独立物理模块：

| 模块 | 版本 | 变化 |

| `ActiveDock` | 新增 `1.0.0` | 从 StudioTools 迁出，命令域 `dock` 与六条命令签名不变；实现 `IShellUiAware` 仅用于探测宿主，被注入即弃权不建窗 |

## 连带修复

`ActiveDockState` 是进程内静态状态，变更经进程内事件通知窗口。改动前命令在服务进程、窗口在桌面进程，两侧是
两份互不相干的静态状态，`dock.hide`、`dock.show`、`dock.pin` 和 `dock.refresh` 因此改不动正在显示的活动坞，
只写入偏好文件，重启桌面进程才生效。

该结论由源码推导得出，**改动前后均未实机复现**。命令与窗口同处服务进程后该缺陷在设计上不再成立，仍需实机确认。

## 影响与边界

- 活动坞的存活范围变成服务宿主进程，`svc.stop` 或显式关闭宿主时才消失；
- 服务宿主运行在用户会话内（登录自启的用户级 Run 项）才能绘制窗口，本次不支持 SYSTEM 或非交互会话；
- 未启动服务宿主、只运行桌面 Shell 时不再出现活动坞；
- 桌面进程仍会加载 `ActiveDock` 程序集并实例化 UI 类型，只是弃权不建窗。要做到桌面侧完全不加载，需要按槽位
  控制承载面，那需要改 AppShell；
- 客户端角色本来就不加载模块 UI，行为不变；
- 活动坞位置与固定状态写入同一数据根，跨进程迁移后照常读取，不需要迁移动作。

## 已知弱点

宿主归属靠"是否被注入 `ShellUi`"隐式推断，而非 manifest 显式声明。若将来出现既需停靠、又需自持窗口的模块，
该推断不足以表达，届时才需要 AppShell 引入 UI 承载面与 manifest `uiSurface` 字段，那条路要求解冻 V3。
本次不预埋该字段，避免留下无实现支撑的空合同。

## 部署顺序

1. 先部署 OHS 2.8.4，打开服务侧界面承载；
2. 同步 `StudioTools 1.2.0`，确认 `command.list` 中 `dock.*` 消失；
3. 再同步 `ActiveDock 1.0.0`，确认 `dock.*` 来源变为 `module:ActiveDock`；
4. 同步 `GitHubConnection 1.0.1`。

第 2、3 步顺序不可颠倒：旧版 `StudioTools 1.1.0` 仍注册 `dock` 域，颠倒会导致命令域冲突。该约束与 2.8.3
迁出 `github` 域时的教训一致。

## 2. 三个上游资产的使用方式（边界务必分清）

### 2.1 z-APPShell —— 整体拷贝，只改 App

- V2-M0 第一步：把 `..\z-APPShell` 整个解决方案拷贝进本目录（`b-Code-OneHistory-V2.0\`），
  删除模板遗留的 `WpfApp1` 试验项目与各 bin/obj，解决方案更名。
- **只读区**：`src/AppShell.Core`、`src/AppShell.Services`、`src/AppShell.Shell`。
  发现"不改框架就做不了"的情况，**停下来向用户上报**，禁止先斩后奏（演进手册 §3）。
- 全部业务代码写在 `src/App` 项目：主窗口内容组件、proj.* 指令、模块托管服务、
  面板 JSON、启动装配（ShellConfig）。
- 在 `TEMPLATE_VERSION.md` 登记：本应用跟随基线 **0.4.1-M4**，未分叉。

### 2.2 b-Code-OneHistory-V1.0 —— 只搬逻辑，不搬窗体

- **允许移植源码**（复制到 App 项目并改命名空间）：
  `Services\WorktreeFileScanner.cs`（大小分级扫描）、`Services\WorktreeLfsHelper.cs`（LFS 检测与指针化）、
  `Models\BranchNode.cs / BranchInfo.cs / WorktreeInfo.cs`（数据模型）、
  `MainWindow.WorktreePush.cs` 中的提交流程编排（Success/Skipped/Rejected/Failed 四态）。
- **禁止移植**：MainWindow 的 UI 事件代码、MessageBox 确认流。V2.0 的确认一律走总线
  ConfirmPrompt 拦截器（模板已有 db.*/res.* 的现成用法可参照）。
- V1.0 中写死的路径（裸仓库、工作树根、模板分支）全部改为配置项，默认值不变。
- `..\Note.txt` 里的 worktree 断链批量修复方案是 PJ-11（proj.repair）的实现规格，照做。

### 2.3 b-Code-MyAPI-Lite —— 冻结原件，移植机制

- MyAPI-Lite 已于 2026-07-07 代码冻结，**一行都不要改它**，也不要让 V2.0 依赖它的 exe。
- V2-M3 的做法：参照 `MyApiLite\ModuleHost.cs`（ALC 热加载、目录监听、800ms 防抖、
  XML 注释解析）与 `Invoker.cs`（参数绑定、反射调用、async 解包）在 App 项目内实现
  等价的 ModuleHost 服务——差别只有一个：**方法注册目标从 HTTP 端点换成指令注册表**。
- 模块契约识别沿用鸭子类型（按 `BaseVariable.ModuleInfoBase` 基类全名匹配），
  保证既有模块 DLL 零修改可用。`BaseVariable` 与 `DemoModule` 两个项目可直接引用/复用。
- HTTP 与 MCP（`Program.cs` / `Mcp.cs`）**首版不移植**（需求 §9-Q2）。

## 3. 开发路线（对应验收单的六个节点）

```
V2-M0 骨架       拷贝模板 → 更名 OneHistoryStudio → 启动冒烟 → 基线登记
V2-M1 指令域     proj.* 全量（先 list/create/delete，再 commit/push，最后 all/repair）
                 ★ 出口：不开任何工具窗口，纯控制台跑通 创建→提交→推送→删除
V2-M2 界面       主窗口项目总览 + 继承树 + 三块面板 JSON
                 ★ UI 只是指令外壳：每个按钮点下去，控制台必须有等价回显
V2-M3 模块托管   ModuleHost 移植 → 模块方法注册为指令 → DemoModule 热重载验收
V2-M4 数据留痕   push_history / branch_notes 两表 + 资源窗口指向项目库
V2-M5 收尾       全量验收 + 模板关键项回归 + 发布 + V1.0 退役
```

节点顺序不建议调换：M1 先于 M2 是模板"控制台完备性"纪律的直接要求——
指令没跑通之前不存在"给按钮绑什么"的问题。

## 4. 关键实现约束（踩坑预防）

1. **git 进程统一封装**（需求 N-02）：一个 `GitRunner`，固定 `-C <目录>`、UTF-8 编码、
   超时、ExitCode 判定。V1.0 的 `RunGitCommandAsync` 可作为参照。裸仓库操作与
   worktree 内操作是两种工作目录，别混。
2. **危险操作单闸口**（需求 N-04）：proj.delete / proj.repair 的二次确认走总线
   ConfirmPrompt——这样 UI 按钮和手输指令自然共用同一道闸（模板验收 9 的机制）。
   受保护分支（0000-000-Template / main / master）在确认**之前**就直接拒绝。
3. **长任务异步 + 进度**（需求 PJ-13）：commitall 逐项上报 `[3/26] 2026-018-MyAPI ✓`
   风格进度；总线有 progress 通道协议（`cmd:progress`），不要自造。
4. **模块指令重名**（需求 MD-07）：注册前查指令注册表，冲突只跳过该方法并 Warn，
   模块其余方法照常注册。禁止静默覆盖内置指令。
5. **热重载与指令表一致性**：重载 = 先注销旧模块全部指令、卸载 ALC，再加载新 DLL 注册。
   确保 help 列表在重载后即时正确（这是验收项）。
6. **本机构建**：dotnet CLI 前设 `DOTNET_EnableWriteXorExecute=0`（LTSC 2021 CET 问题）；
   NuGet 只用 nuget.org。详见模板 TEMPLATE_VERSION.md「本机构建注意事项」。
7. **中文路径**：git 输出解析注意 quotepath 转义；worktree 断链是本机已发生过的真实故障
   （见 ..\Note.txt），proj.repair 就是为它准备的。
8. **测试用仓库**：开发调试期不要对生产裸仓库做删除/修复类操作——先用临时 bare 仓库
   （`git init --bare`）自建 3~5 个分支的沙盒验证，验收时再切生产路径做只读与创建类验证。

# OneHistoryStudio V2.8 · AppShell 解耦与包化消费

> 文档性质：V2.8 解耦立项、迁移合同与验收标准

> 范围：OHS 的工程引用方式、解决方案结构、发布链、文档与目录；**不改 OHS 业务逻辑**

## 0. 一句话定义

**V2.8 = OHS 与 AppShell 彻底分家**：OHS 不再直接引用 AppShell 源码，改为
`PackageReference OneHistory.AppShell.* 3.0.0`；`b-Code-AppShell/`、`z-Package-AppShell/`
及其发布链全部移出 020，由 023 独立维护。**OHS 从此是纯消费方。**

**不做**：不改 OHS 业务逻辑、不改命令语义、不改数据契约、不借解耦之名动 UI。

---

## 1. 为什么必须做

### 1.1 现状：OHS 与 AppShell 是**同一个解决方案里的源码级联动**

| 牵连点 | 实测 |
|---|---|
| `b-Code-Studio/Studio.csproj` | 4 条 `ProjectReference` → `AppShell.Core / Services / Shell / ServiceHost`（第 21~24 行） |
| `b-Code-Studio.Service/Studio.Service.csproj` | 1 条 `ProjectReference` → `AppShell.ServiceHost`（第 18 行） |
| `OHS.sln` | 含 **7 处** `b-Code-AppShell` 路径引用（Core/Services/Shell/ServiceHost/App 五个工程 + "AppShell" 解决方案文件夹节点） |
| `b-Code-AppShell/` | 891K：`src` / `tests` / `eng` / `artifacts` / `workspace`，含发布脚本 `eng/Publish-AppShell.ps1` |
| `z-Package-AppShell/` | 4.3M：`feed` / `manifest` / `checksums` / `changelog` / `staging` |
| `b-Publish/` | 含 `AppShell.Core/Services/Shell/ServiceHost` 的 `dll/pdb/xml` |
| 文档 | `b-Office/appshell/`（4 份）、`b-Office/meta/发布与升级.md`、`b-Publish/docs/发布与升级.md`、`stage/ohs-2.7.5/app/docs/发布与升级.md` 均描述 AppShell 发布链 |

**后果**：AppShell 源码一改，OHS 在同一个 sln 里**立刻上翻，没有任何版本缓冲**。
2026-07-27~28 三个项目同时出问题（AppShell 发 0.7.2 破坏性修订、OHS 做 2.7.x 质量长跑、
WBall 做 v3.4 质量修复），根因就是这个：**上层在一块正在移动的地板上排查问题，
分不清缺陷是自己的还是地板刚挪的。**

### 1.2 对照组：WBall 已经证明包化消费是可控的

WBall（022）是 `PackageReference 0.7.2`。AppShell 0.7.2 是破坏性修订（删除 `MainContent`、
工作页契约与 `page.*`），但 WBall 的迁移**实测只花 2 行改动 + 一次布局迁移**，
且四条确定性哈希逐字未变。**同为消费方，差别只在引用方式。**

### 1.3 前置条件已经成熟

V2.7.5 的质量长跑已把 OHS 的数据库依赖掀掉：`ShellConfig` 不再设 `DataService`，
`HistoryRecorder` / `ToolSyncService` / `PromptGovernanceStore` 全改吃 `paths.Root`，
不再注册表窗口。而 AppShell 3.0.0 的 FZ-00 正是**清除数据库空壳**（删 `IDataService`、
`TableView`、`db.*`）。**两边方向一致，OHS 已经具备迎接 3.0.0 的条件** —— 这是现在动手的窗口期。

## 2. 目标与非目标

### 2.1 目标

1. OHS 桌面与服务宿主**只经 NuGet 包**消费 AppShell，版本钉死 `3.0.0`；
2. 020 工作树内**不再存在任何 AppShell 源码、发布链与包制品**；
3. OHS 的构建、发布、Smoke 全绿，且**不依赖 020 内的 AppShell 目录**；
4. 文档与实际一致：OHS 文档不再以"内含 AppShell"为前提。

### 2.2 非目标

- 不修改 OHS 业务代码（除引用与装配必须的最小改动）；
- 不修改 AppShell 代码 —— 任何框架侧改动走 023 的 FZ-00~06，本文档不承接；
- 不在本版本调整 OHS 的功能、UI 或命令语义；
- 不删除 020 侧的历史证据与版本文档（`b-Office/versions`、`evidence` 保留）。

## 4. 引用改造（核心动作）

### 4.1 `b-Code-Studio/Studio.csproj`

```xml
<!-- 删除(第 21~24 行) -->
<ProjectReference Include="..\b-Code-AppShell\src\AppShell.Core\AppShell.Core.csproj" />
<ProjectReference Include="..\b-Code-AppShell\src\AppShell.Services\AppShell.Services.csproj" />
<ProjectReference Include="..\b-Code-AppShell\src\AppShell.Shell\AppShell.Shell.csproj" />
<ProjectReference Include="..\b-Code-AppShell\src\AppShell.ServiceHost\AppShell.ServiceHost.csproj" />

<!-- 改为 -->
<PackageReference Include="OneHistory.AppShell.Shell" Version="3.0.0" />
<PackageReference Include="OneHistory.AppShell.ServiceHost" Version="3.0.0" />
```

> `Shell` 会经传递依赖带上 `Core` 与 `Services`（WBall 已验证此模式）；
> `ServiceHost` 是服务宿主消费者才需要的包，OHS 桌面同时承载服务能力，故两包都要。
> **改造时先按上述两包试，若编译缺型再显式补 `Core`/`Services`** —— 不要一上来就写四条。

### 4.2 `b-Code-Studio.Service/Studio.Service.csproj`

```xml
<!-- 删除(第 18 行) -->
<ProjectReference Include="..\b-Code-AppShell\src\AppShell.ServiceHost\AppShell.ServiceHost.csproj" />
<!-- 改为 -->
<PackageReference Include="OneHistory.AppShell.ServiceHost" Version="3.0.0" />
```

### 4.3 `nuget.config`

020 当前只有 `nuget.org`（因为过去 AppShell 是源码引用，不需要 feed）。改造后必须新增本地 feed：

```xml
<add key="appshell-local" value="..\2026-023-AppShell\z-Package-AppShell\feed" />
```

**必须用相对路径**（相对 `nuget.config` 所在目录），不得写死绝对路径 ——
换机器/换盘符/全新 checkout 都要能直接 `restore`。若 023 不在同级目录，
用 `%APPSHELL_FEED%` 环境变量覆盖（NuGet 会展开环境变量），不改工程文件。

### 4.4 `OHS.sln`

删除 7 处 `b-Code-AppShell` 引用：5 个工程节点（`AppShell.Core` / `AppShell.Services` /
`AppShell.Shell` / `AppShell.ServiceHost` / `App`）+ "AppShell" 解决方案文件夹节点，
以及 `ProjectConfigurationPlatforms` 与 `NestedProjects` 里对应的 GUID 行。

**验证**：`dotnet sln OHS.sln list` 输出中不含任何 AppShell 工程。

### 4.5 版本钉死策略

- 全部 AppShell 包**统一 `3.0.0`**，不使用浮动版本（`3.0.*`、`[3.0,4.0)` 一律禁止）；
- 建议在 020 的 `Directory.Packages.props` 里集中管理该版本号，工程文件只写包名；
- 3.0.0 冻结期内**不允许**因为"顺手"而升级 —— 升级必须是一次独立的、有回归证据的决定。

## 6. 文档与知识资产处置

### 6.1 原则

AppShell 的文档**跟着 AppShell 走**。OHS 侧只保留"我如何消费它"的说明，不保留"它如何实现"的说明。

### 6.2 《二次开发演进手册》的权威归属（重要）

该手册是 OHS 与 WBall **共同重度消费**的文档 —— 两个消费方都靠它写代码，而不是翻 AppShell 源码。

**V2.8 起：023 的 `b-Office/appshell/` 是唯一权威。** 020 侧：

1. 删除 `b-Office/appshell/` 本地副本；
2. 在 `b-Office/README.md` 增加指向条目：
   `AppShell 二次开发手册 → 2026-023-AppShell/b-Office/appshell/二次开发演进手册.md（适用 3.0.0）`；
3. 若因离线等原因确需本地留档，文件头必须写明
   **`来源：2026-023-AppShell @ 3.0.0，只读副本，不得就地修改`**。

> 背景：WBall（022）已经出现过副本漂移 —— 其本地副本 15041 字节，023 权威版 15180 字节，
> 两份内容已不一致。消费方各存一份可改的拷贝，等于照着过期文档写代码。

### 6.3 OHS 侧需新增的说明

在 `b-Office/meta/发布与升级.md` 增加一节「AppShell 依赖管理」，写明：

- 当前钉死版本（3.0.0）与本地 feed 相对路径；
- AppShell 处于**冻结状态**，OHS 遇到框架缺陷时的正确流程：
  **登记"已知限制" + 向 023 提根因 issue，禁止在 OHS 侧加绕行补丁掩盖框架缺陷**；
- 升级 AppShell 的准入条件（见 §8）。

## 7. 顺序铁律

```
①  023 发布 AppShell 3.0.0 并冻结生效
     ↓
②  OHS 改引用(§4:两个 csproj + nuget.config + OHS.sln)
     ↓
③  ★构建通过 + Smoke 全绿★   ← 不通过则回退 ②,不得继续
     ↓
④  删除 020 内 AppShell 内容(§5,单独提交)
     ↓
⑤  文档处置(§6,单独提交)
     ↓
⑥  完整回归 + 归档证据
```

**②③ 与 ④ 之间不得合并提交。** 顺序颠倒（先删源码再换引用）会让 OHS 立刻无法构建，
且失去"回退一步就能恢复"的能力。

**删前预演**：④ 之前先把 `b-Code-AppShell` 临时改名为 `b-Code-AppShell.bak` 跑一次构建，
通过再真删 —— 这能抓出未被 §1.1 盘点覆盖的隐藏依赖。

## 9. 风险与回滚

| 风险 | 控制 |
|---|---|
| 3.0.0 包缺少源码引用时可见的类型（`internal`、未导出的 API） | ②③ 阶段暴露；缺什么记录成清单交 023，由 AppShell 侧决定"提升可见性发 3.0.1"还是"OHS 侧改用公开 API"。**不允许 OHS 反射硬取** |
| 传递依赖不足（只引 Shell/ServiceHost 编译不过） | §4.1 已写明：先试两包，缺型再显式补 `Core`/`Services` |
| 删除后发现隐藏依赖 | §7 的"改名预演"先抓一遍；真删单独提交，可单独回退 |
| 本地 feed 路径在其它机器解析不到 | 相对路径 + `%APPSHELL_FEED%` 环境变量兜底（§4.3） |
| 023 尚未发布 3.0.0 就动手 | §3 硬前置；禁止临时包与拷贝 dll |
| 文档删除导致消费方无处查阅 | §6.2 要求先在 023 就位并在 020 留指向，再删本地副本 |

**回滚点**：②③（引用改造）与 ④（删除）分别独立提交；任一步失败只回退该提交即可，
不需要整体回滚。3.0.0 发布前的 0.7.2 包与 2.7.5 源码 tag 保持可用。

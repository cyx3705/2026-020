### 1.4 采基线时发现：「命令总数 106」不是不变量

按 §10 边界 1 用 2.3.2 部署版采 v232 基线时，运行时报 **112** 条，与仓库
`docs\命令手册.md` 标称的 106 不符。查证结果（非缺陷，是**判据写法**问题）：

| 口径 | 数值 | 是否稳定 |
|---|---|---|
| **核心指令（框架 + App 注册）** | **102** | **稳定，与环境无关** |
| 模块指令 | 采集时 10 条 | 随 `%AppData%\OneHistoryStudio\Modules` 内容漂移 |
| 运行时总数 | 112 | = 102 + 10，**环境相关** |

`docs\命令手册.md` 的 106 是在模块目录只有 HelloWorld(1) + ToolKit(3) 时生成的（106 = 102 + 4）；
当前机器多了 DemoModule(4)、ToolAlpha(1)、ToolBeta(1)。两份手册**剔除 `module:` 来源章节后
逐字符完全一致**，102 条核心指令一条不差——即 V2.3.2 交付后核心指令面未发生任何变化。

**处置**：本版验收判据一律改用**核心 102 条**；运行时总数只作记录，不作判据（AQ233-14）。
V2.1.6 起沿用的「命令总数 106」写法把环境相关量当成了不变量，在本版终止。
24 号及更早文档作为历史记录不修改。

## 2. QC-01 运行时裁剪（最高优先级，单项收益 ≈ 570M）

新建解决方案级 `Directory.Build.props`，把运行时标识钉死为 Windows x64：

```xml
<Project>
  <PropertyGroup>
    <RuntimeIdentifier>win-x64</RuntimeIdentifier>
    <SelfContained>false</SelfContained>
    <SatelliteResourceLanguages>en</SatelliteResourceLanguages>
  </PropertyGroup>
</Project>
```

效果：`runtimes/` 整个消失，win-x64 原生库以 `e_sqlite3.dll` 落在输出根；
单份输出 **27M → ≈ 4M**。

**不采用的两个替代方案**（留档，避免后人重走）：

| 方案 | 否决理由 |
|---|---|
| `AfterBuild` target 删除非 win-x64 的 `runtimes/*` | 文件删了但 `deps.json` 仍登记，属「账实不符」，运行期探测行为不可预期 |
| 换 `Microsoft.Data.Sqlite.Core` + 手选 bundle | 依赖链最终仍指向同一个全 RID 的 `lib.e_sqlite3`，不解决问题 |

**必须实测的风险点**（SQLite 是全解决方案唯一的原生依赖）：

1. `deps.json` 的 `runtimeTarget` 变为 `.NETCoreApp,Version=v8.0/win-x64`；
2. **部署必须整目录替换**，不得增量覆盖——旧部署目录里的 `runtimes/` 不会被新产物删除，
   增量覆盖会留下 25M 陈旧文件且掩盖验证结果。本版起该要求升级为**强制规则**，
   流程与失败即停条款见 §10.1，验收见 AQ233-18；
3. 部署版冒烟必须显式走一遍 SQLite 通路：`main.db` 打开、`db.*` 指令、表窗口翻页、留痕写入。

## 3. QC-02 冒烟工程合并（5 → 1）

现状 5 个工程各自 `ProjectReference App.csproj`，于是把整个应用输出复制 5 遍 × 2 配置。

**方案**：新建 `tests/Smoke/Smoke.csproj` 单一 Exe：

- `Program.cs` 按 `--suite <name>` 分派；无参数时依次全跑，任一失败即非零退出；
- 五套用例各自成为 `V213Suite / PromptGovernanceSuite / V230Suite / V231Suite / V232Suite`
  （由 top-level statements 改为类方法，**断言逐条原样搬运**）；
- 9 类重复助手收敛为 `SmokeKit.cs` 一份；
- 新工程**加入 `OneHistoryStudio.sln`**，结束游离状态。

**红线**：327 条断言一条不少、判据一字不改、PASS/FAIL 文案与退出码不变——现有回归脚本
（十次 Debug/Release 构建与运行）只改调用行，不改判定逻辑。

收益：测试输出 10 份 → 2 份（272M → ≈ 9M）；回归一次的构建时间同步下降。

## 5.1 QC-09 已入库构建产物退出索引（**待用户授权**）

398 个 `bin/` `obj/` 文件（58.2MB）已在版本控制中，`.gitignore` 拦不住它们。

**方案**：`git rm --cached` 把它们移出索引，**文件保留在磁盘**，随后一次普通提交。

| 特性 | 说明 |
|---|---|
| 是否重写历史 | **否**——旧提交原样保留，只让后续提交不再携带 |
| 与 DQ233-3 关系 | 不冲突。DQ233-3 禁的是重写历史，本条是正向新增一个删除提交 |
| 磁盘影响 | 无，工作区文件不动 |
| 收益 | 后续每个版本不再重复提交约 58MB 构建产物 |

**用户裁决（2026-07-24）：本条不执行，条目关闭。**

> 原话：「不用动，因为我们已经把这个管理做得很棒了，到时候 OneHistory 中设置不跟踪相关
> 扩展名文件即可，你别管。」

即改由本产品自身的 Git 文件规则能力处置（`git.rule.set pattern=… track=false`），
而不是由实施方执行 `git rm --cached`。这与 QC-04 的思路一致——**用自己的工具管自己的仓库**，
且不需要实施方触碰源码 Git 索引。V2.3.3 不再涉及任何 Git 索引操作。

> **副作用提示（仍然有效）**：QC-01 的重建已让这 398 个已跟踪文件在工作区发生变化，
> `git status` 显示约 99 个删除 + 160 个修改（全部是 `runtimes/` 等构建产物）。
> 由用户按上述方式统一处置，实施方不提交、不清理。

### 10.1 部署强制流程（不可跳步、失败即停）

自 V2.3.3 起，正式部署固定为以下六步，**每一步失败立即停止，不得进入下一步**：

```
1  停止程序（确认 OneHistoryStudio.exe 进程已退出、文件无占用）
2  将旧部署目录整体重命名为 OneHistoryStudio-rollback-<版本>-<时间戳>
3  确认重命名成功（旧路径 OneHistoryStudio 已不存在）
4  从 Publish 创建全新部署目录 OneHistoryStudio
5  核对文件数、EXE 版本、逐文件 SHA-256 与 Publish 完全一致
6  启动只读冒烟（版本号、Help 条数、command.list、项目列表、SQLite 通路、正常退出）
```

**硬性禁止条款**：

| # | 禁止 | 原因 |
|---|---|---|
| 1 | 第 2 步重命名失败后继续复制 | 会把 `Publish` 复制成旧目录下的子目录，即 V2.3.2 的 `OneHistoryStudio\Publish` 嵌套事故（当时产生 120 文件异常现场，见 24 号文档交付记录） |
| 2 | 增量覆盖、仅复制新文件、`robocopy` 无 `/MIR` 的同步 | 旧 `runtimes/`（25M）不会被删除，既留陈旧文件又掩盖 QC-01 的验证结果 |
| 3 | 跳过第 3 步直接建目录 | 重命名失败与目录已存在是同一类现场，必须显式确认路径不存在 |
| 4 | 第 5 步哈希不一致时「先用着」 | 发布身份是 AQ233-17 的判据，不允许带差异上线 |

第 2 步若因权限或占用失败：回到第 1 步排查占用进程，**不得**改用复制+删除绕过，
也不得就地覆盖。排查不通则本次部署终止，保持旧部署可用状态。

### DQ233-3 判定依据：为何不重写历史

约 159M 的历史负担**不足以抵消重写风险**。本项目库是「裸仓库 + 多 worktree」的树状结构，
重写会连锁触发：

| 后果 | 影响面 |
|---|---|
| 大量提交 SHA 改变 | 22 号文档的分支历史、回滚记录与既有引用全部失效 |
| 所有分支与 worktree 需重新对齐 | `OneHistory-Projects.git` 下每个 worktree 都要重挂 |
| GitHub 需强制推送 | 破坏性远端操作，且与本产品「子先父后」的安全推送合同相悖 |
| 其他机器上的旧克隆 | 可能把旧历史重新推回来，前功尽弃 |

**重新开启本条的唯一条件**（满足其一即重议）：

1. 这些快照中被发现包含密钥、令牌或隐私数据；
2. 仓库体积已**实际阻碍**克隆或备份（以实测失败或超时为准，不以体感为准）。

在此之前，`Publish/` 的历史成本由 QC-01（单版本 26.5MB → ≈4MB）与 QC-04（转 LFS）
在**增量侧**解决，存量不动。

### 交付后补记（2026-07-24 文档整理时发现）

**一处交付缺口**：已部署的 2.3.3 随程序发布的 `docs\命令手册.md` 内容仍是
**2.3.2 时代生成的**（头部写「版本：2.3.2 / 指令总数：106」）。M4 期间只把手册重新生成到了
`snapshots\v233\command-manual.md` 用于对账，**没有回填仓库里那份随程序发布的手册**。
AQ233-14 比的是快照对快照，因此没能拦住——判据应同时覆盖**随程序发布的那一份**。
该缺口只影响随附文档内容，不影响任何指令行为、MCP 投影或程序功能。

**当前源码已领先于部署区**：文档整理把 `docs\` 拆为 `versions\ / meta\ / snapshots\`，
并按用户裁决同步修改了 `command.manual` 的示例路径（`docs/命令手册.md` → `meta/命令手册.md`）。
该改动进入编译产物，`OneHistoryStudio.dll` 已与部署区那份不同（EXE 哈希相同是因为它只是
apphost 壳，托管代码在 DLL 内——**发布身份应以 DLL 为准记录，本版记的 EXE 哈希不足以标识代码**）。
`meta\命令手册.md` 也已用 2.3.3 运行时重新生成（112 条）。

两者叠加意味着：**再次部署前必须升版本号**，否则会出现两个内容不同、却同为 2.3.3 的构建。
处置留待下一版本决定，本版交付记录不追改。

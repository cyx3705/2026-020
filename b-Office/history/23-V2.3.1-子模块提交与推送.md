# OneHistoryStudio V2.3.1 子模块提交与推送

> 文档性质：V2.3.1 工程实施与验收合同  
> 基线版本：V2.3.0 -> 目标版本：V2.3.1  
> 日期：2026-07-24  
> 状态：**已交付（页面交互视觉签字待用户）**

---

## 0. 一句话定义

在不改变旧命令默认行为的前提下，让 OneHistoryStudio 能识别父项目索引中的直属 Git 子仓库，
按“子仓库先提交/推送，父仓库后提交/推送”的固定顺序完成联动操作，同时兼容标准子模块和
没有 `.gitmodules` 的历史 `160000 gitlink`。

## 1. 问题基线

### 1.1 用户可见现象

使用 OneHistoryStudio 提交 `2026-018-MyAPI` 时，父项目中的 `b-Code-MyAPI-Core` 仍显示子模块变化，
其内部修改、删除和未跟踪文件没有进入提交；随后推送父项目时，也不会把子仓库的提交推送到它自己的远端。

### 1.2 当前项目实况

`b-Code-MyAPI-Core` 具备以下特征：

1. 父仓库索引以 `160000` 模式记录该路径，说明父仓库保存的是子仓库提交指针；
2. 子目录自身包含有效 Git 仓库，当前分支和 `origin` 属于子仓库；
3. 父项目根目录没有 `.gitmodules`，因此它不是声明完整的标准 Git 子模块；
4. 子仓库中存在实际文件改动，但父仓库只能提交 gitlink 指针，无法替子仓库提交文件内容。

这不是普通文件遗漏。Git 仓库边界决定父仓库的 `git add`、`git commit` 和 `git push` 不会自动进入子仓库。

### 1.3 代码根因

现有提交与推送链路均只操作所选父工作树：

```text
proj.commit
  -> ProjectService.CommitAsync
  -> 父工作树 git add .
  -> 父工作树 git commit -m

proj.push
  -> ProjectService.PushAsync
  -> 父工作树 git push origin <父分支>
```

`proj.commitall` 复用同一父工作树提交逻辑，`proj.pushall` 只在 OneHistory 裸仓库执行
`git push --all origin`。当前没有 gitlink 发现、子仓库预检、子仓库提交或子仓库远端推送阶段。

## 2. 目标与边界

### 2.1 必须实现

1. 识别所选项目索引中的全部直属 `160000 gitlink`；
2. 同时支持标准 `.gitmodules` 子模块和无 `.gitmodules` 的历史嵌入式 Git 仓库；
3. 提交前一次性预检所有参与仓库，确认后先提交脏子仓库，再提交父仓库；
4. 推送前一次性预检所有参与仓库，先推送子仓库当前分支，全部成功后再推送父仓库；
5. 子仓库提交描述默认使用父项目描述，也允许本次操作统一覆写；
6. `proj.commitall/proj.pushall` 复用单项目服务能力，不建立第二套 Git 处理逻辑；
7. 命令结果提供结构化逐仓库状态，控制台只显示摘要，失败时明确说明是否出现部分完成；
8. 所有 Git 进程继续统一通过 `GitRunner`，UI 只组装命令并进入 `CommandBus`。

### 2.2 明确不做

- 不自动创建、删除、补写或修复 `.gitmodules`；
- 不把历史 gitlink 强制迁移成标准子模块；
- 不递归提交第二层及更深层子模块；
- 不自动创建远端、修改远端地址或设置 upstream；
- 不执行 rebase、reset、强制推送或任何历史改写；
- 不在多个仓库之间伪造“原子事务”，不因后续失败自动回退已经生成的提交；
- 不新增数据库表，不改变现有项目目录和裸仓库边界配置。

## 3. 子仓库发现模型

### 3.1 唯一发现依据

对子仓库的发现固定使用结构化 Git 输出：

```text
git ls-files --stage -z
```

只把索引模式为 `160000` 的条目视为 gitlink。`.gitmodules` 存在时，可通过
`git config -f .gitmodules ...` 补充标准子模块名称和声明地址，但不得把 `.gitmodules`
作为识别前提，也不得用文本切割自行解析其配置语法。

不得调用 `git submodule status`、`git submodule foreach` 等依赖 Git for Windows shell helper 的命令。
发现子仓库后，所有检查和操作均通过 `GitRunner.RunAsync(childPath, string[] arguments, ...)` 直接执行。

### 3.2 支持的仓库形态

| 形态 | 父索引 | 子目录 Git 元数据 | `.gitmodules` | 处理结果 |
|---|---|---|---|---|
| 标准子模块 | `160000` | `.git` 文件或目录 | 有 | 支持 |
| 历史嵌入式仓库 | `160000` | 独立 `.git` 目录 | 无 | 支持 |
| 未初始化子模块 | `160000` | 不存在或无效 | 可有 | 预检拒绝 |
| 普通嵌套仓库 | 普通目录/未跟踪 | 独立 `.git` | 无 | 不纳入本功能 |

“子模块”是页面统一称谓；内部结果必须保留 `StandardSubmodule` 与 `LegacyGitlink` 类型，便于诊断，
但两类仓库使用完全相同的提交和推送安全规则。

### 3.3 路径边界

1. gitlink 路径必须是父项目内的相对路径，不允许绝对路径、盘符切换或 `..` 越界；
2. 组合并规范化后的子仓库路径必须仍位于父项目根目录内；
3. 路径经过重解析点后可能逃逸父目录时拒绝处理；
4. 子目录必须通过 `rev-parse --is-inside-work-tree` 验证为有效工作树；
5. 不扫描父项目索引之外的任意 `.git` 目录，避免把普通工具目录误当作受管子模块。

## 4. 命令合同

### 4.1 兼容参数

现有四条命令增加可选参数，不新增 UI 专用平行指令：

```text
proj.commit name= msg= submodules=false submsg=
proj.push name= submodules=false
proj.commitall msg= submodules=false submsg=
proj.pushall submodules=false
```

| 参数 | 默认值 | 语义 |
|---|---|---|
| `submodules` | `false` | 是否发现、预检并联动处理直属 gitlink |
| `submsg` | 空 | 子仓库统一提交描述；空或全空白时回退到父项目 `msg` |

命令默认保持 `submodules=false`，确保旧 CLI、脚本和 MCP 调用仍只操作父仓库。页面默认显式发送
`submodules=true`，因此用户从 OneHistoryStudio 页面提交和推送时默认获得完整联动能力。

示例：

```text
proj.commit name=2026-018-MyAPI msg="更新父项目" submodules=true
proj.commit name=2026-018-MyAPI msg="更新父项目" submodules=true submsg="更新 MyAPI Core"
proj.push name=2026-018-MyAPI submodules=true
proj.commitall msg="每日归档" submodules=true submsg="同步子仓库"
proj.pushall submodules=true
```

### 4.2 结构化类型

实施阶段至少提供：

- `GitlinkDescriptor`：相对路径、规范路径、类型、当前分支、操作前 HEAD、父索引 SHA、脏状态和变更计数；
- `SubmoduleOperationEntry`：仓库、分支、操作、操作前后 SHA、结果、消息和是否已完成远端推送；
- `SubmoduleOperationOutcome`：`Skipped / Success / Rejected / Failed`；
- `CommitReport`：保留现有字段，增加子仓库结果集合和 `PartialCompletion`；
- `PushReport`：替代简单 `(bool Success, string Message)`，包含父仓库结果、子仓库结果和
  `PartialCompletion`。

完整报告通过 `CommandResult.Data` 返回。命令消息只显示参与、成功、跳过、拒绝、失败数量及首个失败原因，
不得把全部文件状态刷入控制台。

## 5. 提交流程

### 5.1 完整预检

`submodules=true` 时，在创建任何提交前对父仓库及全部直属 gitlink 完成预检：

1. 发现并验证所有 gitlink 与路径边界；
2. 读取每个子仓库 `status --porcelain=v1 -z --untracked-files=all`；
3. 读取当前分支和完整 HEAD，detached HEAD 直接拒绝；
4. 检查有效的 `user.name` 与 `user.email`；
5. 统计修改、删除和未跟踪文件数量；
6. 检查子仓库内部的 gitlink 状态；存在第二层子模块变化时拒绝，提示 V2.3.1 不递归处理；
7. 沿用现有大文件与 LFS 检查，检查范围扩展到本次参与提交的每个脏仓库。

任一仓库预检失败时，不得先提交其他仓库。干净子仓库记录为 `Skipped`，不制造空提交。

### 5.2 确认内容

存在脏子仓库时，通过现有确认通道显示：

- 父项目名称；
- 子仓库相对路径、类型和当前分支；
- 每个子仓库的修改、删除、未跟踪文件数；
- 子仓库实际使用的提交描述；
- 固定执行顺序及“多仓库无法原子回退”的说明。

用户拒绝时不执行任何 `add/commit`。无脏子仓库时不增加无意义确认，继续原有父仓库提交链路。

### 5.3 固定执行顺序

```text
全量预检
  -> 用户确认
  -> 逐个脏子仓库 git add -A
  -> 逐个脏子仓库 git commit -m <submsg 或 msg>
  -> 父仓库原有大文件/LFS 流程
  -> 父仓库 git add .
  -> 父仓库 git commit -m <msg>
```

子仓库提交成功后，父仓库的 `git add .` 必须把新的 gitlink HEAD 纳入父提交。若某个子仓库提交失败，
立即停止后续子仓库和父仓库提交；已经成功的子仓库提交保留，结果标记 `PartialCompletion=true`，
列出已完成仓库及其新 SHA，禁止自动 reset。

若所有子仓库成功但父仓库提交失败，同样保留子仓库提交并明确提示“子仓库已提交，父仓库尚未记录新指针”。

## 6. 推送流程

### 6.1 推送预检

`submodules=true` 时，推送任何仓库前必须验证：

1. 所有直属子仓库工作树完全干净；
2. 子仓库处于命名分支，且存在 `origin`；
3. 父仓库 HEAD 记录的 gitlink SHA 与子仓库当前 HEAD 一致；
4. 子仓库当前分支和父仓库目标分支均可明确取得；
5. 不修改远端 URL，不自动执行 `push -u`，不使用任何强推参数。

不存在 `origin`、detached HEAD、脏工作树或 gitlink/HEAD 不一致时，整次操作在网络写入前拒绝。

### 6.2 固定执行顺序

```text
全量预检
  -> 按相对路径稳定排序并推送子仓库：git push origin <子仓库当前分支>
  -> 所有子仓库成功
  -> 执行原有父仓库推送
```

任一子仓库推送失败时立即停止，不推送父仓库。此前成功推送的子仓库无法自动撤回，报告必须标记
`PartialCompletion=true`，列出已推送仓库和失败仓库。不得降级为强推，不得忽略失败继续父推送。

### 6.3 批量行为

`proj.commitall submodules=true` 遍历登记工作树并调用同一单项目提交服务；
`proj.pushall submodules=true` 先枚举所有登记工作树的直属 gitlink，按规范仓库路径去重后推送子仓库，
全部成功后才执行现有裸仓库 `git push --all origin`。

批量操作保持现有危险确认入口，并在确认文案中增加参与的子仓库数量。批量阶段的任一项目失败后，
`commitall` 继续处理后续登记项目并在末尾统一汇总，但失败项目的父仓库不得越过其子仓库失败继续提交。
`pushall` 在首个子仓库推送失败时立即停止剩余推送，且不得执行父裸仓库的 `git push --all origin`。

## 7. 页面交互

### 7.1 项目操作

在现有提交/推送区域内增加一个紧凑的“子模块”设置行，不新增窗口：

1. `包含子模块` 复选框，页面默认勾选，同时控制提交和推送命令的 `submodules`；
2. `沿用父提交描述` 复选框，默认勾选；
3. 一个子模块提交描述文本框，仅在包含子模块且取消沿用父描述时启用；
4. 多个直属子仓库共用同一个子描述，本版不增加逐仓库文本框；
5. 页面仍只组装 `proj.commit/proj.push` 并交给 `CommandBus`，不得直调发现或 Git 服务。

### 7.2 项目总览

批量提交区域增加相同的两个复选框和一个按需启用的子描述文本框；批量推送复用“包含子模块”状态。
页面显式发送 `submodules=true/false`，不依赖命令默认值猜测用户意图。

操作完成后，控制台显示摘要；完整逐仓库结果保留在 `CommandResult.Data`，页面可用现有结果展示机制查看，
不新增自动弹出的长列表窗口。

## 8. 操作留痕

不新增数据库表，不修改 `push_history` 结构：

1. 父项目继续记录既有 `commit/push/commitall/pushall` 动作；
2. message 摘要增加子仓库数量、成功/失败数量、操作前后 SHA 和首个失败原因；
3. 逐子仓库结果使用现有记录能力追加留痕，项目标识由“父项目 + 子仓库相对路径”组成；
4. 留痕失败只记录警告，不覆盖 Git 主操作的真实成功或失败结果；
5. 不把 `push_history` 当作 Git 提交或远端历史真值。

# OneHistoryStudio V2.4.3 · 代码卫生与自管理 —— 工程实施文档

> 文档性质：**卫生升级方案**（消除硬编码散布与扩展缺口，不新增功能）
> 基线版本：V2.4.2（文档整理）｜ 本版：V2.4.3 ｜ 日期：2026-07-25～26 ｜ 状态：**已交付**
> 铁律：**对外行为全不变**——指令清单/语义/参数、MCP 工具形态、页面布局、数据表结构、
> 冒烟断言判据逐项一致。核心指令数仍须为 **102**。
>
> **绝对边界**：`b-Office/versions/` 除本文档外一字不动。

---

## 0. 一句话定义

V2.3.3 整备的是**体积与结构**，本版整备的是**事实的归属**：
一件事实（这条命令是否只读、这个目录叫什么、这个版本号是多少）现在被抄写在多个文件里，
新增功能时必须**跨文件同步修改**，漏一处就产生**静默失效的覆盖缺口**。
V2.4.3 让每件事实**只有一个出处**，并让「新增」尽可能**只碰一个文件**。

## 2. H1 · 命令只读性：本版的头号问题（P0）

### 2.1 现状：事实存在错了地方

`CommandDescriptor` 已经能自描述这些属性：

```csharp
public Func<CommandContext, string?>? ConfirmPrompt   // 危险 → 自己声明 ✅
public bool SupportsUndo                              // 可撤销 → 自己声明 ✅
public bool RequiresUiThread                          // UI 线程 → 自己声明 ✅
```

**唯独「是否只读」没有字段**，被放在外部按名字匹配的白名单里：

```csharp
// AppShell.Core/Mcp/McpExposurePolicy.cs —— 框架基线 18 条
private static readonly HashSet<string> ReadonlyCommands = { "help", "history", "db.query", … };

// b-Code-Studio/AppMcpPolicy.cs —— 派生登记 14 条
McpExposurePolicy.RegisterReadonly("proj.list", "proj.tree", …);
```

判定逻辑（`McpExposurePolicy.State`）：

```csharp
if (HardExclusionReason(...) != null) return "hidden";
if (descriptor.ConfirmPrompt != null) return "dangerous";   // ← 自描述
return IsReadonlyAllowed(descriptor.Name) ? "readonly" : "standard";  // ← 查外部名单
```

### 2.2 后果：新增只读命令的真实流程

开发者新增 `proj.foo`（只读）：

| 步 | 文件 | 忘了会怎样 |
|---|---|---|
| 1 | `Git/ProjectCommands.cs` 注册 | 命令不存在（立即发现） |
| 2 | **`AppMcpPolicy.cs` 补白名单** | **默认落到 `standard` 档；readonly 档 MCP 客户端看不见它；不报错、不警告、冒烟也不失败** |

**这就是「开发覆盖缺口」的标准形态**：正确路径要跨文件横跳，漏掉的代价是静默降级。
而「只读」本就是这条命令自身的属性，和它的 `Summary`、`Parameters` 同级。

### 2.3 方案：让命令自己说

```csharp
// AppShell.Core/Commands/CommandDescriptor.cs
/// <summary>
/// 只读声明：命令不改变任何持久状态（不写库、不改文件、不动 Git 索引/远端）。
/// 与 ConfirmPrompt / SupportsUndo 同级，属命令自身事实，由注册处一并声明。
/// </summary>
public bool Readonly { get; init; }
```

`McpExposurePolicy.State` 改为优先取自描述：

```csharp
if (descriptor.Readonly) return "readonly";
return IsReadonlyAllowed(descriptor.Name) ? "readonly" : "standard";  // 兼容层，见 §2.4
```

新增只读命令从此**只碰一个文件**：注册时写 `Readonly = true`。

### 2.4 迁移路径（分两步，本版只做第一步）

| 步骤 | 内容 | 版本 |
|---|---|---|
| **1（本版）** | 加 `Readonly` 字段；把现有 32 条白名单逐条落到对应 `CommandDescriptor` 上；白名单**保留为兼容层**（模块 `mcpExposure=readonly` 仍走它） | V2.4.3 |
| 2（后续） | 确认无遗漏后，删除 `RegisterReadonly` 与 `AppMcpPolicy.cs` | 待定 |

**本版保留兼容层**的理由：`ExposureOf()` 走的是模块清单声明（`mcpExposure=readonly`），
那是模块的事实、不是命令描述符的事实，不能一并删。两步走可验证、可回退。

### 2.5 验收（关键）

迁移前后 `command.list` 输出的 `McpState` 列**逐条一致**——
32 条 readonly 必须仍是 32 条，一条不多一条不少。这是本项唯一硬判据。

## 3. H2 · 版本号写 4 遍（P0，你点名的问题）

### 3.1 现状

```xml
<!-- b-Code-Studio/Studio.csproj -->
<Version>2.4.2</Version>
<AssemblyVersion>2.4.2.0</AssemblyVersion>
<FileVersion>2.4.2.0</FileVersion>
<InformationalVersion>2.4.2</InformationalVersion>
```

`b-Code-AppShell/src/App/App.csproj` 同样 4 行（`0.4.4`）。**升一次版本要改 8 处、且两种写法**
（带 `.0` 与不带）。

### 3.2 事实：后三行全是冗余

.NET SDK 的默认推导链：

| 属性 | 默认值 |
|---|---|
| `Version` | `$(VersionPrefix)` |
| `AssemblyVersion` | `$(Version)` 去预发布后缀，补足四段 |
| `FileVersion` | `$(AssemblyVersion)` |
| `InformationalVersion` | `$(Version)` |

即：**只写 `<Version>2.4.2</Version>` 一行**，另外三个会自动得到
`2.4.2.0` / `2.4.2.0` / `2.4.2`——与当前手写值**完全相同**。

### 3.3 方案

```xml
<Version>2.4.3</Version>
<!-- AssemblyVersion / FileVersion / InformationalVersion 由 SDK 从 Version 推导，不再手写 -->
<IncludeSourceRevisionInInformationalVersion>false</IncludeSourceRevisionInInformationalVersion>
```

`IncludeSourceRevisionInInformationalVersion=false` **必须保留**——它阻止 SDK 给
`InformationalVersion` 追加 `+<git sha>`，而 `AppIdentity` 依赖该值解析版本
（`informational.Split('+', 2)[0]` 是兜底，但保持干净更好）。

### 3.4 验收（必须实测，不能只靠推导）

改后立即核对：

```
EXE ProductVersion / FileVersion 与改前逐字节相同
AppIdentity.Current 的 Version / FileVersion / InformationalVersion 与改前一致
PromptGovernanceSuite 中 4 条身份断言全绿
```

> 本项虽小，但直接影响发布身份。**必须实测，不能推定**。

## 4. H3 · 目录名绕过 `AppPaths`（P1）

### 4.1 现状：已有单一真值，却无人用

`AppShell.Services/AppPaths.cs` 已定义：

```csharp
Root / DataDir / LayoutDir / WorkspaceDir / LogsDir
```

但实际代码在**重新拼**：

| 目录 | 散布 | 问题 |
|---|---|---|
| `"Modules"` | Studio 1 + WiringSuite 1 + ShellWindow 1 | **`AppPaths` 根本没有 `ModulesDir`** |
| `"panels"` | Studio 2 + AppShell演示 1 + PromptGovernanceSuite 1 | **`AppPaths` 没有 `PanelsDir`** |
| `"workspace"` | BuiltinCommands 2 + ShellWindow 1 | `WorkspaceDir` **存在但没被用**，各处 `Path.Combine(dataDirectory, "workspace")` |
| `"data"` | BranchTreeService / FormatInventoryService / StartupMigrations | `DataDir` **存在但没被用** |

### 4.2 方案

1. `AppPaths` 补 `ModulesDir`、`PanelsDir`（与既有五个同级，同样在构造时 `CreateDirectory`）；
2. 全部 `Path.Combine(xxx, "workspace"/"data"/"Modules"/"panels")` 改用 `AppPaths` 属性；
3. `ShellWindow`/`BuiltinCommands` 目前只拿到 `string dataDirectory`——
   **本版不改其构造签名**（那会波及派生应用），改为在内部由 `dataDirectory` 构造一个
   `AppPaths` 或补一组 `static` 路径助手。**取哪种由施工者定，但不得再散写字面量**。

> **注意**：`AppPaths` 构造函数会 `CreateDirectory`，新增两个属性等于新增两个空目录。
> 实际这两个目录本来就会被创建（模块与面板同步时），**属行为等价**，但需在冒烟中确认。

## 5. H4 · 数据表名散布 50 处（P1）

| 表 | 出现次数 |
|---|---|
| `mcp_prompt_proposals` | 12 |
| `tool_registry` | 10 |
| `mcp_history` | 9 |
| `mcp_descriptions` | 8 |
| `branch_notes` | 7 |
| `push_history` | 4 |

**全仓无任何表名常量**（`grep "const string Table"` 零命中）。

### 方案（克制版）

只抽**表名常量**，不动 SQL 语句结构：

```csharp
// 就近原则：表名常量放在拥有该表的类里，不新建集中式常量文件
public sealed class HistoryRecorder
{
    public const string TablePushHistory = "push_history";
    public const string TableBranchNotes = "branch_notes";
    ...
}
```

> **不做**「SQL 语句集中化」或「引入 ORM」——那是重写不是整备，且会打破
> 「各表时间戳格式保持不变」等既有对外行为约束（见 25 号文档 R1）。
> **就近定义**也符合本版「不制造跨文件横跳」的原则：改表名时在**同一个类**里改。

## 6. H5 · 设置键裸字符串（P1）

现有 **15 个 `const string Key*` 常量**（`ProjectService.KeyBareRepo` 等），说明约定已存在，
但这几个漏网：

| 键 | 散布 | 现状 |
|---|---|---|
| `workspace.root` | Studio 1 + AppShell演示 1 + BuiltinCommands 1 | **跨 3 文件裸字符串** |
| `console.history` | ShellWindow 1 + Example 文本 2 | 无常量 |
| `console.buffer` | ShellWindow 1 | 无常量 |

**方案**：按既有约定补 `const string Key…`，定义在**读取方所属的类**里
（`workspace.root` → `WorkspaceService` 或 `BuiltinCommands`；`console.*` → `ConsoleView`）。
`Example` 文本中的键名**保持字面量**——那是给用户看的示例，不是代码引用。

## 7. H6 · `BuiltinDomains` 手写清单脱钩（P2）

`Git/ToolManifest.cs` 手写 20 个内置域，用途是「工具模块名不得与内置域冲突」。

**实测：该文件完全不引用 `CommandRegistry`**——清单与实际注册表脱钩。
实际注册的域含 `motor`/`sample`/`test`（演示与冒烟遗留），手写清单里没有；
手写清单里的 `help`/`history`/`cls` 是无域命令，不是域。

**方案（择一，施工者定）**：

| 选项 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 改为**从注册表实时推导**：`registry.All().Select(c => c.Name.Split('.')[0])` | 需给 `ToolManifestLoader` 传入注册表访问器 |
| B | 保留手写，但加**启动期自检**：清单与注册表不一致时 `log.Warn` | 改动小，但仍需人工维护 |

> 若选 A，注意冲突检测发生在**清单加载期**，而模块指令是**注册后**才进注册表——
> 需确认时序：应取「内置域」快照（模块加载前的注册表），不是全量。

## 8. H7 · 窗口 ID 字面量（P2，本版建议只做标注）

| ID | 出现 |
|---|---|
| `table` | 22 |
| `mcp` | 21 |
| `history` | 8 |

## 10. 边界与克制原则（**给施工者的硬约束**）

1. **不新增扩展接口**。本版目标是**减少**开发者必须知道的挂点，不是增加。
   `Readonly` 字段是把已存在的外部挂点**收回**到描述符，属净减少。
2. **就近定义，不建集中常量文件**。表名常量放拥有该表的类、设置键常量放读取方的类——
   建一个 `Constants.cs` 会制造新的跨文件横跳，与本版目标相反。
3. **不动 SQL 结构、不引 ORM、不改表**。25 号文档已确立「各表时间戳格式属对外行为」。
4. **不做窗口 ID 常量化**（§8）。收益低、误伤高，明确放弃。
5. **不动 `versions/`**。
6. **每步跑冒烟**。本版全部是等价改写，冒烟红 = 改错，不存在「预期内的失败」。

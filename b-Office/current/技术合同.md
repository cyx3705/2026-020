### REQ-028 LFS 规则页：两行控制面板加三列表格（5.12.0）

- `LFS 规则` 分支是 `stack`：控制面板 `janus-lfs`（`rows` ≤ 2，`mode=even`）与表格 `lfs-files`。
- 面板六格都是 `textbox` + `mode=select` + `optionsSource`（`janus.ui.data view=lfsstat item=<格>`），
  取数只回一行 `value`，选择框自动选中它——Aurora 面板没有取数文字控件，用户选定这样凑（DEC-033）。
  取数参数引用 `janus.project` 与 `janus.section` 两个通道：选择框只在引用的通道变化时重取。
- `lfs-files` 三列 `path` / `size` / `op`；`op` 带 `cellAction=janus.lfs.toggle`，动作参数
  `decision={next}`，`next` 由投影算好（未决定 → lfs，LFS → ignore，不纳入 → lfs），不显示。
  决定为「—」（已被入库规则排除）的行不列。行操作 `janus.lfs.uselfs/untrack/clear` 删除。
- 已知限制：`janus.ui.lfsdecide` 只能重取 `lfs-files`（`aurora.ui.refreshdata` 够不着面板），
  面板的决定计数要等下一次换项目或切子页。
- 验收：见验证合同 5.12.0 一节。

### REQ-027 LFS 规则独立成页；不到 100MB 的文件一律不走 LFS（5.11.0）

- 子页面由三个变为四个：`入库规则`（`rule-list`，`view=excludes`，不带项目名）、
  `LFS 规则`（`stack`：`lfs-summary` + `lfs-files`，`view=lfssummary` / `lfs`，带选中项目名）、
  `分支历史`、`GitHub`。`lfs-files` 只列 ≥100MB 的文件，小指针只在汇总里计为违规。两张 LFS 表共用一次检查（`UiLfsProjection`，15 秒缓存，切页与行操作先作废）。
- 规则（DEC-032）：走 LFS 的只能是 ≥100MB 的具体文件，只能写在 `.gitattributes` 的
  `# HistoryJanus lfs begin/end` 托管块里，条目带前导 `/`、通配字符转义、含空白时加引号。
  托管块之外任何 `filter=lfs` 都算违规，嵌套 `.gitattributes` 同样检查。
- 「不再纳入 git」写在 `.gitignore` 的 `# HistoryJanus oversize begin/end` 托管块，
  **总是挪到文件最后**——排在 managed 块的 `!z-*/**` 豁免之前会被盖掉。`z-*` 快照文件不允许选它。
- 决定只写托管块；落进索引在下次提交：`LfsRuleService.StageDecisionsAsync` 对「不纳入 git」且仍被跟踪的
  `git rm --cached`，对「LFS」且索引里还是普通 blob 的 `git add --renormalize`。均不改写历史。
- 提交前门：`CheckPolicyAsync` 发现托管块外 LFS 规则，或托管块里的文件本机有实体却不足 100MB，
  拒绝提交并指向 `janus.gitrule.lfsrepair`。本机只有指针的文件是唯一例外（转不回）。
- 提交时 ≥100MB 文件：已定「不纳入 git」的跳过；`git check-ignore` 命中的跳过；
  其余未走 LFS 的照旧弹窗，同意后 `RecordLfsAsync` 写托管块。`WorktreeLfsHelper.SetupLfsForFilesAsync`
  （`git lfs track`）删除。
- 修复 `RepairAsync`：暂存区非空或 `.gitattributes` 有未提交改动时拒绝；去掉托管块外 LFS 属性但保留
  `-text` 等其余属性，只剩模式的行删除；上一轮「极保守」说明整段换成现行规则；缺实体的小文件逐个
  `git lfs pull --include`；小文件按 `PushChunkBudgetBytes`（300MB）分批 `add --renormalize`
  （NUL 分隔 UTF-8 pathspec 文件）并各自提交；结束后复查仍为指针的小文件数。
- `formatOnly`：只删模式带未转义 `*` / `?` / `[` 的 LFS 规则，精确路径与「极保守」说明保留。
  转回哪些文件不自己推算：改写落盘后用 `git check-attr -z filter`（路径走参数、每批 100 个）
  找出不再被覆盖的小指针；预演同样落盘，结束后写回原文。合规文件原样交回，不因规整空行产生提交。
- 命令：`janus.gitrule.lfs` 的 `Data` 改为 `LfsInspection`；新增 `janus.gitrule.lfsset`、
  `janus.gitrule.lfsrepair`（Ask）与 UI 行操作落点 `janus.ui.lfsdecide`。运行时命令 51 → 54。
- 验收：见验证合同 5.11.0 一节。

### REQ-019 远端分支要能同步到本地并画进图谱（5.10.0）

- 刷新与分支历史两条链路的 `git fetch` 改用 `ProjectService.AllHeadsRefspec`
  （`+refs/heads/*:refs/remotes/origin/*`）并带 `--prune`。
  5.9 及以前两处都在命令行上写死 `+refs/heads/main:refs/remotes/origin/main`；
  **命令行上的显式 refspec 会顶掉 `remote.origin.fetch` 里配好的 `refs/heads/*`**，
  于是除 main 外的远端分支一条都到不了本地。现象是「别人在 GitHub 上推的分支，
  同步过了本地也没有这段历史」——2026-028-LocalChat 的 `feature/bridge-confirmation-guard` 实证。
- `--prune`：远端删掉的分支若不清理，`refs/remotes/origin/*` 会永久留一条指向已不存在
  分支的引用，比不取更容易骗人。取回的只是跟踪引用，不动本地分支与工作树。
- 图谱泳道筛选（`GraphService.SelectParallelCandidates`）取消 `ai/<项目名>/` 前缀这道门槛：
  **主线以外的每一条分支都进平行泳道**，本地的与远端跟踪的同名时合成一条、本地优先。
  `ai/` 前缀只再用于决定泳道**类别**（`BranchKind.AiWork` 对 `BranchKind.Parallel`），
  不再决定去留——分支是谁开的、叫什么名字，不该决定它算不算这个项目的历史。
  继承关系一视同仁，由 `BuildRelationsAsync` 按与主线的 merge-base 算基线。
- `origin/HEAD` 这类符号引用排除在外：它没有自己的历史，画出来是主线的一份重影。
- 验收：见验证合同 5.10.0 一节。

### REQ-022 同步把远端分支落成本地分支（5.10.0）

- REQ-019 让远端分支的**历史**到了本地（`refs/remotes/origin/*`），但 `git branch` 里仍然
  没有它们：要检出、要比较、要开工作区，还得自己先敲一遍。`ProjectService.SyncAsync`
  在主线 `merge --ff-only` 之后调 `RemoteBranchSync.MaterializeAsync` 补这一步。
- 三条硬规矩，写在 `RemoteBranchSync` 的类型注释里：
  1. **只快进，不合并、不改写**。本地领先或已分叉的分支一律跳过并报出原因——
     那是人做过的事，自动化不该替他决定怎么并。
  2. **被任何工作树签出的分支不碰**（读 `git worktree list --porcelain`）。
     AI 工作区是活的检出点，在它背后挪 HEAD 会让那个工作区凭空变成「有一堆未提交改动」。
  3. **主线不走这里**，`origin/HEAD` 这类符号引用也不落地。
- 新建用 `git branch --track`，顺带把上游设成 `origin/<名字>`；快进用带旧值的
  `git update-ref`——读到差距与真正写入之间若有别人动过这条分支，比较失败即放弃，不覆盖。
- 生命周期判定跟着改：main 两端一致、但远端还有本地未建的分支时，状态是
  `Behind` / 动作「同步」，而不是「归档」。**归档只保留 z/Z 文件夹**，此时说
  「本地与远端已验证一致」是不实的——本地压根没有那几条分支。主线自身领先/落后/分叉时
  仍以主线的动作为准，分支数只作为消息后缀补充（`BranchNote`）。
- 分支未能全部落地时 `SyncAsync` 返回失败并停在「同步」，不写已验证 SHA。
- 验收：见验证合同 5.10.0 一节。

### REQ-020 提交差异弹窗里的文件名是中文，不是三位八进制码（5.10.0）

- `GitRunner` 对**每一条** git 命令统一带 `-c core.quotepath=false`。git 默认
  `core.quotepath=true`，凡是输出路径的命令（`status` / `diff` / `ls-files` / `for-each-ref`）
  都会把非 ASCII 字节写成 `\344\270\255` 这种三位八进制码；本库项目名与文件名大量是中文，
  于是提交前的差异弹窗里整排文件变成看不懂的数字串。该开关只影响 git **打印**路径的方式，
  不影响匹配、暂存与提交。
- `GitPath.Unquote` 兜住剩下那一类：`core.quotepath=false` 只管非 ASCII，路径里带引号、
  反斜杠或控制字符时 git 仍会把整条引起来并做 C 风格转义。只还原「整条被引起来」这一种形状，
  没被引起来的原样返回，绝不猜测。`ProjectService.ReadScopeAsync` 的未跟踪文件清单经它还原。

### REQ-021 全库刷新的并发与归档项目豁免（5.10.0）

- `MaxConcurrentFetches` 由 6 提到 **16**。这些 fetch 几乎不传字节，单次开销是一趟 ssh
  握手往返（本机实测约 4 秒），**总时长由并发度决定而非带宽**：本机 47 个项目实测
  并发 6 为 31 秒、16 为 12 秒，且无一失败。再往上收益递减，而真有对象要传的项目
  会开始互相抢链路（本机链路大传输本就易断），因此停在 16。
- 已归档的项目不占限流名额：它们本地只剩 z/Z 文件夹，读数是一条现成的归档记录，
  一次 git 都不跑；混在同一个信号量里排队只会让后面真要 fetch 的项目白等。
  归档项目与联网项目并行算，结果按入参次序合回去。
- `ListWorktreesAsync` 对同一个项目目录不再连读两遍 z/Z 目录。

### REQ-014 提交前看差异，并可就地丢弃脏工作树（5.9.0）

- `janus.proj.diff`（只读）读脏工作树相对 **HEAD** 的差异：已暂存与未暂存一起算，
  否则预览会漏掉人上一步刚 `add` 的内容。未跟踪文件只列路径，不铺内容。
  正文超过 `ProjectService.DiffBodyLimit`（200000 字符）时截断并明说截断。
- `janus.proj.discard`（`Level=Ask`）丢弃脏工作树：`git reset --hard HEAD` 加 `git clean -fd`。
  **不加 `-x`**：被 .gitignore 排除的内容（bin/obj、venv、node_modules）不是「本次的改动」，
  删掉只会让人重跑一次构建。受保护项目拒绝执行。
- 两条共用同一套范围解析（`ProjectService.ResolveScopesAsync`）：预览里看到几个仓，
  丢弃就动几个仓。各自解析范围的话，人看到的和实际删掉的迟早会对不上。
- 界面链路：`janus.ui.projectaction action=提交` 先取差异，再弹一个 `kind=content` 弹窗——
  正文是完整差异，下方是「提交到本地仓库 / 删除本次脏工作树（不可撤销）」两个出路，
  默认落在取消。工作树干净时不弹窗，直接返回「没有要提交的内容」。
  需 **Aurora ≥ 1.24.0**（content 弹窗带 options，Aurora REQ-UI-123）。
- 模块侧参数编码统一改用 `CommandParser.QuoteArg`：原先自写的那份只在有空格或引号时加引号、
  且不转义反斜杠，差异正文里的 Windows 路径和 `\ No newline at end of file` 会把指令拼散架。
- 验收：见验证合同 5.9.0 一节。

### REQ-016 规则表的 LFS 行改为本仓实际走 LFS 的文件（5.9.0）

- `janus.gitrule.lfs`（只读）按项目返回 `git lfs ls-files -s` 的结果；本机没装 git-lfs
  与「装了但一个文件都没走 LFS」分开报，两者不是一回事。
- `janus.ui.data view=excludes` 因此新增 `name` 参数，`rule-list` 的取数参数改为
  `{selection.janus.project.name}`——换项目要重取。原先那一行写的是一条对每个仓都一样的策略
  （「单文件超过 100MB 转 LFS 指针」），看完仍不知道自己这个仓有没有 LFS、有哪几个。
  策略本身没变，它属于提交链路的逐个确认，不属于规则面。

### REQ-017 切到子页面就刷新，取消两个刷新按钮（5.9.0）

- 「刷新规则」「刷新 GitHub」两个按钮及动作 `janus.rules.refresh` / `janus.github.refresh` 删除；
  `janus.ui.refreshrules` 由 `janus.ui.sectionenter` 取代。
- 子页面选项框加 `commitAction = janus.section.enter`，切换时把标题带过去，
  由 `janus.ui.sectionenter` 按节点刷 `rule-list` / `history-rows` / `github-rows`。
  **按节点、不按页**：三支同处一页，按页刷会把没人看的那两支也跑一遍。
- 为什么必须由模块补这一手：Aurora 的 switch 在建页时一次建好三支，切走再切回来是
  同一个控件实例（刻意不重建，为的是保住滚动位置与选中行），因此切回来不会重新取数。
- 已知代价：**首次**切进某一支会取两次数——挂上可视树触发一次，commitAction 再触发一次。
  用一份「哪几支进过」的状态去省掉那一次，代价是这份状态与页面重建的时机必须始终对齐，
  对不上就是漏刷；一次多余的只读取数比那个风险便宜。

### REQ-018 归档项目照实说「已归档」，拉取分段可续（5.9.0）

- `ProjectService.ResolveWorktree` 在目录还在、却已不是 git 仓时查生命周期记录：
  有归档时间就报「项目已归档」并给出取回方式，不再一律报「未找到已登记项目」。
  它是所有读路径的唯一收口（图谱、分支历史、提交、推送、规则、meta），改一处全都对。
  `RefreshProjectAsync` 的归档判定不再要求目录存在：一个 z 都没有的归档项目目录可能被手工清掉，
  那时它仍是「已归档」，不是「读不了仓库」。
- `janus.proj.pull` 由一次性 `git clone` 改为 `ArchiveCloner`：浅克隆（深度 250）→ 反复
  `--deepen=250` → `--unshallow`，每段可重试 3 次，全程 `--progress` 经 `ctx.Progress` 进控制台。
  依据与推送侧 `PushChunkBudgetBytes` 同源：本机链路超过约 300MB 的单次传输会断，
  实测症状是 `fetch-pack: unexpected disconnect / early EOF / invalid index-pack output`。
  只重试链路中断类失败；服务端拒收重试多少次都是同一个结果，重试只会推迟人看到真正的原因。
- 分段只解决「传着传着断了」，解决不了「一个字节都没传出去」。2026-09-19 01:06–01:14
  实测本机到 GitHub 的 SSH 两个口（22 与 443）都被重置，`git@github.com:...` 在握手阶段
  就挂掉，连续三次拉取全部失败——每一段都是同一个握手，分段与重试都救不回来。
  这种断是**间歇**的（同日 01:31 SSH 自行恢复），所以它不是「改一次 origin 就完了」的
  一次性故障，而是随时会再来一次、且只能在发生的当时自动绕过去的东西。
  因此第一段浅克隆在认出**链路级** SSH 不通之后（`Connection reset/closed/refused by`、
  `kex_exchange_identification`、`Could not resolve hostname`、`Network is unreachable`），
  把地址换算成同一个仓库的 HTTPS 再试一次；同一时刻 HTTPS 是通的。
  `Permission denied (publickey)` 不在其中：那是钥匙不对，不是路不通，换条路只会把
  一个能一眼看懂的原因换成一个看不懂的。
- 换算只认带点的主机名：Windows 本地路径（`C:\OneHistory\...`）长得就是 scp 形式，
  少这一条，一个本地裸仓会被当成主机名为 `C` 的远端换成 https（合同测试锁住这一条）。
  换路只发生在第一段：克隆出来的仓 `origin` 就是走通的那个地址，加深、LFS 以及该项目
  以后的取放都沿用它，成功消息写明「本次经 HTTPS 取回，origin 已指向 …」。
  归档记录里的 `Remote` 不动，下次归档会照实记下当时的 origin。
- LFS 内容在克隆期间跳过（`GIT_LFS_SKIP_SMUDGE=1`），完成后单独 `git lfs pull`。
  它失败**不算拉取失败**：git 历史与工作树此刻已完整，为一次重试回滚整个项目不划算。
- `GitRunner` 统一设 `GIT_TERMINAL_PROMPT=0`，并在环境未定义时给
  `GIT_SSH_COMMAND="ssh -o BatchMode=yes"`（`core.sshCommand` 仍优先）。窗口是隐藏的，
  git 一旦在终端上提问就没人看得见，进程停在那儿不动——表现为「点了拉取以后什么都不发生」。
  凭据助手有自己的界面，不受影响。
- 生命周期刷新限流到 `MaxConcurrentFetches = 6`。此前一次刷新同时开四十多条 ssh 传输，
  本机链路撑不住，每条都变慢且偶发中断；同时有拉取在跑时它会被挤到近乎不动。

### REQ-025 宿主 5.4 确认通道（5.8.0）

ProjectService 执行中途的确认改调 `CommandBus.RequestConfirmation`，不再直接读宿主 `Bus.Confirmation`：
确认交给宿主登记的唯一前端（Aurora），没有前端时一律拒绝，与 Level=Ask 闸口同一真值。

### REQ-002 业务能力

- 模块提供项目列举、创建、改名、提交、推送、继承树命令、Meta 文件夹浏览、分支历史、回滚和 Git 文件规则治理，
  以及 3.9.0 起的只读分支 DAG；继承树与分支历史不再提供独立页面。
  DAG 由 `graph` 窗口承载，并入宿主控制台标签组；主线是该项目仓内的 `main`，范围天然是本仓，
  泳道按平行分支（主要是 `ai/<项目>/`）动态增加。已合并平行分支保留合并前历史行，右侧不再画端点；
  `--no-ff` 合并后即使分支 ref 已删除，仍从第二父还原该行（DEC-013 / DEC-015）。
  每个提交的横坐标由其 Git 父边决定（取全部已布局父节点与同泳道前一节点的右侧一个标准间距），
  不按全局时间轴铺开后再整体平移整条泳道。因此开放分支的首节点紧邻分叉点右侧，已关闭历史分支的
  末节点紧邻消费它的 merge 左侧；多提交历史行不得越过分叉点，也不得被跨分支时钟拉到远离接合点的位置（DEC-016）。
  平行泳道优先占用靠近主线的空行：不相交的已合并历史行共用最近空行，只有同一水平区间已被占用时才下移（DEC-018）。
- **指令分类（5.0.0，DEC-012 / DEC-013 / DEC-015 / DEC-022 / DEC-023）**：`janus` 域业务类为 `proj`、`gitrule`、`history`、`github`、`graph`；
  目标 39 条业务命令 + 8 条 Aurora UI 命令 + 宿主投影的只读命令 `janus.status`，运行时 48 条，
  实现与本合同同版本落地。`gitrule` 类只剩 `list` 与 `excludes` 两条（DEC-023）。一律三段式 `janus.<类>.<方法>`（3.5.0 DEC-007 确立）。
  模块不注册诊断或自动化辅助指令：日志承压使用宿主 `vulcan.log.flood`，
  不在业务模块内重复实现。`aiworktree` 类预留给后续版本，4.0.0 不得注册。
- Aurora 通过 `janus.ui.describe` 获取页面描述协议 V1，通过 `janus.ui.actions` 获取动作声明，并通过 `janus.ui.data` 与 `janus.ui.graphnode` 获取数据；跨 HTTP 的结构化结果必须先从 JSON 投影为页面模型。
  页面弹窗只允许调用 `aurora.ui.dialog`，不得 `new Window` 或 `MessageBox.Show`（DEC-025）。
  写操作确认仍只走 `ConfirmPrompt`，页面不得重复弹出。
- **Git 执行等待（3.7.0，DEC-010）**：产品 `GitRunner` 不设置墙钟超时；`add`、`commit`、
  `push`、`fetch` 和其余 Git/Git LFS 操作必须等待进程自行结束，只响应宿主传入的取消令牌。
  GitHub 连接诊断的用户指定超时和验证套件的挂死检测不属于产品 Git 操作，继续保留。
- **文件规则只有一份全库清单（5.0.0，DEC-023）**：规则页是设置 `proj.excludesuffixes`
  的编辑器，不是按项目的状态；没有草稿、没有离页保存时机、没有并发保存协商。
  写入必须经 `janus.gitrule.excludes` 走宿主确认，页面不自行弹窗也不直接写设置。
- 卸载或热重载后不得残留窗口或旧命令注册。

### REQ-004 项目总览显示工作树状态

- 项目总览以 `janus.proj.list status=true` 列出编号项目，并行执行各工作树的只读
  `git status --porcelain=v1 --untracked-files=all`，同时覆盖已跟踪修改和未跟踪文件。
- 返回的每个 `WorktreeInfo` 以可空 `IsClean` 表示状态：`true` 为干净，`false` 为有改动，
  `null` 为目录缺失、Git 失败或取消导致的未知；`WorktreeStatusMessage` 提供悬停诊断。
- 项目总览使用 `✓` 表示干净、`×` 表示有改动、`?` 表示未知；点击“刷新项目”必须重新读取状态。
- 单个工作树状态检查失败不得阻断其余项目展示，也不得把未知猜测为干净或有改动。
- `status` 默认 `false`，项目操作页等只需要名称的消费者不承担额外状态扫描。

### REQ-005 一项目一仓（4.0.0，DEC-015）

- 库根设置键 `proj.libraryroot`，默认 `C:\OneHistory\HistoryClio`。删除 `proj.barerepo`。
  旧键 `proj.worktreeroot` 仅作一次性迁移读取，不得再写入裸仓路径。
- `proj.basebranch` 键名保留，语义为**模板项目名**（默认 `0000-000-Template`），不是父 git 分支。
- `proj.protected` 保护的是项目名；默认模板项目，不再保护 `main`/`master`。
- 列举只扫库根直接子目录，名称匹配 `YYYY-NNN-*` / `0000-*`，且 `.git` 是目录；拒绝 reparse point。
- 按名字解析单个项目仓只检查库根下该直接子目录与 `.git` 目录，不得为定位一个仓而列举全库或对其它仓发 git。
- 创建从模板仓复制工作树（排除 `.git`）后 `git init -b main` 并首提交；禁止 clone。
- 图谱、历史、提交、推送、规则均对 `git -C <项目目录>` 操作；`commitall` / `pushall` 显式遍历各仓，失败隔离。
- 继承树读 `project.manifest.json` 的 `template.source`。HEAD 不是 `main` 时总览可警告，不阻断 list/commit。

### REQ-007 排除清单与提交推送链路（5.0.0，DEC-023）

- Git 文件规则的唯一维度是"是否纳入仓库"：一份全库共用清单存于设置 `proj.excludesuffixes`，
  目录项以 `/` 结尾、后缀项写 `*.xxx` 或裸文件名；含内部分隔符的目录项生成时加 `**/` 前缀，
  否则 git 只按仓库根匹配，嵌套目录会漏掉。
- 清单由**提交链路**每次幂等刷进各仓 `.gitignore` 托管块；没有任何人工下发命令。
  托管块外内容与其它块逐字保留；重复刷写不得重复生成块。
- LFS 只在提交链路触发，且只针对超过 GitHub 100MB 硬限的**具体文件**：
  弹确认→同意则按精确路径 `git lfs track`；拒绝则该仓提交判为 Rejected。
  Janus 不再按扩展名生成任何 LFS 属性。
- 推送统一经一个出口，固化 2026-08 全库首推的实测经验：
  推**显式分支名**（分支名现读，`WorktreeInfo.BranchName` 是项目目录名不是分支名；
  detached HEAD 必须给出指名错误）、`-c lfs.locksverify=false`、
  待推字节超过 `PushChunkBudgetBytes`（300MB）时按提交分批推、失败保留 git 原文。
- 已被跟踪却命中排除项的文件不自动移出索引，只在 `janus.gitrule.list` 里点名。
- 托管块尾部固定生成 `!z-*/` 与 `!z-*/**`（DEC-024）：`z-*` 正式消费快照由发布管线刻意
  入库，任何排除项都不得波及它。否定规则必须排在全部排除项之后，位置是合同的一部分。

### REQ-006 首次推送自动建远端仓库（4.1.0 DEC-019；4.1.1 DEC-020 传输；4.2.0 DEC-021 命名）

- `push` / `pushall` 推送前探 `origin`；已配置则原样推送，缺失则按需在 GitHub 上创建仓库后
  `remote add origin` 再推送，新建远端的首推带 `-u` 建立上游。
- 远端仓库名取项目编号 `YYYY-NNN`（`ProjectRepoLayout.ToRemoteRepositoryName`），不带标题部分，
  与本地目录名刻意不一致（DEC-021）；可见性由可选参数 `visibility` 决定，默认 `public`。
- 令牌只经 `git -c credential.interactive=false credential fill` 从 GCM 取用，不落盘、不新增配置项；
  API 与进程输出一律经 `GitHubRedactor.Redact` 后才进入消息与日志。
- `origin` 优先写接口返回的 `ssh_url`，接口未给时才退回 `clone_url`（DEC-020）；创建返回 422 时
  复用同名既有仓库，可见性以接口事实为准。建仓走 HTTPS token、推送走 SSH 密钥，两条凭据链路不同。
- 建仓成功但推送失败时，结果消息必须仍然点名新建的仓库，不得只回显 git 的报错。
- 创建失败不得写入 `remote`；`PushReport` 以 `RemoteCreated` / `RemoteUrl` / `RemoteVisibility`、
  `BatchPushReport` 以 `CreatedRemotes` 暴露结果，`HistoryRecorder` 同步记录仓库名与可见性。
- `ProjectService.RepositoryProvisioner` 可空；为空时退回旧行为，即没有 `origin` 直接失败。

### REQ-007 项目展示名与工作树目录同步改名（4.3.0，DEC-022）

### 关键流程

1. HistoryVulcan 从自身 Modules 目录读取 manifest 并装载 `HistoryJanus.dll`。
2. `IModuleContextAware.Attach` 使用宿主 registry、bus、settings、log 与 data directory 注册业务组合。
3. Aurora 读取 `janus.ui.describe` 与 `janus.ui.actions` 建立三个页面，再按页面数据源调用 `janus.ui.data`；图谱节点详情调用 `janus.ui.graphnode`。项目总览展示项目与状态，图谱并入控制台标签组，项目操作页提供提交、推送与治理操作。GitHub 写操作必须通过宿主命令总线执行并服从确认策略。
4. 发布管道验证源码、模块生命周期和包集合后提升到 z 级正式消费区。
5. 部署管道原子更新 UI/Service 两个模块槽，并保留上一正式部署用于回滚。

### REQ-015 三块子内容收进项目操作页，由轮换选项框切换（5.4.6）

- 目的：把 5.4.5 的底部三标签收成一页里的一个控件。标签组是**三页**，各占一条底边、
  各自还顶着一段说明文字；收进一页之后版面只剩一条选项框，三块内容拿到同一块完整高度。
- 要求（切换器并入现有控制面板）：`janus-projops` 增加第四行——
  `{ kind: "textbox", id: "section", mode: "select", channel: "janus.section",
  options: [ "Git 文件规则", "分支历史", "GitHub" ] }`（Aurora REQ-UI-045）。
- 约束（排在最后一行）：它管的是自己**下面**那块内容。排在前面的话，人得隔着三行
  项目操作才能把「转了一下选项框」和「下面变了」联系起来。
- 约束（不写 `enabledWhen`）：切页面与选没选中项目无关。按选中启停会让
  「没选项目时连看一眼 GitHub 状态都不行」。
- 要求（内容是 `switch` 容器）：`janus-sections`，`source = {selection.janus.section.value}`，
  三支的 `case` 与选项框的候选项是同一组常量（Aurora REQ-UI-046）。
- 约束（标题只写一处）：候选项与 `case` 取自同一批常量。两边对不上时**不报任何错**，
  表现是切到某一项后下面永远停在第一支——与「这一支没数据」长得一样。
- 要求（各页控件跟着自己那一支走）：「刷新规则」留在规则支的面板里，
  「刷新 GitHub」留在 GitHub 支的面板里。切到哪一支就只看得见哪一支的控件。
- 要求（刷新改为按节点）：三块同处一页之后按页刷会把没被点到的两块一起带上，
  而 GitHub 那条要探 SSH 与凭据助手。`janus.github.refresh` 改 `node=github-rows`；
  规则支经 `janus.ui.refreshrules` 按节点刷 `rule-list`（5.8.1 起 `rule-state` 已删除，见 REQ-026）。
- 要求（删掉页面顶部的说明段落）：四页顶上那几段「这一页是干什么的」全部删除，
  面板内的说明文字同样删除。它们占的是版面，给的是一次性的信息——
  每个打开这一页的人都要重新翻过去一次，而其中内容属于文档。
- 附带（内边距不再由 Janus 操心）：模块页贴着窗格边框画的问题在 Aurora REQ-UI-047 修掉，
  描述里没有、也不需要任何对应字段。
- 验收：`ProjectOperationsPanelContractTests` 的
  `TheThreeSectionsAreFoldedIntoTheOperationsPageBehindOneOptionBox`（含「候选项与 case
  逐字相等」这一半）、`NoPageStillCarriesAPreambleParagraph`、
  `TheRefreshButtonsActuallyRefetchTheirOwnNodes`。
- 依赖：Aurora ≥ 1.8.17。低于该版本时 `channel` 与 `switch` 都不被认识——
  选项框变成一个普通的选择框，`switch` 渲染成一块「该组件待交付」的占位牌。

### REQ-014 项目操作页是一块控制面板（5.4.5，5.4.6 增至四行）

- 目的：选中一个项目，就能对它改名、以它为模板新建、提交和推送——不必再把项目名手打一遍。
- 背景（本轮实测的两处故障）：
  - `projops` 此前写的是页面级 `input` + `button`。这三种节点在 Aurora 1.8.14 已退役，
    真机上渲染成三块写着原因的牌子——**这一页没有一个能点的东西**。
  - `overview` 的表格塞在 `stack` 里，撑满整页且没有纵向滚动条。
    成因在 Aurora 侧（`stack` 曾是 StackPanel，以无穷高量子元素），已由 Aurora REQ-UI-042 修掉。
- 要求（页面结构）：`projops` 的内容是**一块**控制面板 `janus-projops`，
  四个声明行（Aurora 协议 V3 / REQ-UI-060）。5.4.5 是三行加一段页首说明；
  5.4.6 删掉说明、增加第四行子页面切换器（REQ-015）；
  5.4.7 随 Aurora 1.9.2 把 `widgets` 改成 `rows`：

  前三行走**可变宽度**，中间那个文本框写 `flex: true` 吃掉余量。
  不写 `flex` 的话可变的会是最右边那个按钮，于是输入框停在最窄宽度、
  按钮被拉成一条横杠——版面上一眼看得出，但没有任何一处会报错。
  第四行走**均布**：它只有一个元素，铺满整行读起来才像一个独立的切换器。

  1.9.2 之前这里是一个三列共享的 Grid，三行的标签列、控件列、按钮列互相对齐得像张表——
  而这三行本来就没有对齐的理由，对齐的代价是最长的那个按钮把另外两行的输入框一起挤窄。

  | 行 | 标签 | 控件 | 按钮 |
  |---|---|---|---|
  | 1 | 项目名 | `project-name`，跟随选中项目，可就地改成新名字 | 改名 |
  | 2 | 新项目名 | `new-project` | 新建（以第 1 行的项目为模板继承） |
  | 3 | 提交描述 | `commit-message` | 提交当前项目 / 推送当前项目 |
  | 4 | 子页面 | `section`，轮换选项框，切换下方内容（5.4.6，REQ-015） | — |

- 要求（接线走选择通道）：`overview` 的项目表声明 `channel = janus.project`；
  面板的 `project-name` 用 `follows` 跟随它的 `name` 列，四个按钮用
  `enabledWhen: { selected: janus.project }` 启停。**页内节点 id 跨不过页边界**——
  表在中央页、面板在左侧页，两页各渲染一次，只有界面级的通道名跨得过去。
- 要求（两个占位符命名空间不能混）：动作参数里「改谁」取 `{selection.janus.project.name}`，
  「改成什么」取 `{project-name}`。跟随框一开始等于选中行，人改过之后就不再相等——
  两边都从输入框取的话，改名会把项目改成它自己：指令成功、界面无异常、什么都没发生。
- 约束（不得使用 `required`）：这条本仓先立、Aurora 后收。面板的必填校验当年是**全局**的，
  任何一个必填框为空，面板上每个按钮都拒绝执行——把「新项目名」标成必填会连带锁死
  「改名」和「提交」，而报出来的错说的是「新项目名为必填项」，看上去与改名毫无关系。
  Aurora 1.9.2（REQ-UI-060）把这个字段整个退役了，本条因此转为**回归闸**：
  再写它不会报错，只会被静默忽略，那正是最难发现的一类不一致。
  参数缺失交给各条指令自己的 `Required` 去报。
- 约束（不新增后端指令）：四个动作分别落到既有的 `janus.proj.rename` / `create` /
  `commit` / `push`。本轮只改注册，业务面一个字没动。
- 要求（三块底部内容改为标签组）：**5.4.6 已由 REQ-015 取代**——三页收进 `projops`，
  由 `switch` 容器切换。5.4.5 的原文保留在此作为沿革：Git 文件规则 / 分支历史 / GitHub
  注册为三个 `side=bottom` 页面，由停靠层并成一个标签组；当时不用 `toggleGroup`，
  因为它是 Aurora 的缺件，照写只会得到三块占位牌。
- 要求（会跑 Git 的取数一律按单个项目）：`history` / `graph`（5.8.1 前还有 `rulestate`）的取数参数
  都写 `name = {selection.janus.project.name}`，缺 `name` 时 `janus.ui.data` **直接拒绝**，
  不退化成扫全库。落地状态每个项目要跑两条 `git ls-files`，全库一遍是 90 次进程启动——
  那不该由「打开一个页签」触发。排除清单本身只读设置，因此不带 `name`，开页即出。
- 要求（刷新按钮要真的刷）：「刷新规则」「刷新 GitHub」落到 Aurora 的取数刷新台账。
  5.4.4 之前它们绑的是业务指令，指令确实跑了、界面上那张表一动不动——
  「点了有反应」和「点了有用」是两回事。5.4.5 按 `page=` 刷，5.4.6 起改为按 `node=`
  点名刷（REQ-015）。
- 附带修正：图谱此前固定取项目清单的**第一条**，无论在总览里选了谁画的都是同一个项目。
  不报错，只是一直不对。改为跟着选择通道走。
- 验收：`ProjectOperationsPanelContractTests` 逐条核对通道、面板的四个声明行与行模式、
  只有项目名跟随、四个按钮都有启停、无 `required`、四个动作的参数取向，
  外加一条兜底（按钮引用的动作都存在、占位符都指得着东西）与一条
  「不得再出现退役节点 / 退役字段」。
- 依赖：Aurora ≥ **1.9.2**（REQ-UI-060 面板的行是一等结构）。
  这是一条**硬**依赖，不是「低版本少点效果」：1.9.2 之前的 Aurora 只认 `widgets`，
  拿到只写 `rows` 的声明会得到一块没有任何小组件的面板。
  更早的下限仍然记在这里备查——REQ-UI-041 选择通道、REQ-UI-042 栈内让位（≥ 1.8.16）；
  低于那一版时 `channel` / `follows` / `enabledWhen` 会被当作未知字段忽略，
  表现为按钮常亮、跟随框不填，**不会报错**。

## 场景页面注册（5.7.1）

REQ-SCENE-REG：页面显式声明 `scene=HistoryJanus`，注册初值只用于本模块场景。用户保存的各场景完整布局（包括分栏、位置、比例和隐藏状态）优先；模块刷新不得主动打开其他场景的页面。需要 Aurora 1.21.1 的场景注册隔离。

# HistoryJanus 技术合同

## 现行需求

### REQ-001 宿主化运行（5.6.0 当前版本；Aurora 描述化页面）

- Janus 必须作为 `HistoryJanus` 模块由 HistoryVulcan 加载，不创建独立应用、后台服务或第二套 Shell。
- Janus 仅实现 `IModuleContextAware`，由 HistoryVulcan 5.1.2 的 `CommandRegistry` 注册业务命令和 Aurora 页面描述投影；不再注册 WPF 窗口。描述协议声明 `overview`、`graph`、`projops` 三个单例页面。Meta 文件夹浏览并入 `overview`；
  提交 DAG 由 `graph` 窗口承载，**并入宿主控制台标签组**，不占中央主窗口（DEC-013）；
  `projops` 5.4.6 起是一块四行控制面板加一个 `switch` 切换容器，Git 文件规则 / 分支历史 /
  GitHub 三块收在容器里，由面板最后一行的轮换选项框切换。
  合计**三个**页面，见 REQ-014。
- **默认落位（3.7.0；语义随 Aurora 1.18.0 更新）**：`overview` 声明 `side=center`。
  Aurora 1.18.0 起中央区分成两块——命令集独占的主文档区，以及中央工具页组；
  `overview` 落在**中央工具页组**里：位置仍在中间，身份是工具窗口，因此拖得动。
  **Janus 注册不出主页面，也不需要**（REQ-UI-083）。
  `projops` 停靠**左侧**、默认宽度占比 `0.38`。
  `overview` **不得**声明 `DefaultTabTarget`：此前它并入 Mcp 标签组，而那个窗口由
  HistoryMercury 提供，模块装载顺序不保证它先到——先到就并入、没到就回退右侧停靠，
  首次启动落位因此不确定（服务日志中的「标签组目标 mcp 不可用」）。
  中央区不依赖任何别的模块，落位才是确定的。
  3.4.0 引入、3.6.0 仍存在的独立 `github` 窗口在 3.7.0 退役（DEC-008）。
- UI 与无 UI Service 宿主都必须注册同一组 Janus 业务命令及 4 条描述化前端只读投影命令，来源统一为 `module:HistoryJanus`。
- 分段面板不得各自显示重复标题：分段按钮已给出面板名，上方选中项标题已给出当前项目，
  面板内不再重复这两项。

### REQ-002 业务能力

- 模块提供项目列举、创建、改名、提交、推送、继承树命令、Meta 文件夹浏览、分支历史、回滚和 Git 文件规则治理，
  以及 3.9.0 起的只读分支 DAG；继承树与分支历史不再提供独立页面。
  DAG 由 `graph` 窗口承载，并入宿主控制台标签组；主线是该项目仓内的 `main`，范围天然是本仓，
  泳道按平行分支（主要是 `ai/<项目>/`）动态增加。已合并平行分支保留合并前历史行，右侧不再画端点；
  `--no-ff` 合并后即使分支 ref 已删除，仍从第二父还原该行（DEC-013 / DEC-015）。
  每个提交的横坐标由其 Git 父边决定（取全部已布局父节点与同泳道前一节点的右侧一个标准间距），
  不按全局时间轴铺开后再整体平移整条泳道。因此开放分支的首节点紧邻分叉点右侧，已关闭历史分支的
  末节点紧邻消费它的 merge 左侧；多提交历史行不得越过分叉点，也不得被跨分支时钟拉到远离接合点的位置（DEC-016）。
  平行泳道优先占用靠近主线的空行：不相交的已合并历史行共用最近空行，只有同一水平区间已被占用时才下移（DEC-018）。
- **指令分类（5.0.0，DEC-012 / DEC-013 / DEC-015 / DEC-022 / DEC-023）**：`janus` 域业务类为 `proj`、`gitrule`、`history`、`github`、`graph`；
  目标 39 条业务命令 + 8 条 Aurora UI 命令 + 宿主投影的只读命令 `janus.status`，运行时 48 条，
  实现与本合同同版本落地。`gitrule` 类只剩 `list` 与 `excludes` 两条（DEC-023）。一律三段式 `janus.<类>.<方法>`（3.5.0 DEC-007 确立）。
  模块不注册诊断或自动化辅助指令：日志承压使用宿主 `vulcan.log.flood`，
  不在业务模块内重复实现。`aiworktree` 类预留给后续版本，4.0.0 不得注册。
- Aurora 通过 `janus.ui.describe` 获取页面描述协议 V1，通过 `janus.ui.actions` 获取动作声明，并通过 `janus.ui.data` 与 `janus.ui.graphnode` 获取数据；跨 HTTP 的结构化结果必须先从 JSON 投影为页面模型。
  页面弹窗只允许调用 `aurora.ui.dialog`，不得 `new Window` 或 `MessageBox.Show`（DEC-025）。
  写操作确认仍只走 `ConfirmPrompt`，页面不得重复弹出。
- **Git 执行等待（3.7.0，DEC-010）**：产品 `GitRunner` 不设置墙钟超时；`add`、`commit`、
  `push`、`fetch` 和其余 Git/Git LFS 操作必须等待进程自行结束，只响应宿主传入的取消令牌。
  GitHub 连接诊断的用户指定超时和验证套件的挂死检测不属于产品 Git 操作，继续保留。
- **文件规则只有一份全库清单（5.0.0，DEC-023）**：规则页是设置 `proj.excludesuffixes`
  的编辑器，不是按项目的状态；没有草稿、没有离页保存时机、没有并发保存协商。
  写入必须经 `janus.gitrule.excludes` 走宿主确认，页面不自行弹窗也不直接写设置。
- 卸载或热重载后不得残留窗口或旧命令注册。

### REQ-003 正式交付

- 当前模块候选位于 `z-Publish/HistoryJanus-vX.Y.Z/`；旧版本只以历史包保存在 `z-Publish/history`。
- `z-Publish` 根上除 `history/` 与当前一个版本化目录外不得再摊运行文件。
- 正式快照保存 `HistoryJanus.dll`、`HistoryJanus.xml`、`module.manifest.json`、`SHA256SUMS`，
  以及 `docs/` 中已发布 Markdown。
- 部署只把正式快照中的运行文件同步到 HistoryVulcan UI 与 Service 两个模块槽；API 文档由源码
  `b-Office/package` 编辑，由宿主 `vulcan.dev.submit` / `finish` 写入
  `z-Publish/HistoryJanus-vX.Y.Z/docs/`。跨项目读取走 `diana.docs.read domain=janus`。
  Diana 不发布。

### REQ-004 项目总览显示工作树状态

- 项目总览以 `janus.proj.list status=true` 列出编号项目，并行执行各工作树的只读
  `git status --porcelain=v1 --untracked-files=all`，同时覆盖已跟踪修改和未跟踪文件。
- 返回的每个 `WorktreeInfo` 以可空 `IsClean` 表示状态：`true` 为干净，`false` 为有改动，
  `null` 为目录缺失、Git 失败或取消导致的未知；`WorktreeStatusMessage` 提供悬停诊断。
- 项目总览使用 `✓` 表示干净、`×` 表示有改动、`?` 表示未知；点击“刷新项目”必须重新读取状态。
- 单个工作树状态检查失败不得阻断其余项目展示，也不得把未知猜测为干净或有改动。
- `status` 默认 `false`，项目操作页等只需要名称的消费者不承担额外状态扫描。

### REQ-005 一项目一仓（4.0.0，DEC-015）

- 库根设置键 `proj.libraryroot`，默认 `C:\OneHistory\HistoryClio`。删除 `proj.barerepo`。
  旧键 `proj.worktreeroot` 仅作一次性迁移读取，不得再写入裸仓路径。
- `proj.basebranch` 键名保留，语义为**模板项目名**（默认 `0000-000-Template`），不是父 git 分支。
- `proj.protected` 保护的是项目名；默认模板项目，不再保护 `main`/`master`。
- 列举只扫库根直接子目录，名称匹配 `YYYY-NNN-*` / `0000-*`，且 `.git` 是目录；拒绝 reparse point。
- 按名字解析单个项目仓只检查库根下该直接子目录与 `.git` 目录，不得为定位一个仓而列举全库或对其它仓发 git。
- 创建从模板仓复制工作树（排除 `.git`）后 `git init -b main` 并首提交；禁止 clone。
- 图谱、历史、提交、推送、规则均对 `git -C <项目目录>` 操作；`commitall` / `pushall` 显式遍历各仓，失败隔离。
- 继承树读 `project.manifest.json` 的 `template.source`。HEAD 不是 `main` 时总览可警告，不阻断 list/commit。

### REQ-007 排除清单与提交推送链路（5.0.0，DEC-023）

- Git 文件规则的唯一维度是"是否纳入仓库"：一份全库共用清单存于设置 `proj.excludesuffixes`，
  目录项以 `/` 结尾、后缀项写 `*.xxx` 或裸文件名；含内部分隔符的目录项生成时加 `**/` 前缀，
  否则 git 只按仓库根匹配，嵌套目录会漏掉。
- 清单由**提交链路**每次幂等刷进各仓 `.gitignore` 托管块；没有任何人工下发命令。
  托管块外内容与其它块逐字保留；重复刷写不得重复生成块。
- LFS 只在提交链路触发，且只针对超过 GitHub 100MB 硬限的**具体文件**：
  弹确认→同意则按精确路径 `git lfs track`；拒绝则该仓提交判为 Rejected。
  Janus 不再按扩展名生成任何 LFS 属性。
- 推送统一经一个出口，固化 2026-08 全库首推的实测经验：
  推**显式分支名**（分支名现读，`WorktreeInfo.BranchName` 是项目目录名不是分支名；
  detached HEAD 必须给出指名错误）、`-c lfs.locksverify=false`、
  待推字节超过 `PushChunkBudgetBytes`（300MB）时按提交分批推、失败保留 git 原文。
- 已被跟踪却命中排除项的文件不自动移出索引，只在 `janus.gitrule.list` 里点名。
- 托管块尾部固定生成 `!z-*/` 与 `!z-*/**`（DEC-024）：`z-*` 正式消费快照由发布管线刻意
  入库，任何排除项都不得波及它。否定规则必须排在全部排除项之后，位置是合同的一部分。

### REQ-006 首次推送自动建远端仓库（4.1.0 DEC-019；4.1.1 DEC-020 传输；4.2.0 DEC-021 命名）

- `push` / `pushall` 推送前探 `origin`；已配置则原样推送，缺失则按需在 GitHub 上创建仓库后
  `remote add origin` 再推送，新建远端的首推带 `-u` 建立上游。
- 远端仓库名取项目编号 `YYYY-NNN`（`ProjectRepoLayout.ToRemoteRepositoryName`），不带标题部分，
  与本地目录名刻意不一致（DEC-021）；可见性由可选参数 `visibility` 决定，默认 `public`。
- 令牌只经 `git -c credential.interactive=false credential fill` 从 GCM 取用，不落盘、不新增配置项；
  API 与进程输出一律经 `GitHubRedactor.Redact` 后才进入消息与日志。
- `origin` 优先写接口返回的 `ssh_url`，接口未给时才退回 `clone_url`（DEC-020）；创建返回 422 时
  复用同名既有仓库，可见性以接口事实为准。建仓走 HTTPS token、推送走 SSH 密钥，两条凭据链路不同。
- 建仓成功但推送失败时，结果消息必须仍然点名新建的仓库，不得只回显 git 的报错。
- 创建失败不得写入 `remote`；`PushReport` 以 `RemoteCreated` / `RemoteUrl` / `RemoteVisibility`、
  `BatchPushReport` 以 `CreatedRemotes` 暴露结果，`HistoryRecorder` 同步记录仓库名与可见性。
- `ProjectService.RepositoryProvisioner` 可空；为空时退回旧行为，即没有 `origin` 直接失败。

### REQ-007 项目展示名与工作树目录同步改名（4.3.0，DEC-022）

- 项目操作页第二行是当前项目名称文本框与“改名”按钮；成功后共享项目选择切到新名称并刷新项目列表。
- `janus.proj.rename name=<当前> new=<新名称>` 经宿主确认后，把已登记项目展示名与库根直接子目录同步改名。
- 一项目一仓的 Git 主线仍固定为 `main`；改名不得移动、创建或删除仓内分支。
- 受保护项目、非法项目名、越出库根直接子目录、目标目录已存在或文件系统移动失败时必须保持原目录并明确失败。
- 改名成功后继承树缓存失效，下一次读取必须从现场项目目录重建。

### REQ-016 项目生命周期状态与操作（5.5.0）

- 项目总览按脏工作树、领先/无远端、待确认/落后/分叉、已验证一致、已归档的优先级分别显示
  `提交`、`推送`、`同步`、`归档`、`拉取`；点击前必须重新 fetch 并校验当前状态。
- `同步` 只允许 fast-forward，分叉时拒绝自动 merge/rebase；两端一致后原子记录验证 SHA。
- 顶部刷新只由用户触发，不轮询、不代替同步。

### REQ-017 多个直属 z/Z 文件夹（5.5.0）

- z 级文件夹只指项目根目录下名称以 z/Z 开头且不是重解析点的直属目录。
- 总览显示数量；0 个明确提示，1 个直接打开，多个经 `aurora.ui.dialog kind=choice` 选择后打开。

### REQ-018 归档与拉取（5.5.0）

- 归档前强制 fetch，要求工作树干净、origin 可达且本地/远端 SHA 与已验证 SHA 完全一致。
- 归档以同库根临时目录事务性换入，只保留所有直属 z/Z 文件夹；失败回滚原工作树。
- 拉取先克隆临时目录，再以本地保留的 z/Z 内容覆盖远端同名内容并原子换入；失败不改变归档现场。
- 数据区仅原子保存项目名、远端、分支、验证 SHA、z 文件夹名和归档时间，不保存绝对路径。

### REQ-019 归档项目远端历史（5.5.0）

- `janus.history.list` 对归档项目通过现有 GCM GitHub 凭据分页读取远端分支历史。
- 非 GitHub origin、认证失败或 GitHub 不可用必须明确失败，不伪造本地历史；远端图谱不在本版范围。

### REQ-020 项目总览状态动作分列（5.5.1）

- z 级文件夹为 0 个时显示“无目录”，恰好 1 个时显示真实文件夹名，多个显示“n 个”；该列继续绑定打开动作。
- 状态列只显示普通文本，不绑定动作；紧邻的窄动作列绑定 `janus.project.action`，以黄色符号显示提交 `●`、推送 `↑`、同步 `↔`、归档 `□`、拉取 `↓`。
- `janus.ui.data view=projects` 增加内部字段 `statusSymbol`；空或未知生命周期动作回退为“同步”和 `↔`，命令面与确认策略不变。

### REQ-021 总览页顶栏筛选与最新优先（5.6.0）

- `overview` 页签标题为 `Janus`。这一页是模块的门面，页签上写「项目总览」等于把
  「哪个模块」让位给一句功能描述。
- 顶栏控制面板一行三件：`刷新`（原有）、`搜索` 文本框、`年份` 轮换选项框。
  搜索发 `janus.overview.query` 通道，年份发 `janus.overview.year` 通道；
  表格的取数参数按两个通道取值，通道一变 Aurora 重取，Janus 不自己写刷新。
- 搜索词匹配**项目名或任一 z 级文件夹名**，忽略大小写；年份匹配项目名开头的四位年份，
  `全部` 与空值都表示不过滤；两者求交。年份候选由 `janus.ui.data view=years` 动态给出，
  首项恒为 `全部`，其余按年份倒序。
- **筛选只作用在已经取到的那份清单上。** 表格取数参数里不再有 `refresh`：
  查询远端是「刷新」按钮的事（`janus.ui.refreshprojects` 先立一次性标志再让节点重取），
  否则每敲一个字符都会 fetch 一轮全部远端。
- 总览行序改为**最新的项目在最上面**（按项目名倒序，即按年份-序号倒序）。
  `janus.proj.list` 的输出次序不变——那是给人顺着读清单用的。

### REQ-022 分支历史子页只留四列且 HEAD 置顶（5.6.0）

- `分支历史` 子页的列为「时间 / 标记 / 远端 / 说明」。去掉「提交」与「作者」两列：
  短 sha 在这一页没有可点的去处（看单次提交走分支图谱），作者在单人仓里每行都一样，
  两列合起来吃掉 180px，把真正要读的「说明」挤成一条缝。
- 行序倒置，**HEAD 在最上面**，分叉点在最下面。倒置发生在页面投影层；
  `janus.history.list` 的输出次序不变。
- 行数据仍携带 `sha` 与 `author` 字段：行是选中通道的载荷，按字段名取值的地方不止列表。

## 系统架构

| 组件 | 路径或位置 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- | --- |
| 模块入口 | `b-Code-Studio/Module` | 接收宿主上下文，注册命令和页面描述投影 | `IModuleContext`、`CommandRegistry` | 命令注册与 Aurora V1 页面描述 |
| 业务组合 | `b-Code-Studio/StudioBusinessComposition.cs` | 组合项目、Git 规则、历史、GitHub 与图谱命令 | 宿主设置、日志、数据根 | 4.3.0 目标 40 条业务命令（`janus.*`，五类含 `graph`）；组合根注册 `proj.rename` 与其它项目命令；宿主另投影 `janus.status`；实现与本合同同版本落地 |

### 关键流程

1. HistoryVulcan 从自身 Modules 目录读取 manifest 并装载 `HistoryJanus.dll`。
2. `IModuleContextAware.Attach` 使用宿主 registry、bus、settings、log 与 data directory 注册业务组合。
3. Aurora 读取 `janus.ui.describe` 与 `janus.ui.actions` 建立三个页面，再按页面数据源调用 `janus.ui.data`；图谱节点详情调用 `janus.ui.graphnode`。项目总览展示项目与状态，图谱并入控制台标签组，项目操作页提供提交、推送与治理操作。GitHub 写操作必须通过宿主命令总线执行并服从确认策略。
4. 发布管道验证源码、模块生命周期和包集合后提升到 z 级正式消费区。
5. 部署管道原子更新 UI/Service 两个模块槽，并保留上一正式部署用于回滚。

### REQ-015 三块子内容收进项目操作页，由轮换选项框切换（5.4.6）

- 目的：把 5.4.5 的底部三标签收成一页里的一个控件。标签组是**三页**，各占一条底边、
  各自还顶着一段说明文字；收进一页之后版面只剩一条选项框，三块内容拿到同一块完整高度。
- 要求（切换器并入现有控制面板）：`janus-projops` 增加第四行——
  `{ kind: "textbox", id: "section", mode: "select", channel: "janus.section",
  options: [ "Git 文件规则", "分支历史", "GitHub" ] }`（Aurora REQ-UI-045）。
- 约束（排在最后一行）：它管的是自己**下面**那块内容。排在前面的话，人得隔着三行
  项目操作才能把「转了一下选项框」和「下面变了」联系起来。
- 约束（不写 `enabledWhen`）：切页面与选没选中项目无关。按选中启停会让
  「没选项目时连看一眼 GitHub 状态都不行」。
- 要求（内容是 `switch` 容器）：`janus-sections`，`source = {selection.janus.section.value}`，
  三支的 `case` 与选项框的候选项是同一组常量（Aurora REQ-UI-046）。
- 约束（标题只写一处）：候选项与 `case` 取自同一批常量。两边对不上时**不报任何错**，
  表现是切到某一项后下面永远停在第一支——与「这一支没数据」长得一样。
- 要求（各页控件跟着自己那一支走）：「刷新规则」留在规则支的面板里，
  「刷新 GitHub」留在 GitHub 支的面板里。切到哪一支就只看得见哪一支的控件。
- 要求（刷新改为按节点）：三块同处一页之后按页刷会把没被点到的两块一起带上，
  而 GitHub 那条要探 SSH 与凭据助手。`janus.github.refresh` 改 `node=github-rows`；
  规则支有两张表而 `refreshdata` 一次只收一个节点，因此过一道 `janus.ui.refreshrules`，
  由它按节点刷 `rule-list` 与 `rule-state`。
- 要求（删掉页面顶部的说明段落）：四页顶上那几段「这一页是干什么的」全部删除，
  面板内的说明文字同样删除。它们占的是版面，给的是一次性的信息——
  每个打开这一页的人都要重新翻过去一次，而其中内容属于文档。
- 附带（内边距不再由 Janus 操心）：模块页贴着窗格边框画的问题在 Aurora REQ-UI-047 修掉，
  描述里没有、也不需要任何对应字段。
- 验收：`ProjectOperationsPanelContractTests` 的
  `TheThreeSectionsAreFoldedIntoTheOperationsPageBehindOneOptionBox`（含「候选项与 case
  逐字相等」这一半）、`NoPageStillCarriesAPreambleParagraph`、
  `TheRefreshButtonsActuallyRefetchTheirOwnNodes`。
- 依赖：Aurora ≥ 1.8.17。低于该版本时 `channel` 与 `switch` 都不被认识——
  选项框变成一个普通的选择框，`switch` 渲染成一块「该组件待交付」的占位牌。

### REQ-014 项目操作页是一块控制面板（5.4.5，5.4.6 增至四行）

- 目的：选中一个项目，就能对它改名、以它为模板新建、提交和推送——不必再把项目名手打一遍。
- 背景（本轮实测的两处故障）：
  - `projops` 此前写的是页面级 `input` + `button`。这三种节点在 Aurora 1.8.14 已退役，
    真机上渲染成三块写着原因的牌子——**这一页没有一个能点的东西**。
  - `overview` 的表格塞在 `stack` 里，撑满整页且没有纵向滚动条。
    成因在 Aurora 侧（`stack` 曾是 StackPanel，以无穷高量子元素），已由 Aurora REQ-UI-042 修掉。
- 要求（页面结构）：`projops` 的内容是**一块**控制面板 `janus-projops`，
  四个声明行（Aurora 协议 V3 / REQ-UI-060）。5.4.5 是三行加一段页首说明；
  5.4.6 删掉说明、增加第四行子页面切换器（REQ-015）；
  5.4.7 随 Aurora 1.9.2 把 `widgets` 改成 `rows`：

  前三行走**可变宽度**，中间那个文本框写 `flex: true` 吃掉余量。
  不写 `flex` 的话可变的会是最右边那个按钮，于是输入框停在最窄宽度、
  按钮被拉成一条横杠——版面上一眼看得出，但没有任何一处会报错。
  第四行走**均布**：它只有一个元素，铺满整行读起来才像一个独立的切换器。

  1.9.2 之前这里是一个三列共享的 Grid，三行的标签列、控件列、按钮列互相对齐得像张表——
  而这三行本来就没有对齐的理由，对齐的代价是最长的那个按钮把另外两行的输入框一起挤窄。

  | 行 | 标签 | 控件 | 按钮 |
  |---|---|---|---|
  | 1 | 项目名 | `project-name`，跟随选中项目，可就地改成新名字 | 改名 |
  | 2 | 新项目名 | `new-project` | 新建（以第 1 行的项目为模板继承） |
  | 3 | 提交描述 | `commit-message` | 提交当前项目 / 推送当前项目 |
  | 4 | 子页面 | `section`，轮换选项框，切换下方内容（5.4.6，REQ-015） | — |

- 要求（接线走选择通道）：`overview` 的项目表声明 `channel = janus.project`；
  面板的 `project-name` 用 `follows` 跟随它的 `name` 列，四个按钮用
  `enabledWhen: { selected: janus.project }` 启停。**页内节点 id 跨不过页边界**——
  表在中央页、面板在左侧页，两页各渲染一次，只有界面级的通道名跨得过去。
- 要求（两个占位符命名空间不能混）：动作参数里「改谁」取 `{selection.janus.project.name}`，
  「改成什么」取 `{project-name}`。跟随框一开始等于选中行，人改过之后就不再相等——
  两边都从输入框取的话，改名会把项目改成它自己：指令成功、界面无异常、什么都没发生。
- 约束（不得使用 `required`）：这条本仓先立、Aurora 后收。面板的必填校验当年是**全局**的，
  任何一个必填框为空，面板上每个按钮都拒绝执行——把「新项目名」标成必填会连带锁死
  「改名」和「提交」，而报出来的错说的是「新项目名为必填项」，看上去与改名毫无关系。
  Aurora 1.9.2（REQ-UI-060）把这个字段整个退役了，本条因此转为**回归闸**：
  再写它不会报错，只会被静默忽略，那正是最难发现的一类不一致。
  参数缺失交给各条指令自己的 `Required` 去报。
- 约束（不新增后端指令）：四个动作分别落到既有的 `janus.proj.rename` / `create` /
  `commit` / `push`。本轮只改注册，业务面一个字没动。
- 要求（三块底部内容改为标签组）：**5.4.6 已由 REQ-015 取代**——三页收进 `projops`，
  由 `switch` 容器切换。5.4.5 的原文保留在此作为沿革：Git 文件规则 / 分支历史 / GitHub
  注册为三个 `side=bottom` 页面，由停靠层并成一个标签组；当时不用 `toggleGroup`，
  因为它是 Aurora 的缺件，照写只会得到三块占位牌。
- 要求（会跑 Git 的取数一律按单个项目）：`rulestate` / `history` / `graph` 的取数参数
  都写 `name = {selection.janus.project.name}`，缺 `name` 时 `janus.ui.data` **直接拒绝**，
  不退化成扫全库。落地状态每个项目要跑两条 `git ls-files`，全库一遍是 90 次进程启动——
  那不该由「打开一个页签」触发。排除清单本身只读设置，因此不带 `name`，开页即出。
- 要求（刷新按钮要真的刷）：「刷新规则」「刷新 GitHub」落到 Aurora 的取数刷新台账。
  5.4.4 之前它们绑的是业务指令，指令确实跑了、界面上那张表一动不动——
  「点了有反应」和「点了有用」是两回事。5.4.5 按 `page=` 刷，5.4.6 起改为按 `node=`
  点名刷（REQ-015）。
- 附带修正：图谱此前固定取项目清单的**第一条**，无论在总览里选了谁画的都是同一个项目。
  不报错，只是一直不对。改为跟着选择通道走。
- 验收：`ProjectOperationsPanelContractTests` 逐条核对通道、面板的四个声明行与行模式、
  只有项目名跟随、四个按钮都有启停、无 `required`、四个动作的参数取向，
  外加一条兜底（按钮引用的动作都存在、占位符都指得着东西）与一条
  「不得再出现退役节点 / 退役字段」。
- 依赖：Aurora ≥ **1.9.2**（REQ-UI-060 面板的行是一等结构）。
  这是一条**硬**依赖，不是「低版本少点效果」：1.9.2 之前的 Aurora 只认 `widgets`，
  拿到只写 `rows` 的声明会得到一块没有任何小组件的面板。
  更早的下限仍然记在这里备查——REQ-UI-041 选择通道、REQ-UI-042 栈内让位（≥ 1.8.16）；
  低于那一版时 `channel` / `follows` / `enabledWhen` 会被当作未知字段忽略，
  表现为按钮常亮、跟随框不填，**不会报错**。

# HistoryJanus 有效决策

## DEC-024 V5.1.0 正式消费快照豁免于排除清单

- 状态：已接受
- 日期：2026-08-17
- 决策：`.gitignore` 托管块尾部固定生成 `!z-*/` 与 `!z-*/**`，排在全部排除项之后。
  这是系统不变量，不进用户清单，也不可由清单关闭。
  同时把默认清单扩充为覆盖构建产物：新增 `packages/` 目录与
  `*.dll`、`*.pdb`、`*.lib`、`*.exp`、`*.ilk`、`*.idb`、`*.obj`、`*.cache`。
- 原因：`z-*` 是发布管线刻意入库的正式消费快照，跨项目依赖它——实测 `z-*` 内有 820 个
  dll/exe/nupkg 属于故意入库（如 `z-HistoryVulcan/host/*.dll`、各模块的 `z-<模块>/*.dll`），
  而 `z-*` 之外有 1085 个属于该排除。把 `*.dll` 写进清单是正确的，但若无豁免会把正式
  快照一并删出索引，等于毁掉跨项目消费面。gitignore 的否定规则必须排在排除项之后才生效，
  因此位置也是合同的一部分。
- 后果：
  - 清单里写任何后缀都不会波及 `z-*`；用户不必为了保住快照而放弃排除构建产物。
  - GitRules Smoke 用真实 git 仓库断言「排除生效但快照仍被跟踪」，含嵌套目录。
  - 已被跟踪却命中排除项的文件仍不自动移出索引，仍由 `janus.gitrule.list` 点名。
- 替代条件：若将来正式快照改用别的目录前缀，需同级决策并同步改这条豁免与其断言。

## DEC-023 V5.0.0 规则面收敛为一份全库共用的排除清单；LFS 退出规则面

- 状态：已接受
- 日期：2026-08-17
- 决策：
  1. **Git 文件规则只回答一个问题**——这个后缀/目录要不要进仓库。取消按格式维护
     Git/LFS/LF 三态的规则表，取消格式台账与规则建议。
  2. **清单全库共用一份**，存在设置 `proj.excludesuffixes`，不按项目分化。
     目录项以 `/` 结尾，后缀项写 `*.xxx` 或裸文件名；生成时给含内部分隔符的目录项
     统一加 `**/` 前缀。
  3. **不再有人工下发步骤**。清单由提交链路每次幂等刷进各仓 `.gitignore` 托管块，
     `janus.gitrule.sync` 一并退役。托管块外内容逐字保留。
  4. **LFS 完全退出规则面**，只在提交链路触发：仅当单个文件超过 GitHub 的 100MB
     硬限时才弹确认，同意则对该**具体路径**执行 `git lfs track`，拒绝则中止该仓提交
     （超限文件不走 LFS 也推不上去）。阈值取 GitHub 硬限而非可配置偏好。
  5. 命令面从 7 条减为 2 条：`list`（只读）与 `excludes`（确认写入）。
     `set` / `batchset` / `remove` / `sync` / `scan` / `review` 一次性退役，不留别名。
- 原因：那套规则面本身就是故障源。实测模板派生的 `.gitattributes` 有 **137 条**按扩展名的
  LFS 通配，把 `*.asm` / `*.baml` 这类文本也塞进 LFS，最终造成 11 GB LFS 占用、
  历史中大量 LFS 对象丢失、推送被 GitHub pre-receive 钩子拒收。三态规则表还要求人工
  逐格式判断并手动 sync 下发，认知成本高而收益是负的：绝大多数项目的正确答案完全相同。
- 后果：
  - 命令总数 40 → 35（含并行落地的 DEC-022 新增的 proj.rename）；`gitrule` 类保留但只剩两条命令。破坏性变更，主版本升 5.0.0。
  - 删除 `FormatInventoryService`、`FormatInventoryModels`、`RuleSuggestionEngine`、
    `GitFileRuleService.Batch/.Storage` 与规则表 UI，共约 2100 行产品代码。
    QA-008（规则批量交互）随之退役，由 QA-012 取代。
  - `.gitattributes` 不再由 Janus 生成任何内容；LFS 行只在人工同意后按精确路径追加。
  - 已被跟踪却命中新排除项的文件**不会**自动移出索引，`janus.gitrule.list` 点名它们，
    由人工决定是否 `git rm --cached`——自动移出索引等于代替用户做删除决定。
- 替代条件：若将来确实需要按项目分化排除清单，需同级决策，并说明如何避免重新回到
  "每个仓一套规则"的认知负担。

## DEC-022 V4.3.0 项目展示名与工作树目录同步改名

- 状态：已接受
- 日期：2026-08-17
- 决策：项目操作页第二行改为当前项目名称输入框与“改名”按钮，按钮调用
  `janus.proj.rename`，经宿主确认后把已登记项目名和库根直接子目录同步改名；独立仓的 Git 主线继续固定为 `main`。
  受保护项目、非法/越界名称和目标重名拒绝，成功后清除继承树缓存并由页面刷新共享选择。
- 原因：一项目一仓架构下，项目分支展示名与工作树目录是同一登记身份；原页面只能看到名称，用户必须手工移动目录，
  容易造成 Janus 列举、继承树和共享选择暂时不一致。
- 后果：业务命令从 39 条增加到 40 条，运行时总数从 40 条增加到 41 条；版本提升到 4.3.0。
- 替代条件：若未来允许仓内主线随项目改名，需另行定义 Git 分支迁移、远端跟踪和保护策略，不得复用本命令语义。

## DEC-021 V4.2.0 远端仓库名只用项目编号

- 状态：已接受
- 日期：2026-08-17
- 决策：自动建仓时远端仓库名取项目编号 `YYYY-NNN`，不带标题部分；本地项目目录名不变。
  没有编号前缀的项目名原样送出，由 GitHub 命名规则校验拦截。
- 原因：GitHub 会把仓库名里的非 ASCII 字符整段吃掉——实测请求 `2025-001-AGV洗轮机`，
  建出来的是 `2025-001-AGV-`。库里 42 个项目有 30 个是中文名，照目录名建仓会得到一批
  只剩编号加连字符的无意义名字。而 `GitHubRepositoryProvisioner` 的名字校验
  （`^[A-Za-z0-9._-]{1,100}$`）本来就会把中文名挡在调接口之前，等于功能对多数项目不可用。
  编号本身已经唯一，用它既躲开截断，也不会互相撞名。
- 后果：
  - 本地目录名与远端仓库名刻意不一致：本地保留中文便于人工查找，远端只认编号。
    需要对外展示的仓库由用户自行在 GitHub 上改名，Janus 不跟踪改名结果。
  - 已按旧规则建出的仓库（`0000-000-Template`、`0000-001-AIReady`、`2026-018-MyAPI`）
    保持原名、不回溯改名；它们的 origin 已配好，重推不会再触发建仓。
  - 命名规则落在 `ProjectRepoLayout.ToRemoteRepositoryName`，与项目名身份规则同处一地。
- 替代条件：若将来要求远端名可读（英文标题或拼音），需同级决策，并解决为存量项目一次性
  起名、以及改名后如何与本地目录对应的问题。

## DEC-020 V4.1.1 自动建仓的 origin 优先写 SSH

- 状态：已接受
- 日期：2026-08-16
- 决策：`EnsureRemoteAsync` 写入 `origin` 的 URL 改为优先接口返回的 `ssh_url`，
  只有接口没给 `ssh_url` 时才退回 `clone_url`。本条修订 DEC-019 第 2 条。
- 原因：实测本机 HTTPS 推送在包体约 17MB 以上会被稳定重置（`curl 55/56 Recv failure:
  Connection was reset`），`http.version=HTTP/1.1` 与 `postBuffer=500MB` 均无效，
  分批也救不了——模板仓单个提交 `20ac2b7` 自身就带 17MB。同一个包走 SSH 一次推完。
  按 DEC-019 原方案配出来的 HTTPS origin，在这台机器上等于把新建的仓推不上去。
- 后果：
  - 推送认证面从 GCM 的 HTTPS 凭据转到 `~/.ssh` 的密钥。**建仓本身仍走 HTTPS token**
    （`git credential fill` + GitHub API），两条链路的凭据来源从此不同，排查时不要混为一谈。
  - 未配置 SSH 密钥的机器上，自动建仓能成功但推送会失败。错误信息里已带上建出来的仓库名。
  - `GitHubRepositoryCreation.OriginUrl` 是唯一的选择点；`CloneUrl` / `SshUrl` 仍如实保留接口原值。
- 替代条件：若将来 HTTPS 大包推送恢复正常，或需要在无 SSH 密钥的机器上运行，可改回
  `clone_url` 优先，或做成按机器可选——两者都需同级决策。

## DEC-019 V4.1.0 首次推送无条件自动建远端仓库，默认公开

- 状态：已接受
- 日期：2026-08-16
- 决策：`janus.proj.push` / `janus.proj.pushall` 在仓库没有 `origin` 时，直接用 GitHub API 建同名仓库、
  `remote add origin` 后再推送，不额外多弹一次确认。可见性由可选参数 `visibility` 决定，默认 `public`。
  1. 令牌来自 `git credential fill`（`janus.github.login` 已把 HTTPS 凭据存进 GCM），不新增凭据面、不落盘。
     必须带 `credential.interactive=false`：推送跑在无人值守的宿主进程里，缺凭据时不能弹 GCM 窗口。
  2. ~~`origin` 用接口返回的 `clone_url`（HTTPS），与 GCM 里的凭据形式一致；`ssh_url` 只记录不使用。~~
     **已由 DEC-020 修订为优先 `ssh_url`。**
  3. API 返回 422（同名仓库已存在）时改为复用该仓库，不把首次推送卡死；可见性以接口事实为准。
  4. 建仓失败绝不写 `remote`，避免留下半配的 origin 让下一次推送更难诊断。
  5. 新建的仓库名与可见性写进结果消息和 `HistoryRecorder`，出事可追溯。
- 原因：42 个项目仓全都没有 remote，逐个手工建仓库再配 origin 的成本远高于推送本身；
  而 `PushAsync` 原先硬跑 `git push origin HEAD`，「远端还不存在」这个状态在模型里没有位置，只会报底层错。
- 后果：
  - 在没配 origin 的仓库上执行 `pushall`，GitHub 上会直接多出一批**公开**仓库，只经过 pushall 自身那次确认。
    确认文案已写明将按哪个 visibility 建仓；需要私有时显式传 `visibility=private`。
  - `IGitHubRepositoryProvisioner` 独立于 `GitHubConnectionService`：后者绑定单个仓库路径，
    而推送按各自的项目工作树发生，路径必须逐次传入。
  - `ProjectService.RepositoryProvisioner` 可空，为空时退回旧行为（没有 origin 就直接失败）。
  - 门禁不得联网：Smoke 用假 provisioner 和假 HTTP handler 覆盖建仓、复用、失败与已有 origin 四条路径。
- 替代条件：若将来要求建仓前逐仓确认，或默认改为私有，需同级决策。

## DEC-018 V4.0.0 平行泳道优先贴主线，按水平占用复用空行

- 状态：已接受
- 日期：2026-08-16
- 决策：平行分支的 Y 不按发现顺序永久占一行。先按 Git 父链确定哪些提交同属一条逻辑支线，再按该支线的水平跨度
  从主线向下寻找第一条空行。
  1. 主线固定第 0 行。
  2. 不相交的已合并历史行必须共用靠近主线的空行；不得因为后面又出现一条新支线，就把更早的短支线挤到空白行下方。
  3. 只有同一水平区间已被其它平行分支占用时，才下移到下一行。
  4. 开放 tip 和已合并无端点的语义不变；一条逻辑支线内部仍画在同一行。
- 原因：按 ref / 第二父的发现顺序给每条支线分配递增行号时，右侧新分支会先占住靠近主线的行，
  左侧已结束的短历史行只能落到很远的空白下方，分支一多就不可读。
- 后果：`GraphLayout` 在赋 X 之后按水平跨度贪心贴主线；`BranchGraph` Smoke 必须覆盖「不相交共用最近行」
  和「相交才下移」两种回归。
- 替代条件：只有改用逐提交动态列（gitk 风格）且仍保证短历史行贴主线的同级决策可以替代。

## DEC-016 V4.0.0 图谱 X 由 Git 父边决定，不按全局时间轴平移整条泳道

- 状态：已接受
- 日期：2026-08-16
- 决策：每个提交的横坐标由其 Git 父提交决定，而不是由全局时间戳或整条泳道平移决定。
  1. 节点 X = 其全部已布局父节点与同泳道前一节点的右侧一个标准节点间距；无父节点时落在左起点。
  2. 因此开放平行分支的首节点自然紧邻主线分叉父节点右侧；已关闭历史分支的末节点自然紧邻消费它的
     主线 merge 左侧。多提交历史行同时满足这两端，不得为了钉住 merge 而越过分叉点。
  3. 禁止先按全局时间轴铺开、再把整条平行泳道平移去贴住分叉或 merge。那种算法只能钉住一端：
     提交数多于分叉到 merge 的主线 hop 时，历史行会跑到分叉左侧；时间跨度大时开放行会在时间轴上拉得很长。
  4. 提交时间只用于拓扑平局时的处理顺序，不设置 X；开放 tip 和已合并无端点的既有语义不变。
- 原因：不同分支的提交时钟不保证单调，也不保证与 Git 拓扑顺序一致。仅按全局时间轴定位会把分支节点
  拉到分叉点或 merge 很远的位置；只平移整条泳道则无法同时贴住分叉和 merge。
- 后果：`GraphLayout` 按父边逐点赋 X；`BranchGraph` Smoke 必须覆盖倒序时间戳、已合并多提交越界和
  开放行时间跨度三种回归，直接断言节点间距。图谱命令、DTO、窗口 ID 和对外命令总数不变。
- 替代条件：只有引入新的图谱坐标合同、且能继续保证分叉/合并可读性的同级决策可以替代。

## DEC-015 V4.0.0 一项目一仓；库根 HistoryClio；仓内默认分支 main

- 状态：已接受
- 日期：2026-08-14
- 决策：对齐 HistoryVulcan DEC-040。Janus 的存储单位是**一个编号项目一座独立 git 仓库**，
  不再把项目编码成共享裸仓上的分支或 git worktree。
  1. **库根**默认 `C:\OneHistory\HistoryClio`，设置键 `proj.libraryroot`。
     删除 `proj.barerepo`。旧键 `proj.worktreeroot` 只读一次作迁移：若不是 Vesta 默认路径则当作库根，不再写入 barerepo。
  2. **身份**：已登记项目名 = 库根直接子目录名（`YYYY-NNN-*` / `0000-*`），且 `.git` 必须是目录。
     仓内默认分支固定 `main`。`name=` 仍是项目文件夹名，调用方口令不变。
  3. **创建**：从模板**项目仓**复制工作树（排除 `.git`），`git init -b main`，首提交在 `main`。禁止 `clone`，以免把模板历史带进新仓对象库。
  4. **删除**：删目录；受保护的是**项目名**（默认模板 `0000-000-Template`），不是 `main`。
  5. **修复**：逐仓诊断（独立 `.git`、能 `status`）。若仍是指向 Vesta 的 `.git` 文件则报告，不自动删盘。退役「删光全部工作树再按分支重建」。
  6. **图谱 / 历史**：`git -C <项目>` 的 refs；主线 `main`；平行线本仓其它分支（`ai/<项目>/`）。
     范围天然是本仓，不再用正则剔其它编号项目，也不再相对父编号分支做 cutoff。
  7. **继承树**：读各仓 `project.manifest.json` 的 `template.source`，不再用裸仓 `merge-base` 假装共用历史。
  8. **规则同步**：从模板**仓**拷 `.gitattributes` / `.gitignore` 的 baseline 块。
  9. **禁止两套引擎并存**。本轮不注册 `janus.aiworktree.*`；引擎允许在**某个项目仓**上再挂 worktree，写路径仍按 DEC-012 推迟。
- 原因：共享裸仓里项目与分支平级，单项目多分支会污染其它项目的 `refs/heads`。HistoryClio 里编号项目已经是独立仓。
- 后果：版本升到 4.0.0（存储引擎破坏性变更）；命令名与三个窗口不变。DEC-014 作废。
- 替代条件：只有再次改项目库编码的同级决策可以替代。

## DEC-014 V3.9.3 新建与修复工作树时补齐裸标记覆盖

- 状态：已作废（由 DEC-015 替代）
- 日期：2026-08-12
- 决策：`ProjectService` 在 `git worktree add` 成功后、以及 `RepairAsync` 重建全部工作树后，
  统一调用 `WorktreeBareMarker.Ensure` 确保
  `<裸仓>/worktrees/<名>/config.worktree` 里有 `[core] bare = false`。
- 原因：本项目库的裸仓同时开着 `core.bare = true` 与 `extensions.worktreeConfig = true`。

  于是每次新建都会重现，且 `RepairAsync` 重建后的 status 复测必然失败。
- 后果：
  - admin 目录由工作树 `.git` 文件里的 `gitdir:` 指针解析，不按目录名推算——

  - `Ensure` 幂等：已声明 `bare = false` 时不写盘，也不覆盖该文件里的其他 per-worktree 配置。
  - 补写失败不阻断建项：项目已经创建成功，只在返回消息里附带警告并指向 `janus.proj.repair`。
  - `RepairAsync` 摘要新增补写计数；补写失败计入整体失败。
- 验证：新增 `WorktreeBareMarker` Smoke 套件，先在夹具上**复现**故障
  （断言缺覆盖时 `git status` 必须失败且原因正确），再验证修复、幂等与非工作树的明确失败。

## DEC-010 V3.7.0 Git 等待归属与文件规则离页保存

- 状态：已接受
- 日期：2026-08-11
- 决策：
  1. 产品 `GitRunner` 不再设置固定墙钟超时。Git/Git LFS 自己决定传输超时或失败，
     Janus 只响应宿主取消；GitHub 诊断和测试套件的显式超时保持独立。
  2. Git 文件规则在页面内只形成内存草稿。规则面板失去可见性，以及项目切换、刷新或删除前，
     使用现有 `janus.gitrule.batchset` 进行一次预览、一次宿主确认和一次批量应用。

- 原因：大文件的 add、commit 或 push 可能合法地超过 Janus 原有 300/600/1800 秒上限；
  主动杀死仍在工作的 Git 会制造假失败，并可能让紧接着的重试碰到 `index.lock`。
  文件规则原有 600ms 自动保存又会把每次勾选都变成一次确认和索引同步，无法连续调整多条规则。
- 后果：
  - 长 Git 操作不再由 Janus 自决超时；真实非零退出码和 `index.lock` 错误仍原样报告，
    Janus 不猜测成功，也不自动删除锁文件。
  - 规则保存确认从“每次编辑后”收敛为“离页时一次”；无脏数据或预览无变化时不弹确认。
  - 宿主整体隐藏页面时无法撤销外层导航；保存失败仍保留草稿，并保证返回时选中规则分段。
